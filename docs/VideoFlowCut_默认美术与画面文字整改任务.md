# VideoFlowCut 默认花字与整场视觉开发方案

**目标：用户只给主题，系统也能主动做出有花字、有材料层次、美术与动作相互配合的解说视频；出处、原件页码和研究备注不作为新增说明叠到画面上。**

本方案讨论项目的正常制作能力，不是某条机票视频的分镜。先解释问题和原因，再说明优化方案与取舍，最后给出开发位置、具体文案和验收办法。正文包含实施所需的判断，不要求接手者阅读聊天记录或其他方案。

<a id="problems"></a>
## 一、问题：哪些没有达到要求，哪些已经有效

### 1.1 要解决的是默认输出不足，不是用户不会描述需求

完整解说制作不应要求用户先懂字体、描边、材质、构图和运动机制。用户只给主题，专业作者就应主动选出值得强调的内容，设计重点文字的造型，并安排素材、文字和图形怎样共同表达。

当前反复出现的情况是：主题任务可以完成正文、取材、生成和导出，但重点文字仍主要采用普通粗体、放大、换色和移入。画面组织又回到“上方说明、下面内容”或“左边大字、右边资料”。在这种结构里增加动效，往往只是让同一张页面更新得更顺。

**本产品要交付的花字，是承担问题、反差、转折或结论的画内重点文字，具有明确造型，并与当前场面共同运动。** 具体轮廓、承托、字形、配色和动作由作者决定。普通字幕、准确条件和表格小字不需要全部花字化；用户只要求机械改字或保留原片时，也不扩大成重新设计。

这里的要求包含两个层次：重点文字本身要做出来；它还要与整幅画面配合。只把普通大字换成描边大字，仍然放在永久标题栏里，只完成了其中一部分。

### 1.2 已有材料能证明什么

| 已核对的材料 | 能确认的事实 | 对问题定位的意义 |
|---|---|---|
| 视觉入口和美术方法 | 已写入“无偏好也进行整场设计”，并接入按需参考 | 不能继续把原因概括为“职责没写”或“案例目录不存在” [E1] |
| 开发样本 `cabin.tsx` | “空间”主要通过字号、字距、横移和一条横线呈现 | 该样本的文字造型在提交源码时就比较基础，不是丰富花字被渲染丢失 [E2] |
| 开发记录中的实际查询 | 已指定“实景向一侧让位，另一侧文字显露” | 作者在搜索前就选择了侧栏结构，检索主要是在补实现手段 [E2] |
| 已获用户动效认可的参考 | 客舱显示范围、相关花字与解释区域共同变化；费用退出后，剩余内容实际取得空间 | 现有制作能力允许更完整的对象协作，不能直接认定渲染器只支持局部动画 [E3] |
| 当前生产截图 | 可以看到新增来源长条、原件页码，以及反复使用的左右资料布局 | 这些静态呈现问题确实存在；截图不足以判断完整动态、运行版本或具体绘制组件 [E7] |
| 开发与验证记录 | 接口、声音、SRT、字幕布局等有技术测试；作品样本没有完成完整正常入口的创作验收 | 技术成果要保留，视觉能力仍须独立验证 [E2] |

参考作品的用户认可范围是动效，不能扩大为所有美术和完整声画均已通过。当前花字目标来自明确的产品要求；参考用于说明可见的造型和协作方法，不用于擅自确定全项目风格。[E3]

### 1.3 来源说明是另一类问题，不能与美术不足混为一谈

花字是否好看，需要模型作设计并查看作品。新增出处、页码是否违反任务要求，则有更明确的文字与数据边界。

当前 `DocumentVisual` 只在 `props.sourceCaption` 非空时显示来源，已经避免了部分元数据自动上屏。但作者主动填写该字段，或者直接在 TSX 中画一行“来源：……”，仍然能够产生出处长条。[E4]

**“字段默认不显示”只解决程序自动添加，没有解决作者主动添加。** 如果任务要求不增加来源说明，显式填写字段也应该受到约束。

同时，出处长条可能混有真正的适用日期、含／不含条件和单位。这些内容需要拆开：删除制作性出处，不得连同影响结论的条件一起删掉。

### 1.4 本方案保留什么

保留已经实现并有测试记录的原旁白放置、原 SRT 导入、字幕实际行数高度、素材绑定、源时钟、正式渲染和恢复规则。完整声画仍要在实际作品中检查，但不因美术不足推倒这些技术能力。

保留现有导演、视觉作者、素材作者与审阅职责，不增加同义代理。已认可参考保持原视频和源码，不为修改教学说明重渲染参考，也不把当前生产作品未经批准覆盖。

<a id="causes"></a>
## 二、原因：为什么参考完整，生成结果却只剩局部效果

### 2.1 “源码里没有花字”只是定位起点，不是根因分析的终点

一个最终效果至少经过四个环节：任务要求、具体设计、源码实现、渲染输出。发现源码没有实现目标，只能先排除“本来设计并实现了，后来被渲染丢掉”这一种解释。

还要继续判断：当前稿有没有设计花字？交给实现者时是否保留了具体造型？作者是否认为普通大字已经达标？生成后，为什么没有按实际差距返工？

开发样本中的普通文字写法、预先指定侧栏的查询，以及作品验收范围有限，共同支持一个判断：**问题主要发生在创作决定和完成标准上，不能只按字体加载或渲染故障处理。** 对新的生产任务，仍需读取它自己的设计稿和源码，不能用开发样本替代其运行事实。[E1][E2][E7]

### 2.2 只有职责，没有一致的完成标准，作者仍可能交出基础答案

“负责整场设计”“主动设计重点文字”说明了职责，但并没有自动让所有作者对完成程度形成相同判断。作者可能认为：用了粗字体、放大、换色，就完成了文字设计；让素材缩到一侧，就完成了整场变化。

与此同时，“不强制描边”“不固定风格”等要求本来是为了保留创作空间，却可能被解释成降低完成度的理由。于是作者并不认为自己少做了工作，而是把较弱的结果称为一种克制选择。

**解决办法是明确区分结果要求与实现自由：花字是需要交付的重点设计；采用哪一种花字造型，是作者的自由。** 不固定拼贴、胶带或色板，不等于默认可以让所有重点退回普通标签。

这不是给所有字强加特效。结果标准应落在实际重点上：它是否形成了与普通辅助文字不同的视觉对象，是否参与当前表达，是否与素材、图形和空间协调。代码里出现了几个 CSS 属性，不能替代这项判断。

### 2.3 页面先定下来，机制就会被当作页面的补丁

从内容出发设计画面，与先排一张页面再寻找动画，是两种不同的工作方式。

前者先问“观众这时需要看见什么变化”，再共同决定主体、字形、空间和动作。后者先决定“图片在左、文字在右”，然后查询怎样让图片缩小、怎样让字出现。后一种查询即使找到了很丰富的参考，也容易只摘取适合当前页面的一小部分。

开发记录中的侧栏查询已经包含了这种布局选择。它能合理找到让位动作，但不能证明侧栏就是该内容最好的画面组织。[E2]

```text
表达任务被过早改写成固定布局
                 ↓
机制检索只解决这个布局缺少的动作
                 ↓
不适合当前布局的参考内容被舍弃
                 ↓
原页面继续保留，局部运动增加
```

因此，不能只扩大检索数量。**要让参考在构图尚可调整时参与，并允许作者根据实际材料改变当前布局。** 有明确品牌版式、用户锁定或实际阅读需求时可以保留布局；作者自己的第一种想法不应自动成为不可改的限制。

### 2.4 参考的动作被看到了，参考的美术与组织方法却未必被使用

一段参考的观感，可能来自文字轮廓、前后遮挡、素材比例、边界和运动共同工作。只读取“让位、聚焦、展开”这些动作关系，仍需要作者重新解决文字造型、材料质感与整场构图。

如果作者读完动作说明就开始写代码，美术部分很容易回到最熟悉的默认文字和纯底。此时不是库里没有花字，而是参考中关于美术的可见信息没有转成当前设计。[E1][E3]

同一批机制已经包含正文、分镜和相关媒体入口，不需要再安排一个美术作者重搜。需要补的是：**实际查看这些图像与必要视频，把适合本片的造型和协作关系选出来。** 动作合适但美术不合适，可以分别选择；不能把动作采用视为美术工作也已经完成。

局部借鉴本身合理。参考只帮助解决一个对象退出时，其他对象怎样重排、重点字怎样参与，仍由本片作者完成。完整的是本片的观看过程，不是对参考逐项复制的比例。

### 2.5 抽象查询是为了找资料，不能成为实现者唯一的设计输入

“从整体中突出一个对象”适合跨题材搜索。它不说明本片的主体是谁、文字长什么样、谁让出空间、进入细节以后怎样继续。

如果设计再被交接成“突出重点、增强层次”，实现者就必须重新作选择。最容易写出的仍是基础文字、透明度和短距离移动。这样，即使上游曾有具体想法，也没有稳定进入源码。

当前 `creativeBrief` 有 6000 字符上限，可以保存提交摘要，但不适合独自承载复杂场面的全部设计。完整当前稿应沿现有任务文件交接，不应为了压缩摘要而删除重要动作和造型。[E5]

**解决的重点不是要求文档无限变长，而是减少重复概括。** 同一位作者尽量沿同一份具体画面稿完成设计、源码和修订；换人时传真实稿和必要资料，不再重新摘要成几个形容词。

### 2.6 把文件直接当画面，容易只剩“素材加文字”

素材文件解决“有什么”，不直接解决“它以什么形式出现在画面里”。一张原表可以作为证据全貌、阅读局部，也可以在核对数据后产生编辑图形；一条视频可以占满画面，也可以与解释区域共同改变显示范围。

同样，花字不是一个文本字符串。它可以由文字、轮廓、承托和相关图形构成；这些部分何时一起动、何时分开，属于画面设计。

如果主体始终只是一个不可改变的图片框，文字始终只是一个独立标签函数，协作自然容易停在“图片缩小，旁边出字”。已认可参考中的共同变化说明，现有代码可以组织更完整的关系：素材窗口改变时，相关文字和新解释区域也按同一过程安排。[E3]

需要补的是这种对象组织与设计，不是默认把所有照片抠图或三维化。真实素材不支持分层、背面或跟踪时，应调整表现或补材，不能编造能力。

### 2.7 技术验证覆盖了执行，却没有覆盖用户期待的作品结果

接口成功、视频可解码、字幕高度正确，都是必要测试。但它们回答的是程序有没有按输入执行，不回答输入中的设计是否值得采用。

开发记录明确说明了微型样本、直接应用层调用、局部借鉴和未完成连续观看等边界。因此，不应指责技术测试虚假；真正缺的是从正常用户入口到实际作品的创作验收。[E2]

即使已有专业审阅 Skill，也不能据其存在推断实际完成了审阅。记录里看到的若主要是错字、边距、遮挡和数据问题，作品可能越来越准确，却仍没有满足花字和整场设计要求。

**“用户没有再提要求”不能作为默认美术完成的证据；“连续听审还没做”也不能掩盖静帧已经能确认的缺失。** 但一张静帧只能说明对应时刻，不足以证明整个视频从未出现花字或全部动作都很弱。

### 2.8 来源问题来自“后台依据”与“可见文字”的边界不完整

证据方法要求核实来源、保留条件，这是正确的。若把它解释成每段必须画出机构、文件名和页码，就会把研究记录变成页面组件的一部分。

当前显示逻辑主要看 `sourceCaption` 是否为空。作者主动填入后，程序没有仅凭该字段就判断“这是内容必需，还是未经要求的新增出处”的能力。自由 TSX 还可以完全绕开该字段。[E4]

所以，要解决两件事：作者在设计时把两类文字分开；程序对有明确结构的来源展示检查任务策略。复杂动态字和图像内容仍需结合实际输出判断。

这里不能把所有来源相关文字都删除。机构可能就是讲述对象，原件也可能自然带页码；真正要禁止的是未经要求新增的出处说明层，而不是事实本身。

### 2.9 因果判断与尚待核对的部分

本方案的主要判断是：**默认目标没有稳定转成具体设计，设计又容易受先定页面限制；参考与实现只完成局部任务，作品验收未及时纠正；来源展示则存在可明确修复的数据边界缺口。**

这些判断由当前源码、查询和记录支持，不是经过单变量实验得到的唯一原因。实际发布版本、当前作者读到了哪些文件、某个作品是否走了内置模板，仍要用该任务的运行记录核对。不能因为截图相似就断言插件未部署，也不能看到模板代码存在就认定该作品使用了模板。

<a id="solution"></a>
## 三、优化方案：让默认制作完成具体设计

### 3.1 先明确产品承诺，再给作者选择空间

完整解说默认包含三项工作：重点短语的花字设计，真实素材与图形的材料层次，以及随内容发展的整场构图和动作。个人偏好为空时照常执行。

具体色号、字款、材质和运动由本片决定。用户要求简洁时，减少竞争和多余装饰，不把设计工作关闭。普通字幕保持独立稳定。只改字、只导出或保留原片的任务，则按真实范围处理。

这项要求放在正常业务方法中，不通过伪填 `explicitCreativePreferences` 为某种风格来启动。**默认的是设计能力和完成度，不是一张固定外观。**

### 3.2 让美术与动作决定同一个过程

同一连续范围由现有视觉作者持续负责。美术不先交一份不可改的静态页面，动画也不只接一个需要填效果的区域。

作者同时决定四件事：当前看谁；重点文字具体怎样出现；主体变化时其他内容如何配合；读清后下一内容怎样进入。造型、颜色、材质与动作都包含在这些决定中。

已经成立的参考可以帮助选择，已经锁定的事实继续保持。主素材需要更大空间时，可以改文字位置；文字承担转折时，可以临时成为主要画面。变化要由内容推动，不为制造运动而让所有层同时动。

### 3.3 正常流程怎样运行

```text
主题、可选素材和真实要求
              ↓
主任务承接默认花字、美术与画面文字规则
              ↓
文案研究 ↔ 主题取材，真实文件分批返回
              ↓
导演交清表达重点、事实边界与前后关系
              ↓
视觉作者查看材料和已有参考
共同决定花字、构图、材料与动作
              ↓
同一份具体画面稿 → 源码与真实绑定
              ↓
正式生成 → 查看真实作品
   ├─ 设计缺失：回当前范围完成设计
   ├─ 实现遗漏：保留设计并修源码
   ├─ 已实现但不好看：重选相关美术与构图
   └─ 违规说明：删除新增说明，保留必要条件
              ↓
声音、普通字幕与画面合成 → 终检 → 交付
```

这是现有工作的内容与交接关系，不是新增逐镜审批。无依赖的素材、声音和设计可以并行，相关材料到达的部分先做。正式声音已有时提前用于设计时钟，不等动画结束才考虑同步。

### 3.4 把参考用作设计依据，不当答案，也不只摘一个动作词

构图还可调整时，用本段真正需要表达的关系寻找候选。只有用户要求或材料条件确实限定布局时，才把该布局作为检索条件。并非永远禁止侧栏，而是不把第一种方便的排法直接当成唯一选择。

同一作者共用已有正文、分镜和视频。查看之后，落实为本片选择：借用了什么造型或对象配合，哪些因素材不同需要改变，剩余工作怎样完成。有缺口再补查，不因美术与动作是两项职责就重搜同一批资料。

开发者需要使用已认可范围的参考校准完成度。普通制作按需读取，用户不需要提供外部参考视频；不能把一个案例的金额、布局、配色和时长复制成全项目默认。

### 3.5 具体画面稿要能直接指导实现

沿现有场面稿写实际决定，不增加花字数据库或独立审批表。稿中至少让接手者明白：实际重点短语是什么，选定了怎样的造型，与哪个主体共同工作，怎样进入、读清和退出，下一内容使用哪里。

“做有设计感的花字”“增加层次”是目标，不是完成后的设计。作者要选定具体做法，而不是把描边、承托、遮挡等一串可选词交给下游继续猜。

同一人设计与实现时，当前稿可以很短，并随探索更新；无需在写任何代码前完成长篇报告。需要避免的是主要布局已经固定，重要美术与动作却仍以“稍后增强”占位。

### 3.6 正式输出必须允许推翻弱设计

已有设计被完整执行，不等于设计值得保留。审阅看实际作品，分别判断内容正确、设计兑现、视觉完成度。

花字没有设计出来，就回设计；花字已经具体却没写进源码，就修实现；字有轮廓但仍贴在固定资料页上，就处理构图与动作关系。不能把这些不同问题都改成“描边加粗一点”。

已经能确认的问题应在现有返修中处理。未知范围如实记录；预算不足或工具受限时交付草稿及缺口，不无限重试，也不把未完成说成通过。保留已成立的声音、字幕、数据和无关画面。

### 3.7 来源规则同时落在创作与显示路径

来源必须核实并保存，但新增出处和页码说明默认留在幕后。当前画面稿把旁白、普通字幕、画内重点与制作备注分开；代码只接收需要展示的内容。

对原生解释组件，程序检查明确的来源展示字段。对自由源码，静态检查能确定的出处层提前发现，其他情况由实际画面审阅补充。事实条件、原件自然文字和真正的署名要求分别处理。

这一项适合最小的任务级展示策略；它不是美术风格，也不是新增内容审核平台。其作用是让相同规则在创作、提交和渲染准备中一致生效。

### 3.8 为什么选择这套改法

| 其他看似直接的做法 | 不作为主要方案的原因 | 本方案的选择 |
|---|---|---|
| 再加一句“美术要高级” | 作者仍可用基础大字解释已完成 | 明确实际交付，并让设计、源码和作品互相对应 |
| 强制所有字描边 | 可能只得到带描边的资料页，小字还会难读 | 默认完成重点花字，具体造型和主次由内容决定 |
| 强制完整复制机制 | 素材不同，复制可能失真；也不能替代本片构思 | 理解完整参考，按材料适配，补齐本片剩余设计 |
| 增加通用花字组件 | 能减少代码，但无法自动决定何时使用及怎样布局 | 允许作品内复用绘制方法，不把组件化设为前提 |
| 多做几个几秒小样 | 容易只测一次入场与技术正确性 | 先用正常入口完成可比较的连续内容，再验证新主题 |
| 把所有“来源”词删掉 | 会误伤原件、叙述对象和必要条件 | 区分后台记录与新增展示，按来源层的真实用途处理 |

这些取舍的共同原则是：让模型承担本来需要判断的创作，让程序承担可以确定的规则；不让任何一方假装完成另一方的工作。

### 4.5 修改四：源码按设计组织对象，不添加固定页面外壳

**位置：** `remotion-production/SKILL.md`、其现有组件与素材方法，以及各作品实际 TSX。

实现要求如下：花字中的字形、承托、轮廓和影子有明确归属，共同进入和退出，组内可错开；主体变化时，相关文字和辅助内容按设计重排。素材时钟与窗口运动分开，普通字幕不进入花字或运镜父层。

**检查结果：** 对照同一段具体设计、源码和真实输出，能定位每项重要选择在哪里实现。若方案只是普通标签，修设计；若方案明确而代码少做了，修代码。

#### A. 最小任务级策略

优先检查是否已有等价的展示策略，有则复用。没有时，按下面的最小合同接入。**以下是拟开发接口，不是当前工具参数。**

```ts
type SourceDisplayPolicy =
  | { mode: "internal_only" }
  | {
      mode: "specified";
      exceptions: Array<{
        scopeId: string;
        text: string;
        basis: string;
      }>;
    };
```

`internal_only` 表示不新增出处说明。`specified` 只允许有真实依据的指定文本和实际范围，例如用户明确请求的署名，或核实后必须在画面内完成的署名要求。

建议使用 `project.brief.sourceDisplayPolicy` 随现有 Project/Revision 保存，不放进个人风格偏好，不新增数据库表。字段缺省的解析、合同迁移和历史恢复必须统一实现。

建议文件为 `packages/contracts/src/source-display-policy.ts`，导出 Schema 和解析方法；在 `packages/contracts/src/index.ts` 的 `CreativeBrief`、Brief Schema 及创建／获授权更新／读取投影中接入。字段足够则不扩展其他同义设置。

例外由现有获授权的主任务写入，`scopeId` 必须属于当前项目的有效范围，`basis` 能回到真实请求或署名依据。**`basis` 只是记录，不是授权证明；视觉 Props 自带 `allowed=true` 也不能自行授权。** 工具若没有区分调用者权限，不能宣称仅凭角色名称实现了安全隔离；先如实保留任务约定和依据核对，不能伪造权限能力。

#### B. 原生解释 Program 的确定性检查

**位置：** 解释 Program 的实际写入与校验路径、相关合同、`packages/remotion-runtime/src/explainer-registry.tsx`。

1. 写入前读取当前策略，对明确的 `sourceCaption` 检查范围与文本。`internal_only` 下非空即拒绝；`specified` 只允许匹配例外。
2. 建议错误码 `SOURCE_CAPTION_NOT_ALLOWED`。返回对象位置、冲突字段和纠正建议，不删除后台来源，也不先写入部分对象。
3. `eyebrow`、高亮 `label`、`state.detail` 仍能承载内容，去掉从文件名、出处和研究摘要自动补成展示文字的逻辑，不把这些字段全部禁用。
4. 正式渲染准备复核本次冻结的策略与输入。源码、参数或策略变化时更新相应身份，不复用不匹配的检查结论。

历史不可变作品和已导出视频不静默改变。恢复历史任务按其固定合同执行；新创作和明确修订使用适用策略。迁移前先核对真实快照、任务版本及哈希规则，不能统一给全部历史记录补默认值后宣称兼容。

#### C. 自由 TSX 的检查与边界

**位置：** `packages/edit-application/src/index.ts` 的受管作品提交路径及现有源码校验调用处。共用检查逻辑可集中到应用层的一个小模块，具体文件名按工程组织确定。

自由 TSX 能直接画出字符串，所以原生字段检查不覆盖全部作品。利用现有源码解析能力，定位可静态确定的独立出处文字、原件页码标签和来源元数据转成可见文字的映射，结合当前可见文字稿判断。

明确冲突的新增出处层返回定位信息并拒绝提交；语义不确定的内容只提示核对。例如视频在解释“数据来源”概念，不能因为包含该词就拦截。不要自动改写源码，也不要全局删除机构名。

动态拼接、SVG 路径绘字和素材像素不属于静态检查的完整覆盖。实际输出仍要检查新增说明层，没有命中不意味着绝对不存在。检查记录关联真实源码与输出身份，不能用旧记录给改动后的作品背书。

这项能力只处理明确的来源展示边界，不扩建通用审核平台；程序也不通过统计描边数量判断美术质量。

## 五、验证与交付：怎样证明默认能力真正生效

### 5.1 技术验收与创作验收分开

技术验收覆盖接口、来源策略、原子性、幂等、字体绑定、素材时钟、声音和字幕。保留现有测试成果，并以实际重跑结果报告。

创作验收回答花字有没有真正形成、素材与图形有没有共同工作、整段画面有没有发展。几个短片能生成，或者源码里存在 `textStroke`，都不能直接回答这些问题。

技术记录如果已经说明未验收美术，应保留这种边界。需要补的是作品验证，不是改报告措辞，把技术通过变成视觉通过。

### 5.2 先用相同内容，从正常入口生成

在已核对 Release 的 Worker 中新建独立任务。使用现有参考目录 `input/inputs/` 的准确正文、原WAV、SRT、原件与客舱素材，保留真实格式、时间和事实限制。历史 `input/开始制作.md` 不作为新的启动指令。

用户侧只提出“用这些内容完成解说视频”。花字、材料和整场协作要求来自开发后的运行时 Skills，而不是开发者临时给作者补一份答案。

通过正常分派、参考、设计、实现和返修生成。开发者不预写 TSX，不用直接调用渲染函数冒充主题创作测试。内置参考按现有方法使用，用户输入不指定机制编号、色号、逐镜布局或外部参考片。

相同内容减少了材料难度与时长差异，使开发者能检查是否达到参考所展示的协作完成度。比较文字有没有造型、有没有参与主体变化、空间是否合理重排；不要求相同配色，也不能用“风格不同”解释关键设计根本没有完成。

这里是在测试产品默认能力，不是在重新生成并覆盖已认可视频。原参考文件、哈希与历史认可范围保持不变。

### 5.3 再验证新内容与真实生产范围

固定内容达到目标后，通过正常主题入口检查原件阅读、真实行动和抽象关系等不同材料条件。按授权允许系统取材，不把这些类型注册成新模板。

主题输入不添加花字、材质术语。记录实际使用的模型、Release、任务范围、正常读取入口、参考与设计产物。能力允许时做独立重复运行，并保留所有结果，不只挑最好的一条作为结论。

5—6秒微样本可以验证技术或单个动作，但不能代替连续内容、重点文字变化和相邻场面接续。固定内容任务按给定声音长度完成；新的任务按本次真实内容与时长制作，不要求生产中每段执行固定时长或机制配额。

已实现的声音与普通字幕要通过正式链路合成，并检查与主画面的竞争。静音参考的动效认可不能替代新作品的声画验收。

### 5.4 明确的作品通过与返工条件

| 项目 | 达到目标 | 应返工 |
|---|---|---|
| 花字 | 选中的画内重点有可辨认的造型，动作与含义协调 | 全部重点仍是基础大字，只改字号、字色和透明度 |
| 整场配合 | 主体、文字与空间随表达合理安排，变化有后续用途 | 一侧素材长期固定，另一侧反复换字，主要关系没有发展 |
| 美术 | 字形、材料、面积与颜色有主次，运动中途也清楚 | 花字孤立贴在页面上，或白图、浅底、亮字互相竞争 |
| 参考使用 | 适配了当前材料，实际完成相关造型与对象协作 | 只记录编号、抄一个位移，或复制外观却没有表达 |
| 来源文字 | 后台依据完整，无违规新增出处与页码条 | 作者填了字段就显示，自由 TSX 又把来源画回去 |
| 内容与字幕 | 必要条件保留，字幕独立稳定、实际行数自适应 | 去出处时删掉条件，做花字时把字幕一起移动 |
| 默认能力 | 任务要求来自运行时方法，作者自行完成设计 | 必须由开发者临时补分镜、补造型或写代码救场才成立 |

这些标准不把卡片、稳定构图或某个位置一律判错。判断基于当前内容与实际作品，也不以描边数量、颜色数量和运动面积打分。

单帧只证明对应状态；连续媒体与声音按真实覆盖记录。不能观察的内容保留未知，已观察到的确定问题仍要返修。未经用户明确认可的开发样本，不加入正式认可案例。

### 5.5 程序回归与最小记录

| 用例 | 断言 |
|---|---|
| 偏好字段省略或为空 | 仍进入完整视觉任务，不伪填风格，不关闭花字与材料设计 |
| 默认策略下新增 `sourceCaption` | 写入前明确拒绝，不产生半个对象，不删除后台出处 |
| 有依据的指定例外 | 仅允许真实范围与文本；无效范围、缺少依据或超范围使用拒绝 |
| 其他可见字段 | 无来源元数据自动回填；准确内容标签仍可正常使用 |
| 自由 TSX 中明确的出处层 | 定位真实新增文字并报告；不全局删除关键词；模糊语义保留核对 |
| 原件自然含名称或页码 | 不无差别遮盖，事实来源继续可追溯 |
| 固定输入与历史恢复 | 策略、源码和任务身份一致，不静默改变历史输出，不重放未知提交 |
| 原声音、SRT与字幕 | 不重配、不重复平移；一行、两行和空档正确；字幕不随花字运动 |
| 发行与引用 | 实际 Worker 读取的版本一致，参考媒体与源码可访问 |

优先并入已有测试套件，不另建平行测试系统。源码预检的覆盖范围与误判处理单独写明，不能将关键词未命中报告为所有画面绝无来源说明。

运行记录复用已有任务与版本：实际 Release、输入范围、任务分派、读取入口、当前稿、源码／Props、输出和真实返修。保留可核对的设计决定，不采集模型私下推理，不新增追踪数据库。

### 5.6 实施顺序与最终交付

先完成正常入口、视觉方法、参考选择和实现交接，使作者在当前场面上完成具体花字与整场设计；来源策略和显示路径并行整改。构建和安装按授权进行，读回实际 Release 后再测试正常入口。

开发只交一个目录，包含 `开发与验证.md`、真实测试结果、作品入口、对应源码及必要输入信息。报告分清技术结果、实际视觉评价和仍未完成范围。没有部署授权时使用候选环境，并明确没有验证生产部署。

当前生产作品需要修复时，先读它自己的稿、源码和输出。保留正文、已核实数据、正确动效、声音与字幕；从真实绘制位置删除新增出处和页码，处理必要条件，并重做相关花字与构图。不要用开发包微样本代替生产作品，也不顺带重做无关范围。

**完成标准是正常任务自行交出了符合要求的作品。** 只更新说明、通过技术测试、复制参考目录，或把问题记为“待审”，都不能替代尚未完成的视觉结果。
