## **一、我已经找到一个非常关键的证据：这次实际没有走完你设计的创意—视觉—OD 制作链路**

这意味着一个非常重要的事实：

**你优化的重点是让视觉作者把完整参考迁移成可执行的视觉导演方案，再让 OD 直接制作动态首版。但这次实际产物并没有经过这个 OD 制作环节。**

所以不能把这次失败简单归结为 OD 的美术能力差，也不能说是参考迁移技能完全没起作用。中间的制作路径实际上发生了偏离。

## **二、创意参考实际上没有完成完整迁移**

这直接违反了当前技能已经写明的要求：

`creative-sequence-design` 要求亲自观看完整采用范围；`full-reference-transfer` 要求核对完整视觉表现；`visual-treatment-planning` 要求实际试摆；OD 制作也要求读取正式采用的原片。

也就是说，**技能里写了完整迁移，但本次执行留下的证据表明，创意和视觉研究并没有真正完成完整迁移。**

这里不是少写了几个花字或者少做几个动画的问题，而是参考的原片动态过程、构图和美术表现都没有被完整研究，后续自然无法准确迁移。

## **三、这次还有一个更深层的问题：角色任务指令与技能本身存在冲突**

我检查了实际派给三个作者的指令，发现一个容易被忽略的问题。

实际角色指令反复出现：

> 禁止读取或参考历史项目和任务。

- 必须观看 R40 的 016、026、032。
- 在首次查询前完成原速对照练习。

两组要求存在冲突。

我认为这里非常可能是导致案例教学没有落实的重要原因。

你真正想禁止的应该是：

- 不允许直接复制以前项目的照排稿。
- 不允许拿以前的成片当作本片的现成答案。
- 不允许直接沿用以前项目的素材和时间线。

创意作者仍须通过 R40 学习整片参考研究、完整迁移和素材接力。

**学习历史案例与照搬历史项目是两件完全不同的事情。**

这次的实际记录恰恰证明了这个区别没有被执行好。

### **另一个问题：主导演没有给视觉作者形成足够具体的创作基准**

虽然视觉作者后续补写了视觉导演稿，但主任务没有将它作为正式冻结的制作输入交给 OD。

这就造成了一个断点：

主导演有内容安排，创意作者有观看关系，视觉作者有初稿，但最终制作实际依据的是主任务自己组织的时间线和原生解释场景。

## **五、为什么前两轮技能优化没有产生实际效果？**

我把当前 main 的技能、发行副本、方案和本次制作档案对照后，得到一个重要结论：

**技能文本已经增加了不少正确要求，但系统没有形成从研究证据到最终作品的完整执行闭环。**

具体有四个断点。

| 环节       | 现在的问题                         | 实际后果                       |
| ---------- | ---------------------------------- | ------------------------------ |
| 创意研究   | 没有真正完成原片原速观看           | 参考的构图、运动和美术无法迁移 |
| 创意交视觉 | 观看关系没有形成足够具体的冻结设计 | 视觉作者只能重新猜测和补充     |
| 视觉交 OD  | 没有正式制作委托和冻结作品         | OD 没有依据完整导演稿制作      |
| 成片审核   | 主要依靠抽帧，缺少连续声画检查     | 严重偏差没有在首版阶段被阻止   |

更重要的是，当前 `ProductionUnitHandoff` 的创意正文 `body` 仍然是自由文本。它能验证参考身份和交接条件，却不能仅凭 Schema 证明完整构图、花字、背景、材质、运动和美术都已经迁移。

这意味着：

**我们优化了交接工具的规则，却没有证明实际生产入口一定经过这些规则，也没有证明通过交接的设计一定能在成片中出现。**

这才是两轮优化之后仍然反复失败的核心系统性问题。

## **六、我认为真正需要解决的是五个问题，而不是继续给技能加文字**

我把问题分成五层，按优先级排序。

### **P0：首先修复实际生产路径**

这是最重要的。

普通完整解说新片必须满足：

```
主导演
  ↓
文案、素材作者启动
  ↓
创意作者：完整参考研究与迁移
  ↓
视觉作者：整片视觉编排与冻结
  ↓
正式制作准入
  ↓
OD：依据冻结稿制作动态首版
  ↓
视觉作者：连续观看与返修
  ↓
主导演、创意作者、审核：联合确认
```

不能再允许出现：

```
创意作者写了方案
       ↓
视觉作者写了初稿
       ↓
主任务直接使用原生解释场景
       ↓
导出成片
```

这次就发生了后面这种情况。

需要检查主任务的实际路由和正式制作入口，确保普通完整新片不能静默绕过 OD。

如果 OD 运行环境版本不匹配，应明确报告制作阻断，而不是自动退化到另一条不符合创作目标的制作路径。

### **P1：修复参考研究的真实性**

不是要求创意作者多找几张参考图片，而是要求真正研究完整参考。

我建议将参考研究拆成三个必须完成的阶段：

1. 原片研究：原速观看完整采用范围，研究构图、主体、背景、文字、运动和美术。
2. 本片迁移：用本片真实素材重新建立完整视觉过程，不能只迁移内容含义和动作方向。
3. 实际试演：在本片画幅中试摆关键构图、素材接管和连续运动，验证视觉效果。

没有完成这些工作，不能把研究状态登记为正式完成。

同时修复历史案例学习与禁止照搬旧项目之间的指令冲突。

### **P2：明确视觉作者交付的是完整视觉作品设计，而不是镜头安排**

当前视觉作者的职责虽然已经包含美术、构图、花字、运动和整片组织，但实际交付必须进一步明确。

我认为每场至少要有以下内容：

| 维度   | 必须解决的问题                     |
| ------ | ---------------------------------- |
| 主体   | 观众首先看什么，真实素材承担什么   |
| 构图   | 整幅画面如何组织，主体占据什么位置 |
| 多素材 | 接管、并列、叠放、交叉如何发生     |
| 层次   | 前景、背景、画框、遮挡如何共同存在 |
| 花字   | 文字如何参与构图，而非普通字幕     |
| 美术   | 色彩、材质、明暗、字体如何统一     |
| 运动   | 起势、发展、关键变化、高潮、出口   |
| 节奏   | 哪些地方加速、停留、转换、收势     |

这些不是要求每场机械出现所有效果，而是确保每场有完整的视觉设计。

尤其要注意：不要让视觉作者把创意参考降级成几个简单的动作指令。

### **P3：让 OD 不能静默改变创意**

OD 应该拥有实现自由，而不是重新决定主要视觉创意的自由。

例如：

- 可以深化运动曲线。
- 可以优化遮罩和局部坐标。
- 可以调整缓动和具体帧。
- 可以优化技术实现。

但是：

- 不能把多素材同屏改成普通切镜。
- 不能把连续运动改成简单渐显。
- 不能删除花字和重要视觉层。
- 不能把真实素材替换成独立图解。
- 不能为了方便制作而改变完整参考的关键视觉关系。

改变这些内容必须返回视觉作者确认。

### **P4：修复审核标准**

本次最大的审核问题之一是：有技术导出结果，却没有完成完整作品审核。

以后必须区分：

- 技术导出成功。
- 画面静态检查通过。
- 动态连续过程检查通过。
- 完整声画检查通过。
- 创意参考迁移审核通过。

尤其是连续动态检查，不能用每隔三秒抽一张图替代。

```
- 同版时间计划和真实旁白。
- 当前正式 OD 制作请求及其 ProductionRun。

不得因为 OD 版本不匹配、制作工具暂不可用或某个制作范围存在问题，就自动改用 VideoFlowCut 原生解释场景、内置图表或普通素材切镜代替完整视觉制作。

OD 无法启动时：
1. 保留已经冻结的视觉方案。
2. 返回真实版本、工具和运行错误。
3. 明确受影响的制作范围。
4. 保留其他不依赖该问题的研究和准备工作。
5. 等待恢复原制作链路后继续。

不得将未经过 OD 的原生解释场景导出结果，报告为已经完成正式 OD 首版制作。

```

**为什么这里只补准入，而不重写整个 OD 技能？**

因为本次已经证明 OD 技能有相关要求，但实际根本没有进入 OD。

现在重复增加 OD 制作技巧，解决不了实际路由绕过的问题。

这里我建议坚持一个原则：

当前仓库已经有这些工具：

| --------------------------------- | -------------------------------- |
| `record_creative_decision`      | 记录参考研究、迁移判断和来源依据 |

但是目前有几个明显缺口。

## **4.1 修改&#x20;**`record_creative_decision`**&#x20;的研究准入**

文件：`apps/server/src/mcp.ts`

当前 `record_creative_decision` 已经支持：

- `research_coverage`
- `research_references`
- `observed_relation`
- `research_outcome`
- `input_decision_ids`
- `delivery_ref`

这是正确的设计，不需要新增研究数据库。

问题是：目前 Schema 中不少研究字段是可选的，`research_coverage` 也允许不提交。

这样就存在一个风险：作者登记了 `researched`，但研究正文、完整观察范围和迁移依据并没有充分记录。

**修改思路：**

在 `application.recordCreativeDecision` 的正式写入校验中增加条件，而不是简单地把所有字段都设为必填。

具体规则：

| 条件                           | 程序要求                                  |
| ------------------------------ | ----------------------------------------- |
| 普通完整新片 creative_research | 必须提交研究覆盖情况                      |
| `overall_visual=covered`     | 必须提交整片视觉研究正文                  |
| `scene_composition=covered`  | 必须提交构图研究和本片迁移正文            |
| `motion_mechanisms=covered`  | 必须提交运动关系研究和本片迁移正文        |
| 某层为 `not_applicable`      | 必须填写不适用原因                        |
| 参考被正式采用                 | 必须提供参考 ID、指纹、采用范围和观察关系 |
| 正式状态为 `researched`      | 不能存在未解决的阻断问题                  |

这里要区分两个概念：

- `pending`：允许作者继续推进其他工作。
- `researched`：意味着该正式研究单元已经达到交付标准。

不允许因为工具调用成功，就自动认为研究完成。

### **MCP 工具描述建议替换**

将 `record_creative_decision` 当前 description 替换为：

```

持久化本次制作的创作判断、真实作者分派、输入版本、上游决定和参考研究证据。

creative_research 必须区分整体视觉、场面构图和运动机制三个研究层次。每个 covered 层次填写实际研究与本片迁移正文；not_applicable 必须填写原因。

正式完整参考必须记录真实来源、资料库指纹、原片采用范围和实际观察到的视觉关系。

research_outcome=pending 表示研究尚未完成，可以继续其他工作。
research_outcome=researched 表示该研究单元已完成实际参考观察、完整迁移和必要的本片试演。

工具写入成功不代表视觉研究自动通过。

正式视觉采用必须引用同一版本的视觉设计和冻结交付清单。

```

注意：`record_creative_decision` 目前仍然允许阶段性研究，这是有用的，不应该删除。不能把所有研究都变成必须等整片完成才能提交。

## **4.2 修改&#x20;**`update_production_run`**&#x20;的单元交接校验**

文件：`apps/server/src/mcp.ts`配套文件：`packages/contracts/src/production-unit-handoff.ts`配套文件：`packages/edit-application/src/production-unit-handoff.ts`

当前工具已经有：

```
action=record_unit_handoff
```

内部支持：

```
submit_draft
accept_draft
return_draft
```

当前 `ProductionUnitHandoff` 已经要求普通完整新片使用 `full_reference`，也要求参考研究决定、原片范围和素材绑定。

这部分保留。

我建议补充三个校验。

**第一：创意交件不能只是一个参考编号。**

`submit_draft` 的 `body` 必须包含完整本片演出正文，不能只是查询结果或参考卡摘要。

在现有 `production-unit-handoff.ts` 的 `submit_draft` 校验中增加正文结构检查，要求能够定位：

- 整片视觉研究。
- 原片完整表现。
- 本片真实素材及源范围。
- 本片完整演出。
- 必须保留的视觉特征。
- 素材替换和补偿。
- 场间接续。

不新增 `preserveFeatures` 等重复字段，直接检查和使用现有正文。

**第二：正式视觉接件必须有完整的动态对照。**

当前 Schema 已经有：

```
comparisonPath
observation
sourceMs
projectFrame
```

并且程序已经要求 `full_reference` 提供视频格式的对照文件。

保留这套结构。

进一步要求 `observation` 明确说明：

1. 同状态对照在视频中的位置。
2. 连续过程对照在视频中的位置。
3. 原片对应时间。
4. 本片对应帧段。
5. 实际观察到的视觉差异。
6. 是否存在关键视觉特征被删除或简化。

**第三：不能只凭一份视频文件就认为视觉接件通过。**

程序可以验证视频文件是否存在、格式是否正确、是否能够解码；但它不能仅凭文件存在就证明作者真正观看并理解了连续运动。

所以实际观察结论必须由视觉作者提交，并由审核作者抽查。

这部分不能伪装成程序已经能够自动识别美术和创意质量。

## **4.3 修改&#x20;**`manage_visual_treatment`**&#x20;的正式采用规则**

文件：`apps/server/src/mcp.ts`配套文件：`packages/edit-application/src/visual-design-revisions.ts`

当前 `manage_visual_treatment` 已经支持：

- `action=upsert`
- `action=remove`
- `action=adopt`

也支持将多个视觉计划和素材在同一 Revision 中采用。

这个能力应该保留。

需要补的是正式采用的关联校验。

正式采用必须满足：

1. `adopted_decision_ref` 指向本次真实视觉作者的 `visual_design` 决定。
2. 该视觉决定引用已经完成的创意和机制研究决定。
3. `delivery_ref` 对应的冻结清单和 SHA256 与本次视觉稿一致。
4. 交付清单中的 Scene、参考映射和实际采用范围一致。
5. 每个主要视觉单元存在完整主参考覆盖。
6. 局部机制只能作为辅助映射，不得冒充完整参考。
7. 视觉稿和采用清单必须属于同一个当前版本。

**重点：候选登记与正式采用不能混为一谈。**

视觉作者可以先交候选稿，继续修订，不影响当前已采用版本。

只有主导演确认同版设计后，才通过现有 `action=adopt` 正式采用。

## **4.4 完整制作状态必须能发现 OD 没有执行**

文件：`packages/edit-application/src/production-status.ts`配套：`packages/edit-application/src/production-coordination.ts`

这是我认为本次程序改动中最重要的一项。

当前 `read_production_status` 已经能够返回制作状态、单元交接和审阅覆盖。

但是需要确保它能明确区分：

- 创意研究完成。
- 视觉设计完成。
- 导演正式采用。
- OD 正式接单。
- OD 实际交回作品。
- 作品进入项目。
- 完整成片审核。

建议复用现有状态，不新增另一套状态机。

对普通完整新片，状态判断应该遵循：

| 条件                               | 状态           |
| ---------------------------------- | -------------- |
| 缺完整参考研究                     | `incomplete` |
| 创意原稿没有完成视觉接件           | `incomplete` |
| 视觉稿没有正式采用                 | `incomplete` |
| 没有正式 OD 制作委托               | `incomplete` |
| OD 有 Run，但没有冻结作品          | `incomplete` |
| OD 有冻结作品，但没有进入项目      | `incomplete` |
| OD 作品没有覆盖要求的制作范围      | `incomplete` |
| 作品已进入项目，但缺少连续声画检查 | `incomplete` |
| 全部范围完成且必要问题已经复查     | 才能完成       |

这项改动不能简单地在 `read_production_status` 里增加一条文字提示。

必须让 `completeProductionRun` 实际使用这些检查结果。

# **5. 第三批：程序怎么改？**

这里需要特别注意：**目前代码已经有完整参考交接准入，但没有证据表明所有普通完整新片的实际制作入口都强制经过它。**

因此不能再只增强 `production-unit-handoff.ts`，必须补正式生产入口。

## **5.1 修改&#x20;**`production-coordination.ts`

文件：`packages/edit-application/src/production-coordination.ts`

当前已有：

```
export function requiresFullVisualCoordination(
  report: SkillExecutionReport,
  snapshot: ProjectSnapshot
): boolean {
  return report.intent === "visual_rework" ||
    report.intent === "full_creation" &&
    snapshot.project.profile !== "vlog";

```

这段逻辑保留。

它已经能识别完整新片是否需要完整视觉协作。

问题是：**需要完整视觉协作，不等于实际生产必须通过 OD。**

我建议增加一个普通完整新片的制作准入函数。

伪代码如下：

```

function validateFullCreationProductionGate(
  report: SkillExecutionReport,
  snapshot: ProjectSnapshot,
  targetRevision: number
) {
  if (!requiresFullVisualCoordination(report, snapshot)) {
    return [];
  }

  const issues = [];

  // 1. 每个主要视觉单元必须有完整参考交件
  // 2. 创意作者必须完成交件
  // 3. 视觉作者必须完成接件
  // 4. 视觉设计必须正式采用
  // 5. 同版冻结导演稿必须存在
  // 6. OD 必须存在本次 ProductionRun 对应的正式作品
  // 7. OD 作品必须覆盖要求的连续帧范围
  // 8. OD 作品必须实际进入目标项目版本
  // 9. 不能只使用原生解释场景或静态图表代替 OD 完整制作

  return issues;
}

```

上面是规则示意，不是建议直接照抄的实现代码。

实际实现应该复用：

- `readUnitHandoff`
- `unitHandoffDeliveryIssues`
- `visualDesignCovers`
- `sameVisualDelivery`
- `motionWorkVersion`
- `MotionWork.readyRanges`
- `ProductionRun`
- 当前 VisualPlan 和采用记录

不再新增独立的制作状态对象。

### **为什么要增加这道准入？**

因为目前：

```

```

只说明这个任务需要完整视觉协作。

如果实际主任务没有调用对应的正式交接和 OD 制作流程，原生解释场景仍然可能被创建并导出。

所以必须让正式生产检查真实的制作结果，而不是只检查任务类型。

## **5.2 修改&#x20;**`motion-adoption.ts`

文件：`packages/edit-application/src/motion-adoption.ts`

这里复用已有 `MotionWork`。

当前 `MotionWork` 已经具有：

- `author.frozen_version`

1. OD 作品的 `author.project` 必须等于当前项目。
2. `author.run_id` 必须对应当前正式制作任务。
3. `author.frozen_version` 必须等于实际冻结版本。
4. 作品的 `readyRanges` 必须覆盖对应的本片目标帧范围。
5. 作品定义哈希和实际采用版本必须一致。
6. 作品不能只存在于 OD 侧，还必须通过现有作品登记和采用流程进入 VideoFlowCut 项目。

不能只检查有没有 `MotionWork`。

例如，一个 OD 作品可能只做了 5 秒，但正式任务需要制作 80 秒。存在作品并不等于覆盖完成。

必须检查实际范围。

## **5.3 修改&#x20;**`complete_production_run`**&#x20;的底层完成检查**

文件：`packages/edit-application/src/production-status.ts`

当前 `apps/server/src/mcp.ts` 中的 `complete_production_run` 已经调用：

```
application.completeProductionRun(...)
```

这里应该增加完整新片制作准入检查。

伪代码：

```

async function completeProductionRun(input) {
  const state = readCurrentProductionState(input.runId);

  // 原有的结构、采用、观察和问题复查检查继续执行
  const existingIssues = evaluateExistingCompletionRules(state);

  // 新增：普通完整新片必须完成 OD 正式制作
  const odIssues = validateFullCreationProductionGate(
    state.report,
    state.snapshot,
    input.finalRevision
  );

  const issues = [
    ...existingIssues,
    ...odIssues
  ];

  if (issues.length > 0) {
    return {
      status: "incomplete",
      issues,
      nextActions: buildOwnerActions(issues)
    };
  }

  return completeWithExistingRules(input);
}

```

这样即使有人绕过了技能路由，直接创建原生解释场景，也不能把这个任务标记为完整新片正式完成。

## **5.4 修改&#x20;**`submit_export`**&#x20;的最终交付准入**

文件：`apps/server/src/mcp.ts`底层检查：`packages/edit-application/src/` 中实际处理导出的 Application 实现

这里不能把所有导出都禁止，否则会影响正常的草稿、局部测试和中间预览。

我建议只对正式交付用途进行完整制作准入。

| -------------------- | -------------------------- |

| 局部测试             | 允许                       |
| OD 中间阶段预览      | 允许                       |

正式交付前检查：

## **5.5 OD 运行时版本不匹配怎么处理？**

这里有个架构边界需要明确。

我检查了 `apps/server/src/mcp.ts`：

- 它有 `read_runtime_release`。
- 它能检查 MCP 和 Runtime 的 Release ID 是否一致。
- 但 `start_motion_authoring`、`wait_motion_authoring` 和 `prepare_motion_handoff` 并不是这个 VFC MCP Server 中注册的工具。

这些是生产协调流程所使用的 OpenDesign 制作能力，不能误把它们当成 VFC MCP 里的现有接口。

所以需要分别处理：

**VideoFlowCut 侧：**

- `read_runtime_release` 继续负责读取本地 Runtime 状态。
- 普通完整新片的完成和正式导出必须检查实际 OD 作品。
- 不存在作品时不能通过准入。

**OpenDesign 制作连接侧：**

- 正式调用 `start_motion_authoring` 前检查 OD 工具版本和运行能力。
- 版本不匹配时不提交正式制作。
- 已提交任务则按原 Run 和幂等键恢复。
- 禁止自动调用 VFC 原生解释场景作为替代。

**任务协调侧：**

将 `production-coordinator/references/task-routing.md` 中原有的 OD 正式派发要求保留，并明确失败处理。

增加：

```

### OD 正式制作失败处理

普通完整新片必须使用正式 OpenDesign 制作链路。

调用正式制作前，检查 OD 当前发布版本、工具可用性和本次项目输入。

若版本不匹配或工具不可用：

1. 不得绕过 OD 直接使用原生解释场景生成正式首版。
2. 不得将原生图表、普通素材切镜作为替代成片。
3. 保存已经完成的创意稿、视觉稿和冻结交付。
4. 记录真实运行错误和影响范围。
5. 其他不依赖 OD 的素材、研究和准备工作继续推进。
6. 恢复后沿原 ProductionRun、冻结稿和制作委托继续。

草稿、单项技术测试与正式完整新片首版分开处理，不得混淆制作状态。
```

这才是真正解决本次 OD 绕过问题的办法。

## **5.6 修改&#x20;**`visual-explainer-director/references/explanation-design.md`

文件：`.agents/skills/visual-explainer-director/references/explanation-design.md`

我专门检查了这个文件，发现一个值得处理的细节：

它已经明确禁止原创图解、流程图、数据演示和抽象动画替代真实素材，但是仍然保留了 `DataConclusion` 作为解释场景类型。

我不建议删除 `DataConclusion`，因为有些参考本身就可能使用图形与实拍共同构图。

但需要把它的使用边界写得更清楚。

找到：

```
### DataConclusion

用于趋势、比例和结论。按确定文案保留画面表达所需的读数、单位和限定，动画不得改变数据含义。
```

替换为：

```

### DataConclusion

用于参考原片中已经存在的、与真实素材共同构成视觉表现的数据关系。

DataConclusion 只承担辅助视觉表达，不得独立成为普通完整解说新片的主要内容解释画面。

使用前必须确认：
- 已经存在完整创意参考。
- 参考中的数据表现方式确实服务于真实素材的组织。
- 本片有真实素材承担主要观看内容。
- 数据、文字和图形能够与实拍共同构图和运动。
- 数据变化不会替代真实素材的观看过程。

允许：
- 在真实机械臂旁显示辅助概率曲线。
- 在实拍主体旁叠加与真实事件对应的计数。
- 使用参考中的线条、色面、数字和局部图形强化实拍关系。
- 让数据、花字和真实素材共同运动。

禁止：
- 真实素材退出后，用全屏原创柱状图、折线图或数据卡独立解释主要内容。
- 因为旁白出现概率、数据或抽象概念，就自动生成图表。
- 先制作原创图表，再将真实素材作为装饰或短暂背景。
- 用 DataConclusion 代替完整参考研究和真实素材组织。

素材表现不足时，继续检索、补材、重新取景和迁移完整参考，不得将 DataConclusion 作为创意回退路线。
```

这样不会限制参考中本来就有的图形语言，但可以防止图表脱离实拍成为另一部独立的解释视频。

# **6. 第四批：修复质量审核**

## **6.1 修改&#x20;**`quality-verification/SKILL.md`

在现有完整新制和主要视觉重做的审核章节中，增加以下内容。

```

## 完整新制的连续声画与视觉迁移审核

完整新片必须区分技术成功、静态画面通过、连续动态通过、完整声画通过和创意参考迁移通过。

这些结果不能相互替代。

### 一、完整参考逐项核验

对每个正式采用的完整参考：

1. 打开原片实际采用范围。
2. 打开本片对应的完整连续范围。
3. 按相同观看顺序比较。
4. 检查主体、构图、空间、背景、花字、美术和运动。
5. 检查关键中途、共存、接管、结果和出口。
6. 记录原片与本片实际差异。

不得只看首尾帧或参考关键帧。

### 二、连续动态检查

逐场连续观看：

- 入口是否成立。
- 主体是否持续可辨。
- 素材之间是否形成设计关系。
- 旧层是否在正确时间保持。
- 新层是否正确接管。
- 关键中途是否完整。
- 花字是否参与构图和运动。
- 动效是否围绕真实素材展开。
- 场面是否有明确结果和出口。

特别检查以下退化：

- 多素材并列被简化为普通切镜。
- 连续运动被简化为一次渐显。
- 完整构图被简化为视频加普通标题。
- 参考中的花字和背景被删除。
- 真实素材被独立图表或图解替代。
- 运动只有开始和结束，没有关键中途。
- 画面缺少结果停留和视觉收束。

### 三、完整声画检查

按真实旁白和实际成片连续播放。

检查：
- 旁白是否与画面发展协调。
- 画面是否为了等待旁白而无目的停留。
- 无旁白区间是否有明确视觉或声音目的。
- 素材源时钟是否正确。
- 环境声、动作声和音乐是否按设计落实。
- 花字和重要视觉变化是否落在正确时刻。
- 场间接点是否与声音自然衔接。

没有实际听审的范围，保留未知，不得写通过。

### 四、问题归属

- 原片理解或迁移缺失：原创意作者。
- 构图、美术、素材组织或节奏设计不足：视觉作者。
- 已确定设计没有实现：原 OD 制作作者。
- 内容、事实、主线和跨场取舍：主导演。
- 素材缺失或源段不成立：素材作者。

### 五、返修复核

所有问题必须关联：
- 当前作品版本。
- 实际观察范围。
- 原参考和研究决定。
- 本片实际表现。
- 缺失的视觉关系。
- 原责任作者。
- 新版实际复核结果。

一次真实观察只登记一次。

静态截图只能支持静态观察；抽帧不能替代连续动态检查；技术导出成功不能代替完整声画审核。
```

## **6.2 明确最终验收标准**

我建议把最终验收统一成下面五个维度。

| 验收维度 | 通过条件                                 |
| -------- | ---------------------------------------- |
| 素材主体 | 真实素材持续承担主要观看内容             |
| 创意迁移 | 参考完整视觉表现实际改变了本片素材组织   |
| 视觉表现 | 构图、美术、花字、背景和运动形成完整作品 |
| 制作兑现 | OD 实际完成冻结稿规定的动态关系          |
| 声画审核 | 完整连续观看和听审，关键问题已复查       |

另外明确三个不能作为通过依据的指标：

- 检索到多少张参考卡。
- 生成了多少段动效源码。
- 产生了多少张抽帧截图。

这些都不是作品质量。
