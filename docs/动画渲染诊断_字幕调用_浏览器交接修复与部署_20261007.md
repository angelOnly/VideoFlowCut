## 动画失败的实际根因

原实现把三份字体原件的base64嵌入HTML。固定输入生成的HTML为83,178,963字节；Puppeteer `request.respond`通过CDP再次把响应体base64化，仅响应体已约110,905,284字节，超过Chrome DevTools pipe的104,857,600字节（100MiB）接收缓冲。独立复现的浏览器stderr明确记录：

```text
Too large read data is pending: capacity=104857600, max_buffer_size=104857600, read=104857600
Connection closed, not enough capacity
```

页面导航后约1秒，发生页面关闭、主框架脱离和浏览器协议断连，再返回 `Navigating frame was detached`。自然失败基线报告位于 `.repair-validation/attention-runtime/.videoflowcut-runtime/diagnostics/jobs/job_90453d31-a24a-4c28-b1e7-4c1fd07e73c0/b512f813-72ca-437f-a675-0b9a08b0a1d0/report.json`，同目录保留浏览器stderr。另一轮无界关闭实验人工终止，不能用其退出码证明浏览器自然崩溃。

修复为在字体首次使用时，通过 `https://motion.invalid/fonts/<已绑定hash>.<真实格式>` 提供经过原件校验的固定字节。仅接受本件已声明的hash和格式，拒绝未知hash、额外路径和外部URL；CSP继续采用opaque origin沙箱，所有未允许请求仍拒绝。没有换字体、子集删字、关闭沙箱、提高128MiB JS堆限额或扩大CDP容量。相同作品HTML降为1,510,383字节。

原失败清理还直接无限等待 `browser.close()`，导致已经失败的任务继续挂住。现在关闭限时3秒，到期记录原因并终止本任务自己的浏览器；记录第一次主动终止原因，后续正常清理不会覆盖它。

## 诊断的实现

调用链：`submit_motion_work → Job Worker → runMotionJob → MotionDiagnostics → 字体/图片/视频源准备 → renderManagedMotion → 导航/初始化/逐帧/确定性复核/编码 → 输出验证 → 完整Asset登记`。

- `motion-diagnostics.ts`记录阶段、当前帧、最后成功帧、实际进展时间、浏览器版本/PID/断连/退出、首次异常和附加错误。进度最多每5秒写入既有Job检查点，阶段切换立即写入；续租心跳不等于渲染进展。
- 最近100条事件在内容采集时也有限额；stderr按UTF-8字节保留最多64KiB，避免中文输出使自己保存的报告不可读。失败报告总量限制在读接口的1MiB上限内。
- `error-detail.ts`保存name/message/stack/code/cause，限制异常链深度、字符串长度并处理循环引用。发行生成不含源码正文的source map，启用源码位置映射；Worker控制台同时打印结构化完整异常。
- 首次渲染异常不再被源复核或清理失败覆盖。源复核、浏览器关闭、诊断保存失败分别保留附加证据；页面安全拒绝的错误保留原始异常作为cause。
- 报告位于工作区 `.videoflowcut-runtime/diagnostics/jobs/<Job>/<本次尝试>/`，不写入ProjectSnapshot、Revision或素材。Job保存摘要和工作区相对路径。
- 新增只读 `read_job_diagnostics(project_id, job_id)`，核验Job项目归属、realpath边界、报告身份和大小；不接受任意文件路径。
