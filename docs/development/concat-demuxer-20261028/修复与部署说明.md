## 根因与实现

原 `compositeTimeline` 在最终阶段为每段添加一个 `-i`，并把逐段 `setpts` 与多输入 `concat` 滤镜内联到命令。约 300 个分段加上 Windows 项目长路径，导致启动进程时 `spawn ENAMETOOLONG`。失败发生在最终拼接启动，不是已成功登记的主视觉损坏。

按已批准方案删除最终多输入和内联长滤镜，不设分段阈值或第二套回退合成：

1. 所有临时视觉段统一为 **FFV1 level 3 / BGRA / NUT**，使用项目尺寸、帧率、1:1 SAR 和显式编码帧时基。媒体段直接输出此格式；浏览器段保留原 MP4 缓存，取回后只解码视频并无损转为同一中间格式，中间音轨丢弃。
2. 生成 `visual.ffconcat`，只使用模块生成的相对文件名 `visual-N.nut`，并按真实帧数记录段时长。列表内容随段数增长，进程命令始终只有清单和统一音频两个输入。
3. FFmpeg concat demuxer 顺序读取同构流；最终单输入滤镜按 `N/(fps*TB)` 重建连续帧时钟，按目标帧数编码。声音仍由原 `renderTimelineAudio` 按全局帧处理，最终只混入一次。

FFmpeg 官方文档明确要求 concat 各文件具有相同流、codec、time base 等；因此没有直接拼接异构 FFV1/MKV 与 H.264/MP4。NUT 避免使用 MKV 毫秒时间戳作为中间接点时钟。依据：[concat demuxer 文档](https://ffmpeg.org/ffmpeg-formats.html#concat)，本机 FFmpeg 8.1 的 NUT muxer 能力已核对。

主要调用链：`RevisionRenderer.renderRange` → `buildRenderPlan` → 常规媒体渲染 / 必要范围浏览器与缓存 → 统一无损 NUT 分段 → `renderTimelineAudio` → concat 清单 → 最终 H.264/AAC → 原帧率、帧数和导出校验。

## 失败处理与代价

分段、归一化或最终编码失败沿原异常链返回，清理本次输出、报告和临时目录；已取消任务不继续拼接。新增失败/取消回归通过。Job 仍由原 Worker 记录真实诊断，未把旧失败状态改成成功。

浏览器段新增一次无损转码与无损暂存，会增加这类范围的 CPU/I/O 和磁盘占用；媒体段本来就用 FFV1，主要变更为 NUT 容器。保留原 MP4 缓存，避免升级使既有视觉缓存失效。1080p 验收采用易压缩的技术夹具，约 19.1 MB 的临时占用不能外推正式作品；没有承诺正式 9,528 帧作品的合成速度，也没有执行其连续视听或用户定稿。
