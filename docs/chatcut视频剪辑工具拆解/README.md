# ChatCut 视频剪辑工具拆解

## 这套文档究竟在拆什么

这不是一份“工具名清单”，也不是一次测试的流水账。它要还原的是 ChatCut 对外可观察的剪辑系统：一条原始素材怎样变成一条可继续修改的成片；谁决定内容，谁保存帧；主线改变时，哪些对象会重新计算，哪些对象仍需重新判断。

整套文档围绕四个问题展开：

1. ChatCut 如何保存原素材、可查询证据、时间线、字幕、声音和可见结果；
2. 口播、访谈、Vlog、影视高光等不同视频，为什么主时间轴的规划单位不同；
3. Script、Track、Item、Caption、音效、音乐和 MG 分别如何和同一条时间尺建立关系；
4. Web、Codex、Skill、MCP、ChatCut 后端和用户，分别拥有哪一部分判断权与状态权。

本目录只讨论 **ChatCut 外部产品**。不会把其他视频系统的架构、代码、产品计划或推荐实现混入结论。对 ChatCut 私有实现没有公开证据时，文档会明确停在“合理推断”或“未验证”。

归档的官方 Codex Plugin 中文译文是版本 `0.2.25` 的历史阅读资料。它可说明官方工作流和工具前置条件；当前会话的 MCP Schema、实际返回字段和浏览器读回，才是当时运行时能力的最终依据。

## 什么叫“深度拆解”

每个核心能力都沿同一条因果链写，而不是只说“某工具能做什么”：

~~~text
它要解决什么剪辑问题
→ 直接靠模型拖帧或靠单一主轨为什么会失效
→ ChatCut 对外暴露了哪些状态对象与引用关系
→ 哪一个对象是当前事实的权威
→ Agent、后端、用户各自决定什么
→ 一次写入怎样从编辑意图变成可播放状态
→ 上游改动后哪些对象会重算、哪些会失去原来的理由
→ 过期、冲突、素材不足时怎样停下、读回和恢复
→ 哪个实验或官方合同支撑这句话，仍不能外推什么
~~~

例如，“`ripple` 只推动同轨后续 Item”不是一条孤立的功能观察。第 04 篇会把它放回完整关系中解释：V1、V2、A1、字幕和效果共享一把时间尺，却不是父子树；因此同轨重排、字幕投影、片段绑定效果和绝对时间效果会有不同的反应。第 05 篇同样不只说“Script 能删一句话”，而是解释“读取版本化播放稿 → 做语义选择 → 预览/提交编译 → 原子写入 → 读回派生层 → 审片”的状态边界。

## 统一证据标记

ChatCut 是外部产品，本调研没有读取其私有源码。因此每个关键结论都使用以下标记：

| 标记 | 在本目录中的意思 |
| --- | --- |
| **[已实测]** | 本轮实际调用了当前 MCP；写入后读回项目状态，涉及画面或声音时还检查了合成帧、浏览器或导出样本。 |
| **[工具 / Skill 合同明确]** | 当前运行时 Schema 或官方 Skill 说明了输入、前置条件、流程或限制，但本轮未把它完整执行到底。Skill 不等于同名 MCP 已经暴露。 |
| **[合理推断]** | 为解释多个外部现象所必需的最小职责边界；不是私有源码、数据库、模型或队列的事实。 |
| **[未验证]** | 当前素材、权限、入口或实验范围不足，不能下结论；不表示 ChatCut 一定没有此能力。 |

“链路闭环”是另一件事：它要求有明确输入、一次受控操作、后端读回、可见/可听验证，并写清不能外推到哪里。工具返回 `success`、一张截图或一段 Skill 描述，都不足以单独构成闭环。

## 本次调研的范围与保护边界

- 调研使用独立 ChatCut 项目，不公开编辑器启动令牌、完整资源链接或个人数据；
- 核心样本包括陈清泉访谈、数字人口播、无声 Vlog 素材与多轨受控 Timeline；
- 2026-08-27 审计时当前运行时可见 **58** 个 MCP 工具；工具数量和字段会随插件版本、宿主和授权状态变化；
- 文中不把大体积视频、音效或背景音乐存入 Git；资源许可和下载限制单列在第 09 篇；
- 官方译文是工作方法与合同资料，不是 ChatCut 私有源码，也不证明每个能力已在当前会话中可调用。
