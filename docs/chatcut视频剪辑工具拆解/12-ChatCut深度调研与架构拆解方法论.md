# 12｜ChatCut 深度调研与架构拆解方法论

> 本篇是这套 ChatCut 文档的写作和取证标准。它解释怎样把浏览器观察、MCP 返回、官方 Skill 和受控实验，写成“产品为什么这样工作”的拆解，而不是把若干测试步骤换一种排版再写一遍。

> 它不宣称 ChatCut 私有源码、数据库、模型、队列或调度器的实现细节。文中出现的状态图、对象图和“编译”一词，均是为了精确说明外部可观察的职责边界。

## 先记住一句话：测试证据不是最终交付物

一次工具调用、一张浏览器截图、一次导出，最多证明某个样本在某个版本里发生了一个局部现象。

真正的深度拆解要让读者即使不看实验日志，也能回答：

~~~text
ChatCut 想解决什么剪辑难题？
为什么不能让 Agent 直接维护所有帧？
它至少要区分哪些对象、坐标、版本和责任？
一次“删句 / 插镜头 / 加字幕 / 放音效”怎样成为项目里的真实状态？
哪一层自动更新，哪一层必须重新判断？
旧状态、无效引用、素材未就绪、写入失败时怎样不把项目弄乱？
~~~

实验是上面这张因果地图的**证据**，不是正文的主角。若拿掉实验编号，正文仍能解释状态、关系和失败边界，才算架构拆解；若拿掉实验编号就只剩“工具 A 能做什么”，那仍是测试报告。

## 一、先区分三种写作对象

| 写作对象 | 要回答的问题 | 应产出什么 | 绝不能替代什么 |
| --- | --- | --- | --- |
| **取证** | 当前外部接口和页面实际发生了什么？ | MCP 关键字段、前后读回、合成帧、导出或错误。 | 不能直接推出内部源码或全产品承诺。 |
| **架构解释** | 什么状态和约束至少要存在，才能稳定产生所见行为？ | 对象关系、坐标模型、状态转换、不变量、失败恢复。 | 不能把解释模型伪装成 ChatCut 私有数据表。 |
| **下一轮问题** | 哪一个机制还缺哪一环证据？ | 可证伪假设、最小实验、终止条件、能升级或不能升级的结论。 | 不能因“看起来合理”直接填成产品事实。 |

以 Script 为例，三层应该分别写成：

~~~text
[已实测] 删除一条完整语义后，V1 的 Item、源范围、成片帧和相关 Caption 发生了读回可见变化。

[合理推断] 系统至少需要把“语义选择”与“帧级时间线写入”分开，才不必让 Agent 在每次修改后重新手算所有帧。

[未验证] ChatCut 内部使用什么版本号、哈希、锁或数据库事务来拒绝陈旧 Script。
~~~

三句话各自完整；不要把第三句的未知用想象补成第一句的事实。

## 二、深度拆解的起点：先找根矛盾，不先列功能

浅层调研通常从功能菜单开始：有多少 MCP、能否加字幕、能否加音乐、能否删片段。这能得到工具清单，却难以理解它们为何要存在、怎样协同、在哪里会失效。

对 AI 视频剪辑，最核心的矛盾是：

~~~text
Agent 擅长依据语义、画面和编辑目的做“保留什么、怎样讲”的判断；
但它不应长期维护每一个帧号、片段边界、字幕词、音效起点和效果范围。

否则一次删句、插入或重排都会让旧坐标和旧依赖失效，
并迫使 Agent 在不可靠的记忆里继续做帧级算术。
~~~

这个根矛盾自然推导出深拆时必须回答的七个问题：

1. **选择权属于谁？** 谁判断一段话、镜头或声音是否值得保留？
2. **一致性由谁保证？** 谁把选择变成合法的源范围、帧范围、轨道和可渲染对象？
3. **事实保存在哪里？** 原素材、转写、Script、Timeline、字幕、效果各自谁是权威？
4. **坐标如何转换？** 原片时间、成片帧、词级时间、声音事件和视觉锚点如何区分？
5. **改动如何传播？** 哪些对象有明确依赖可更新，哪些只是共享同一把时间尺？
6. **失败如何恢复？** 陈旧状态、非法重叠、转写未完、资源不合规时怎样停住？
7. **用户怎样看懂？** 哪些是可验证的结构事实，哪些仍需要看画面、听声音或做创意判断？

答案不是“更多工具”，而是一个可解释的项目状态模型。

## 三、固定的八层拆解框架

每个核心能力——Script、字幕、音效、TTS、MG、多机位或跨入口协作——都用同一套八层拆。视频类型改变的是“主线单位”和“首要证据”，不是这八层。

~~~mermaid
flowchart TD
    A[1. 根问题与观众结果] --> B[2. 核心抽象]
    B --> C[3. 状态、身份、坐标与版本]
    C --> D[4. 意图如何落成写入]
    D --> E[5. 下游关系与失效传播]
    E --> F[6. 不变量、失败与恢复]
    F --> G[7. 控制面与权力边界]
    G --> H[8. 证据等级与待验证边界]
~~~

### 1. 根问题与观众结果

从用户真正想得到的画面/声音开始，而不是从工具动作开始。

| 用户的话 | 不应立即翻译成 | 深拆时应问什么 |
| --- | --- | --- |
| “删掉这句” | 删除第 N–M 帧 | 是删完整意思、一次失败重拍，还是只压缩停顿？删后还要保留哪一层语气和上下文？ |
| “这里加一个 Ding” | 在第 N 帧放一个音频文件 | 这个声音服务确认、转场、喜剧还是节奏？观众应在什么时刻真正听到它？ |
| “把口播剪短” | 连续 `split_item` / `edit_item` | 观众最终应依次听到哪些完整表达？哪一版重拍更自然？ |
| “做一个 Vlog” | 按上传顺序排 V1 | 主线是场景、经历、动作、旁白、音乐还是情绪变化？ |

### 2. 核心抽象

工具不是架构核心；系统为了保持可编辑和可验证，才需要长期区分下面的对象。

| 抽象 | 大白话 | 它不是什么 |
| --- | --- | --- |
| **Asset** | 一份可复用的原始或生成素材。 | 它不等于已经出现在成片里。 |
| **源转写 / 源证据** | 原片某段说了什么、画面在什么时刻可被检查。 | 它不等于观众最终会看到的字幕。 |
| **Script** | “观众还要听到哪些原有表达、按什么顺序听”的选择表面。 | 它不是普通文稿，也不是具体帧号。 |
| **Timeline / Track / Item** | 这一版成片在什么轨道、什么帧播放 Asset 的哪一段。 | 它不等于素材库，也不是编辑理由本身。 |
| **Caption Card / Token** | 屏幕文字、布局、样式和最终帧上的词级时间。 | 它不等于 ASR 原词的唯一权威。 |
| **编辑事件** | 一个转场、观点落点、动作、情绪或节拍的创作理由。 | 它不一定等于音效 Item 的物理起点。 |

### 3. 状态、身份、坐标与版本

深度通常不在“对象很多”，而在对象不会被混淆。每一段结论都要至少检查四件事：

~~~text
身份：这是哪个 Project、Asset、Timeline、Track、Item 或 Card？
坐标：它在原片第几秒，还是在最终 Timeline 第几帧？
版本：读取时看到的 Script / Timeline，提交时还是不是同一版？
关系：它依赖语义、目标 Item、绝对时间，还是仅与某一轨同序？
~~~

同一句话可能同时有多种地址：

~~~text
源素材：Asset A 的 12.3s–16.1s
语义选择：当前 Script 中保留的一个完整表达
成片播放：Timeline 的 420–534 帧
字幕显示：Card 的 420–534 帧，Card 内每个 Token 另有起止帧
编辑强调：第 480 帧是“结论落点”，可供 Ding / MG / Zoom 参考
~~~

把它们统称为“第 N 帧的东西”，就是后续改动会乱的开始。

### 4. 意图如何落成写入：用“编译”解释，而不猜内部源码

当用户说“删一句、把结论前置、换一段画面”，需要的是从高层意图到确定性项目状态的边界：

~~~text
源素材 / 转写 / 局部画面证据
→ 可回源的 Script 或节目段落计划
→ Agent 做删、留、重排和创作选择
→ ChatCut 校验版本、源范围、轨道约束
→ 写入新的 Item、帧范围、字幕或异步任务
→ 读回并检查下游影响
~~~

这里把执行层叫作“编译”只是职责比喻：它描述的是谁把语义选择降成 Item、源偏移和整数帧，不是声称 ChatCut 内部存在同名模块。

任何写工具都应从五个合同面分析：

| 合同面 | 要问的问题 |
| --- | --- |
| 输入 | 指向哪个 Project、Timeline、版本、源段、Track 或范围？ |
| 前置条件 | Asset 可用吗？转写就绪吗？引用和快照新鲜吗？ |
| 程序责任 | 哪些帧换算、顺序、重叠、源尾与原子性必须由确定性程序保证？ |
| 输出 | 生成或更新哪些 Item、Caption、资源、Job 或失败原因？ |
| 验证 | 用哪个读回对象、哪个合成帧或哪个导出样本确认结果？ |

### 5. 下游关系与失效传播

“主轨”是编辑骨架，不是一个会强制支配所有轨的万能父对象。要按对象实际保存的关系逐个解释。

| 下游对象 | 它可能记住什么 | 主线变化后应分辨什么 |
| --- | --- | --- |
| 字幕 | 最终语音、Token、Card、成片帧。 | 是否能重新投影；切口是否仍是自然语言边界。 |
| 同轨后续 Item | 同一 Track 上的顺序。 | 是否显式 ripple，是否存在 gap。 |
| 片段绑定效果 | 目标 Item 与局部范围。 | 被保留的 Item 移动/重建后，该关系是否被保存。 |
| 绝对时间效果 / 覆盖层 | 成片绝对帧范围。 | 它可能物理合法却已经服务错了内容。 |
| 音效 | 编辑事件、资源 onset 与物理 Item 范围。 | 起音和能量是否仍落在正确事件。 |
| 背景音乐 | 时长、段落、人声 Anchor/Follower。 | 主线长度、片尾、循环、Duck 和听感是否仍适合。 |
| 旁白 | 画面锚点、文案、真实时长与摆放范围。 | 画面重计时后哪些同步行已经 stale。 |

这里一定要区分两种正确：

~~~text
物理正确：对象仍有合法帧范围、没有越界、重叠或丢失。
编辑正确：对象仍在正确的语义、情绪、动作或节拍上出现。
~~~

程序更容易保证前者；后者仍需要 Agent 和用户的创作判断与审片。

### 6. 不变量、失败与恢复

深度文档必须说明系统**不能允许什么**，不能只描述正常路径。

可从当前合同和实测归纳的检查项包括：

- 陈旧 Script 不应静默覆盖已变化的 Timeline；
- 保留的源引用必须仍存在并可被解析；
- 同一轨的范围、顺序、素材边界要合法；
- 结构性批次不应留下“前半段写了、后半段失败”的半状态；
- 字幕、音效、MG 等下游对象不能被假装已经在语义上修好；
- `no_audio`、处理未完成或许可不明的 Asset 不能被伪装成“已经理解和可交付”。

每一条失败说明都要补四个回答：

~~~text
错误来自哪里？
是否可以安全重试？
重试前必须重新读取什么？
用户或审片者还需看到什么？
~~~

例如陈旧 Script 的正确恢复不是“重复提交同一份旧文稿”，而是重新 `read_script`、基于当前主线重新判断、预览再提交。

### 7. 控制面与权力边界

分析 Web、Codex、MCP、Skill 和用户时，要写清谁保存**项目事实**，谁只是给出**指令或方法**。

| 角色 | 应承担的职责 | 不应被误写成 |
| --- | --- | --- |
| 用户 | 目标、取舍、许可、品牌/审美判断和最终确认。 | 被动等待器。 |
| Web 编辑器 | 素材上传、可视化、手工修改、显示同一项目。 | 所有 Agent 的共享思维数据库。 |
| Codex 或 Web Agent | 读证据、形成计划、做内容/创作选择、解释风险。 | 帧级一致性和数据库事务的唯一维护者。 |
| Skill | 推荐顺序、专业约束、停止和验证规则。 | 会自动执行的后台任务。 |
| MCP | 读取项目事实、提交受控读写、跟踪部分异步状态。 | 自动导演或审美裁判。 |
| ChatCut 项目状态 | Asset、Timeline、Item、字幕、效果、任务和可见编辑结果。 | 对话历史或模型推理日志。 |

特别是“同一个 `projectId`”只能证明项目状态可成为共同事实；它不证明 Web AI Panel 的聊天、@ 引用、原生 Agent 计划和 Codex 对话会自动互通。

### 8. 证据等级与未知边界

最后才把每段结论放回四种标签：已实测、工具/Skill 合同明确、合理推断、未验证。先写机制，再用证据限制它的范围；不要先塞一句“已实测”，却没有解释它到底证明了怎样的状态关系。

## 四、实验怎样设计：验证机制，不是验证“工具有没有”

有价值的实验不是“点一下看会不会成功”，而是先写能被证伪的假设。

### 通用实验卡

~~~text
研究问题：这项机制要解决什么编辑混乱？

假设：若具有 X 合同，执行 Y 后应看到 Z；
      若违反前置条件，应拒绝、回滚、要求刷新或进入可解释的等待状态。

基线：Project、Timeline、相关 Asset / Item / Caption / 效果的读回。
变量：一次只改变一个编辑意图或一个前置条件。
操作：MCP 或浏览器的可复现动作。
读回：结构、版本、坐标、合成帧；必要时导出或试听。
结论：能证明什么、不能证明什么、应写回哪一篇架构正文。
~~~

### 例：Script 的深度实验组

| 要验证的机制 | 最小操作 | 必须观察什么 | 能升级出的架构结论 |
| --- | --- | --- | --- |
| 语义选择不是直接帧操作 | 删一个完整表达 | Script 顺序、Item 源范围、最终帧范围。 | Agent 可在语义面选择，后端承担落帧。 |
| 后端负责主线重编译 | 删除后读取后续 Item | 后续成片位置、时长、源偏移。 | 不应让 Agent 长期维护后续帧算术。 |
| 字幕是主语音派生层 | 删除前后读取 Card / Token | 被删文字消失、保留文字的新帧位。 | 字幕可投影，不等于切口已自然。 |
| 旧快照不能覆盖新状态 | 读 Script 后另改 Timeline，再提交旧快照 | 拒绝、刷新要求或版本冲突。 | 结构编辑存在新鲜度边界。 |
| 批量写入有一致性边界 | 在一个批次中故意放入非法操作 | 是否整体失败、是否残留半状态。 | 不能凭单次成功推断原子性。 |
| 独立包装不会天然语义跟随 | 切点周围放 Ding、MG、B-roll 或绝对效果后删句 | 各对象的位置、关系和语义是否仍合适。 | 影响传播要按依赖类型拆，不能统一假设。 |

若某个入口因授权、工具缺失或用户未授权而无法执行，正确结果是“未验证 / 当前入口受阻”，不是把理论上合理的结果写成成功。

## 五、架构正文和证据账本怎样分工

### 架构正文应该写什么

正文按**问题和机制**组织，而不是按“实验 1、实验 2”组织：

1. 为什么这类剪辑需要这个抽象；
2. 哪些对象、坐标、版本和权威状态参与；
3. Agent、后端和用户各怎样交接；
4. 主线变化为何会影响不同下游对象；
5. 正常、失败和恢复路径分别怎样走；
6. 结论属于哪一种证据等级。

正文可以引用一个小样例解释对象关系，但不能被几十行 JSON、每一步按钮点击或无关截图淹没。

### 证据账本应该写什么

第 08 篇和附录承担追溯职责，应保存：

- 实验目的、假设、样本和边界；
- 写入前后的关键返回字段、ID、时间范围和错误；
- 浏览器、合成帧、导出或声音核验；
- 能证明什么、不能证明什么；
- 它具体支撑正文的哪条机制。

隐私 URL、编辑器启动令牌、账号信息、完整原始响应和不必要的大体积素材路径，不应成为正文内容。

### 一个合格的回链关系

~~~text
正文：解释“为什么 Script 必须有新鲜度保护”。
  ↓
证据账本：记录“旧 Script 在 Timeline 已变化后被拒绝”的前后状态。
  ↓
附录 B：把尚未验证的并发、回滚、跨入口同步列成下一轮可证伪实验。
~~~

不是：

~~~text
正文：贴出长工具返回
→ 说“所以产品有架构”
~~~

## 六、正文中什么该写，什么不该写

| 应写进 ChatCut 拆解正文 | 应留在证据账本、改成未知或删除 |
| --- | --- |
| “源时间和成片时间是两套坐标，因此重排不等于改坏原片。” | 某次实验恰好删了第 690 帧的完整操作日志。 |
| “Caption 是最终可播放语音投影出的屏幕对象，含文本、布局和词级时间。” | `read_captions` 的全量原始 JSON。 |
| “独立音效和 MG 可以保留物理位置，却失去原有叙事理由。” | “工具返回成功，所以音效自动选对了。” |
| “Skill 规定专业决策顺序，MCP 执行当前宿主暴露的受控操作。” | 把 Skill 当作某个当前 MCP 一定存在的工具。 |
| “Web 与 Codex 可以围绕一个项目工作，但聊天和推理未证实共享。” | 猜测 Web Agent 的私有队列、模型、向量库或内部代码。 |
| “当前没有观察到统一影响报告。” | “ChatCut 一定没有任何影响报告能力。” |

## 七、常见失败模式与改法

### 失败一：从工具清单出发

**症状：** 记录了 58 个工具，却说不清哪些一起构成一条编辑链。  
**改法：** 先按“素材事实 → 证据 → 主线选择 → 时间线写入 → 包装 → 验证”划分能力域，再把工具作为每段的读写入口。

### 失败二：把一次成功写成全产品能力

**症状：** “删句成功”被写成“所有下游对象都会自动跟”。  
**改法：** 一定补“对象记住什么、这次具体测到什么、尚未测什么”。字幕重投影不能证明 Ding、MG 或音乐自动重锚。

### 失败三：把结果当作内部原因

**症状：** “后面的 Item 左移了，所以 ChatCut 一定用了某个算法”。  
**改法：** 只写外部可确认的状态变化；需要解释机制时，写“要稳定产生这种行为，至少需要类似的坐标/版本/写入职责”，并标为合理推断。

### 失败四：把 Agent 和程序职责混为一谈

**症状：** 既说 Agent “删一句”，又说 Agent “重算所有帧、保证回滚”。  
**改法：** 固定用两个词：**内容选择权**属于 Agent/用户，**一致性责任**属于确定性项目写入和验证层。

### 失败五：只写 happy path

**症状：** 文档顺畅，却无法回答陈旧 Script、处理未完成、授权失败、同轨冲突怎么办。  
**改法：** 每个核心机制至少有一个失败/恢复路径；无法测试时也要把终止条件写出来。

### 失败六：把编辑方法写成 ChatCut 自动功能

**症状：** 用“访谈应按问答剪”“影视高光应有情绪弧”就得出“ChatCut 已经自动生成它”。  
**改法：** 清楚分开“专业规划方法”“Skill 合同”“当前 MCP 实测”。第 02 篇的类型规划是解释主线如何应当被判断，不是未证实的一键模式。

### 失败七：测试报告压过架构解释

**症状：** 读者记住了帧号和工具名，却不知道为什么删一句与删一帧不同。  
**改法：** 正文以机制为标题，实验归入第 08 篇；正文只保留足以证明关系的最小例子。

## 八、不同视频类型如何沿用同一方法

不同类型改变的是“主线单位、首要证据、写入路径和验收问题”，不是把架构分析换成另一套。

| 类型 | 主线单位 | 首要证据 | 主写入路径 | 首要验证风险 |
| --- | --- | --- | --- | --- |
| 单人口播 | 完整表达、重拍、观点。 | 转写、词级时间、停顿和口型。 | Script → `apply_script`。 | 删句后逻辑、字幕和声音切口。 |
| 访谈 / 播客 | 问答回合、回答、反应。 | 多人转写、说话人、同一时刻的机位。 | 先内容主线，机位再通过 Timeline 选择。 | 同步事实与节目版是否被混淆。 |
| 无声 Vlog | 场景、动作、旅程事件。 | 局部源帧、环境声、用户说明、旁白计划。 | Timeline Item；旁白另建同步图。 | 不应把 `no_audio` 写成自动故事理解。 |
| 教程 / 录屏 | 一个可完成的步骤。 | 屏幕状态、操作、前后结果。 | 画面主线 + Callout / 字幕 / 旁白。 | 讲解和关键操作是否仍对应。 |
| 影视高光 | 冲突、升级、爆点、余韵。 | 表演、动作、台词、声音与反应。 | 视觉/声音结构的 Timeline 规划。 | 不应把普通排片能力写成自动情绪选段。 |

深度实验也因此不同：口播重点测 Script、版本、字幕和切口；Vlog 重点测画面证据与旁白锚；影视高光重点测选段证据是否足够，而不是只测“片段能不能放到 V1”。

## 九、交付前自检

### 架构理解

- [ ] 不看第 08 篇，读者是否能画出主要对象、状态和引用关系？
- [ ] 是否先解释根矛盾，而不是从 MCP 工具数开始？
- [ ] 是否分清源坐标、成片坐标、字幕时间和事件锚？
- [ ] 是否分清 Agent 的内容选择权与程序的一致性责任？
- [ ] 是否写清主线改变后为何不同对象有不同命运？
- [ ] 是否至少有一条不变量和一条失败/恢复路径？

### 证据边界

- [ ] 每个关键结论是否标为已实测、合同明确、合理推断或未验证？
- [ ] 是否把单一样本扩大成全版本、全素材或内部实现？
- [ ] 是否把 Skill 的推荐流程误写成当前宿主必有工具？
- [ ] 是否把原始帧号、JSON、截图和操作日志留在证据账本？

### 文档范围

- [ ] 是否所有结论的主语都是 ChatCut、当前 MCP、官方 Skill 或本轮实验，而非其他项目实现？
- [ ] 是否把“继续研究什么”写成待验证问题，而不是外部产品缺陷？
- [ ] 是否把用户、Web、Codex、Skill、MCP 和项目状态的边界写清？

## 十、最终工作流

~~~mermaid
flowchart LR
    A[定义根问题] --> B[提出可证伪机制假设]
    B --> C[画对象、状态、坐标与依赖]
    C --> D[设计最小对照实验]
    D --> E[读取 MCP / Skill / UI / 导出证据]
    E --> F[区分实测、合同、推断、未知]
    F --> G[写架构正文]
    F --> H[写证据账本与下一轮实验]
    H --> G
~~~

最终目标不是证明“ChatCut 工具很多”或“某次剪辑成功”，而是让读者能够稳定回答：

~~~text
它为什么需要这几层状态？
它怎样避免多轮编辑后坐标和对象混乱？
哪一部分是 Agent 的编辑判断，哪一部分由程序兜底？
改动或失败时，什么会更新、什么会停下、什么必须让人确认？
目前的结论究竟是实测、合同、推断还是未知？
~~~

能够严谨地回答这些问题，才算完成一次深度的 ChatCut 产品拆解。
