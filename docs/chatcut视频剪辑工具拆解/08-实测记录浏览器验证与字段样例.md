# 08｜实测记录、浏览器验证与字段样例

> 证据范围：本篇仅记录本轮真实 ChatCut 项目的可观察结果。项目 ID、完整资源 URL、编辑器启动令牌和完整内部 UUID 已脱敏；字段名来自当前 MCP 返回，不应被误当成未来版本的永久接口承诺。

## 实验原则

每条结论至少按下列证据链记录：

~~~
操作前状态
→ MCP 写入或读取结果
→ 再读项目 / Timeline / Item / Caption
→ 浏览器或云端合成帧检查
→ 写出已证明和未证明的部分
~~~

工具返回 success、生成任务完成或某个 Asset 出现在素材库，都不是“观众实际看到的视频正确”的充分证据。

本篇的主体始终是 **ChatCut 当前 Hosted MCP + 当前 Web 编辑器接入面**。它记录的是外部产品证据；第 10 篇只用来区分“证据等级”和“链路是否闭环”，不把实验现象转写成其他系统的实现结论。

## 实验不是“功能打勾”：每一组证据支撑哪一条产品机制

本篇中的实验被拆到对应正文里使用。下表让读者能从一个实验回到它真正证明的状态关系，也能看清它没有证明什么。

| 实验组 | 试图回答的根问题 | 支撑的机制章节 | 已经能证明什么 | 仍不能证明什么 |
| --- | --- | --- | --- | --- |
| 项目 / 浏览器同项目 | MCP 写的是否是真实编辑器项目 | 01、11 | MCP 与 Web 围绕同一项目与 Timeline 工作 | 内部实时同步协议、后台任务拓扑或毫秒级推送 |
| ASR、无声、弱口播 | 素材处理是否会把无语音伪装成文字 | 03 | no_audio 是成功终态；有声素材可进入转写路径 | 已完成完整视觉语义索引或自动故事理解 |
| 18 段口播重排 | 谁在决定内容，谁在计算帧 | 02、05 | Agent 选语义主线；后端编译跨 Asset 的 V1 Item | 自动选择“最佳”叙事，或自动补包装 |
| 删完整语义 | Script 会怎样影响主线和字幕 | 04、05、06 | 主线重编译；被删 Card 消失；后续字幕重投影 | 所有 V2/A1/MG/音乐都会语义跟随 |
| 插入 30 帧与 1 帧删改 | ripple 和独立轨怎样传播 | 04、06 | ripple 只移同轨 V1 后续 Item；V2/A1/绝对时间 Zoom 保持原帧 | 任意效果、MG、B-roll、音乐的通用跟随规律 |
| 片段 / 轨道两类 Zoom | 效果为什么有时跟随、有时不跟随 | 04、06 | 本轮 builtin Zoom 有片段绑定与绝对时间两类关系 | 所有第三方效果、转场、LUT 都相同 |
| 字幕 Card / Token / Span | 字幕是怎样准确落到成片时间线 | 04、06 | Card 有布局、Token 有绝对帧、局部强调可随词级时间变化 | 人工逐词重计时、翻译、多源叠放的完整闭环 |
| Ding / Whoosh / Duck 导出 | 声音位置与最终混音是否真的进入交付物 | 06 | Item 起点不等于主要声音能量；Duck 在最终 MP3 中生效 | 每种声音都自然好听、音乐生成质量或完整混音审美 |
| 陈旧 Script / 原子批次 / 副本 | 写入错误会不会留下半成品 | 05、07、11 | 旧 Script 被拒；非法批次无半提交；副本局部隔离 | 多用户自动合并、完整版本历史和跨项目回滚 |
| 自动导演入口审计 | ChatCut Web / MCP 是否暴露内置导演入口 | 07、11 | 当前 Hosted 接入面没有可实测入口 | 其它权限、版本或 Desktop 面没有该能力 |
| 资源下载与外部搜索 | 项目内可用是否等于可下载、可复用 | 09 | source 下载目标和一次外部检索可观察 | 内置/生成资源批量下载与许可闭环 |

读正文时应按这个方向使用证据：

~~~text
实验观察到的输入 / 输出
→ 只升级为一条有限的行为结论
→ 用这条行为解释对象关系、职责边界或失败恢复
→ 明确不把它扩大为私有算法、全产品承诺或未测过的运行时能力
~~~

例如，“Duck 导出的两段人声窗口都下降约 6.6 dB”只支撑“Anchor / Follower 配置进入本轮最终云端 MP3”；它不能支撑“背景音乐一定好听”，更不能支撑“ChatCut 的音乐生成已经完整测通”。

### 历史实验基线（2026-08-26）

本篇实验 1、3、4、7 中的“调研-节点联动实测”是历史测试线：它当时为 1280×720、30 fps、2700 帧（90 秒）、8 条 Timeline。浏览器中可见陈清泉访谈主画面、V2 的关键观点 MG 动画、V1 的访谈片段和 A1 的音效波形。它仍是有效的实验记录，但不再是项目当前活动状态。

## 实验 1：MCP 与浏览器是否指向同一个项目（2026-08-26 历史基线）

### 目的

验证 MCP 不是一个脱离编辑器的“假状态”，而是写入/读取同一 ChatCut 项目。

### 读回

read_project 返回：

~~~
activeTimeline:
  canvas: width=1280, height=720
  fps: 30
  durationInFrames: 2700
  captions: present
assets.byType:
  video: 5
  audio: 1
  motion-graphic: 1
timelines: 共 8 条
~~~

浏览器中可见同一个活动 Timeline、同一个 90 秒标尺和相同的轨道组织。

### 结论

**已实测：**MCP 与浏览器编辑器指向同一项目状态。  
**未证明：**浏览器可见不自动意味着每一次网络写入都即时同步；做写入时仍应读回最新状态。

## 实验 2：素材处理、ASR 与无声素材

### 使用的素材类别

| 素材 | 观察到的结果 | 可以得出的结论 |
| --- | --- | --- |
| 陈清泉访谈 C1297 | ready、ASR complete、云端可用 | 语音驱动素材可进入转写与字幕工作流。 |
| 陈清泉访谈 C2770 | ready、ASR complete、云端可用 | 同上。 |
| 陈清泉另一机位 C2169 | ASR complete，但处理/云端状态不完全可用 | “已转写”不等于所有云端动作已准备好。 |
| 猫咪竖版 | no_audio 成功终态，字幕为 0 | 没有语音是成功分析结果，不应强行重试。 |
| 游泳弱口播竖版 | ASR complete，长静音没有生成字幕 | 系统不会把无声段虚构为语言。 |

### 结论

**已实测：**ChatCut 对有声与无声素材有不同处理终态。  
**不能推出：**无声素材已经被自动理解为“Vlog 场景、人物行为和故事线”。

## 实验 3：历史 Timeline 的真实字段（2026-08-26）

在“调研-节点联动实测”的第 630–740 帧窗口读取 Timeline，得到如下去标识化结构：

~~~
V1
  video Item：timelineRange [0, 2700)
  sourceRange：原素材 1800s–1890s

A1
  gap [630, 672)
  audio Item（Clean Ding）：timelineRange [672, 721)
  gap [721, 740)

V2
  gap [630, 674)
  motion-graphic Item：timelineRange [674, 729)
  gap [729, 740)

V1 effects
  builtin:zoom：fromFrame 674，durationInFrames 55
~~~

preview_timeline 返回中可见的重要字段包括：

| 字段 | 人话解释 |
| --- | --- |
| trackAlias / trackId | 该对象属于哪一条轨道，例如 V1、V2、A1。 |
| timelineRange.fromFrame/toFrame | 它在成片哪一段出现，结束帧为排他边界。 |
| sourceRange.startSeconds/endSeconds | 视频 Item 从原始素材哪段时间取。 |
| itemType | 它是 video、audio、motion-graphic 等什么对象。 |
| effects | 某轨或片段上的效果范围和参数。 |
| role | 音轨的 Anchor / Follower 自动 duck 角色，未设置时为 null。 |

### 结论

**已实测：**视频、音频、MG 动画和效果是不同的对象，但都共用 Timeline 的帧坐标。  
**注意：**这条历史测试线的 Ding/MG 起点与“删 1 帧”隔离测试线不相同；这是两条独立 Timeline，不能把不同版本的帧号混为同一次状态。

## 实验 4：字幕 Card 的真实结构

在 2026-08-26 的历史测试线中，`read_captions` 返回 52 个 Caption Card，并包含一个修订版本号。2026-08-27 对当前活动线再次读取，仍为 52 张 Card；当前字幕样式和几何信息中可见：

~~~
fontFamily: Inter
fontFallbacks: [Noto Sans SC]
layout: left=192, top=613, width=896, height=49
~~~

单个 Card 具有：

~~~
id
source / variant
frame=开始帧-结束帧
text
words 数量
layout（有效位置、换行能力、overflow 状态）
styleOverride / inlineStyles / tokenStyleSpans
~~~

其中关键观点“科学家的使命”在历史活动 Timeline 中是一个自动 Card，范围为第 674–729 帧。它与 V2 的关键观点 MG 动画和 Zoom 效果在同一段时间内相遇，但三者是不同对象。

### 结论

**已实测：**字幕不仅有文本，还有修订版本、帧范围、来源、布局、换行与局部样式状态。  
**补充后的状态：**数字人口播实验已经直接读取词级 Token 时间，并写入了 span 的常态样式、当前词高亮和进入动画；逐词 Token 的人工重计时、翻译和多源字幕仍未实测。

## 实验 5：删除 1 帧的联动行为

本实验的完整解释见第 04 篇，这里只记录结果。

| 测试版本 | V1 后续视频 | 字幕 | A1 Ding | V2 MG 动画 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 不 ripple | 保持原起点，删除处留下 1 帧空洞 | 在空洞前后拆开 | 不移动 | 不移动 | 其它独立轨不跟 V1 物理删除自动位移。 |
| ripple | V1 后续 Item 从 691 自动左移到 690 | 重新连续 | 不移动 | 不移动 | ripple 只处理同轨的后续 Item；字幕为派生层。 |

云端合成帧在不 ripple 版本中显示：第 690 帧为黑底 + MG 动画、无字幕；在 ripple 版本中，第 689/690/691 帧连续显示人物、标题和字幕。

### 结论

**已实测：**删除后同轨 ripple 是 ChatCut 后端完成的帧位移，不是 Codex 手工重新计算。  
**已实测：**字幕随最终可播放语音重新映射。  
**已实测：**音效和 MG 动画不会自动语义跟随，需要检查和必要时重锚。

## 实验 8：18 段数字人口播的语义短版、逐字字幕与句子删除联动

> 本实验使用与前述访谈调研分开的 ChatCut 项目，避免把两个项目的 Timeline、帧号和素材数混为同一份证据。下文不记录完整项目 ID、资源 URL 或启动令牌。

### 8.1 测试素材与进入项目的状态

| 项目 | 实测结果 |
| --- | --- |
| 输入 | 18 段数字人口播视频；每段约 10.125 秒，768×1344、24 fps。 |
| 总时长 | 约 182.25 秒。 |
| 导入状态 | 18/18 已成为项目中的独立视频 Asset，均可云端读取。 |
| 转写状态 | 18/18 完成中文转写，并具备词级时间。 |

最重要的观察是：18 个文件在转写完成后仍是 18 个独立来源。ChatCut 没有自动宣布“它们合起来是一篇已经理解好的口播文章”；要先通过 Timeline 和 Script 把它们组织成一条可以编辑的主线。

### 8.2 从 18 个 Asset 到 81 秒语义短版

先将 18 段按原叙述顺序摆到同一条 V1。读回得到：

~~~text
18 个 V1 Item
4374 帧
约 3 分 02 秒
18 个来源区块、59 个可操作语义段
~~~

随后通过 Script 一次性保留并重排：

~~~text
01 → 02 → 05 → 09 → 13 → 15 → 16 → 18
~~~

提交后的活动 Timeline 为：

~~~text
8 个 V1 Item
1944 帧
81 秒
768×1344、24 fps
~~~

结构读回显示 8 个 Item 都仍引用原素材的完整源范围；这不是把 8 个视频在本地预合成为一个不可编辑 MP4。云端合成帧和浏览器时间线都显示了这 8 个按顺序排列的片段，未发现黑帧或丢画面。

### 8.3 浏览器看到的是什么

同一项目已在 ChatCut 浏览器编辑器中打开。实际可见：

~~~text
项目名：数字人口播多片段语义剪辑调研
活动 Timeline：81 秒
V1：01、02、05、09、13、15、16、18 八段视频缩略图
预览：竖版数字人画面与字幕
~~~

这证明 MCP 写入的是浏览器编辑器可见的项目结构。它不证明每个切点在创作上已经自然：这条短版仍以硬切连接，不同片段的手势、姿态和镜头观感可能跳变。

### 8.4 字幕 Card 与逐字强调

短版的 25 个 Script 语义行被重新分页为 33 张字幕 Card。也就是说：

> Script 行负责“要不要播放这段话”；Caption Card 负责“观众此刻读哪一小句”。

对“慢慢把意义做出来”这句做了真实的 Card 内局部样式写入：

| 项目 | 结果 |
| --- | --- |
| Card 范围 | 807–856 帧。 |
| 常态 | 黄色、加粗、放大约 12%。 |
| 当前说到的字 | 深色字、黄色强调底。 |
| 进入动画 | 约 180ms 的轻微上移与缩放。 |
| 验证 | 读回显示该 Span 绑定 8 个词级 Token；抽样合成帧确认了样式和高亮状态。未对整段逐帧播放，也未做完整听感验收。 |

这 8 个 Token 的实际时间为：慢 `809–814`、慢 `815–817`、把 `817–823`、意 `823–828`、义 `828–831`、做 `831–837`、出 `837–840`、来 `840–846`。这说明 Card 的样式可以绑定到词级时间；它不等于已经逐帧验收整段动画是否每一帧都自然。

这一项是字幕动态，不是 MG 动画。数字人口播受控短版没有添加 MG、Zoom、B-roll、转场、背景音乐或音效。

### 8.5 删除一句话后，视频与字幕怎样联动

在另一条隔离 Timeline 中，先只放一段约 10.1 秒的数字人口播，然后通过 Script 删除开头完整一句“但人可以在每一次选择里慢慢把意义做出来”，以及相邻的无声空隙。

| 删除前 | 删除后 |
| --- | --- |
| 一个视频 Item，约 10.1 秒 | 仍是一个视频 Item，约 4.5 秒 |
| 使用源素材 0–10.1 秒 | 使用同一源素材约 5.6–10.1 秒 |
| 后两句在源片后半段 | 后两句从新 Timeline 的第 0 帧开始播放 |

启用并刷新字幕后，第一张 Card 是“不是等答案出现”，范围为 0–55 帧；第二张是“而是先去认真的生活”，范围为 55–134 帧。合成帧确认两句都贴合新画面，没有黑帧或被删句子的残留字幕。

**可得结论：**对口播做 Script 语义删除时，后端会重新计算源偏移、Item 时长和最终字幕时间；这不是 Codex 手工把后续所有对象逐帧平移。

### 8.6 硬切声音的实际处理

对 81 秒短版运行 smooth_audio，先预检、再真实提交：

~~~text
真实交叉淡化：0
没有可用源余量、退化为淡入/淡出：7 个切口
写入短淡入：8 个片段
写入短淡出：8 个片段
~~~

两个相邻视频 Item 读回均显示约 0.1667 秒的音频淡入和淡出。原因是每段均使用完整源范围，不能用不存在的余量做真正重叠。这个结果只能证明“后端按规则处理了切口”，不等于已经通过完整听感审片。

### 8.7 本实验已经证明与尚未证明的边界

| --- | --- |
| 多个独立口播 Asset 可经 Script 跨来源重排为可编辑短版。 | ChatCut 会自动替编辑者找到最好的叙事顺序。 |
| 句子删除后，源范围、主视频和字幕可重新落在新的时间线位置。 | MG、音效、音乐会自动理解语义并一起移动。 |
| Card 内文字可按词级时间做局部强调和进入动画。 | ChatCut 会自动决定哪些句子应高亮、应推近或应加 MG。 |
| 无源余量时，音频平滑会退化为短淡入淡出。 | 这种技术处理已经保证所有切口听起来都自然。 |

## 实验 9：多轨时间线的插入、语义删除与 1 帧删除（2026-08-26）

> 本实验在“调研-语义删插联动-实测副本”中的独立 Timeline 完成；没有修改最初的调研项目。所有项目 ID、编辑器启动令牌、资源 URL 均省略。

### 9.1 为什么这条线比前面的单轨实验更有价值

之前的 Script 句子删除实验主要验证了 V1 与字幕。这次故意把不同类型的对象同时摆进一条 30 fps、768×1344 的 Timeline，测试“主线变化后谁跟、谁不跟”：

| 对象 | 基线位置 | 对象关系 |
| --- | --- | --- |
| V1 主口播 | 三段顺序 Item：`[0,120)`、`[120,240)`、`[240,360)` | 主叙事骨架。 |
| V2 画中画 | `[160,220)` | 叠在 V1 上方的独立视频 Item。 |
| A1 `Clean Ding` | `[178,227)` | 独立音频 Item；编辑事件在约第 180 帧。 |
| V3 Zoom | `[170,210)` | 轨道范围效果，按绝对成片帧定位。 |
| V1 Zoom | 绑定在后两个 V1 Item | 片段绑定效果，按目标 Item 关系定位。 |
| 字幕 | 仅选择 V1 为来源 | 由最终可播放语音派生的 Caption Program。 |

这条基线不是“已经包装完成的片子”：没有背景音乐、MG 动画或转场。它的目的只是把最容易混淆的四类对象——主线 Item、独立上层/音频 Item、片段绑定效果、绝对时间效果——放到同一个可读回的实验里。

### 9.2 在 V1 中插入 30 帧视频：谁被后端推开，谁不动

在 V1 的第 120 帧边界插入一段 30 帧口播，并调用带 `ripple:true` 的 `edit_item`。没有对 V2、A1 或 V3 发送移动命令。提交前后读回如下：

| 对象 | 插入前 | 插入后 | 这说明什么 |
| --- | ---: | ---: | --- |
| V1 第二段 | `[120,240)` | `[150,270)` | 同轨后续 Item 被后端右移 30 帧。 |
| V1 第三段 | `[240,360)` | `[270,390)` | 同上。 |
| 整条 Timeline | 360 帧 | 390 帧 | 主线变长 30 帧。 |
| V2 画中画 | `[160,220)` | `[160,220)` | 独立上层 Item 没有一起右移。 |
| A1 Ding | `[178,227)` | `[178,227)` | 独立音频 Item 没有一起右移。 |
| V3 Zoom | `[170,210)` | `[170,210)` | 绝对时间效果没有一起右移。 |
| V1 片段绑定 Zoom | 附着在原目标片段 | 仍附着在对应片段 | 它不是按整条时间尺保存的位置。 |

插入后的云端合成帧确认：第 119→120 帧切换没有黑帧；第 160、180 帧仍显示画中画和 Zoom；第 300 帧的字幕已对应第三段内容。这里的“仍显示”也是风险提醒——视觉或声音对象虽然仍存在，却未必仍对应原来要强调的语义。

### 9.3 用 Script 删完整语义：不是 Codex 手算所有帧

在插入版本的副本中，调用 `read_script`，直接从 `timelineMd` 删除插入素材下完整的语义行“后来”，然后先执行：

~~~text
apply_script({ timelineMd, preview: true })
~~~

预览返回的关键信息是：V1 删掉 1 行后变成 3 个 Item，顺序回到原来的三个口播来源；被删来源被明确列出；V2 保留既有 gap 与画中画。也就是说，Script 的预览面表达的是“观众不再听到什么”，不是一张要求 Codex 手填新帧号的表。

正式提交后，再读 Timeline、Item 与字幕：

| 对象 | 读回结果 |
| --- | --- |
| V1 | 原先第 150 帧开始的后续片段变为第 120 帧开始；原先第 270 帧开始的第三段变为第 239 帧开始；V1 Item ID 已改变。 |
| V2 | 仍在约 `[160,221)`，没有跟 V1 一起左移。 |
| A1 Ding | 仍在 `[178,227)`。 |
| V3 绝对时间 Zoom | 仍在 `[170,210)`。 |
| 片段绑定 Zoom | 新 V1 Item ID 虽变，`inspect_item` 仍显示效果附着在相应保留片段。 |
| 字幕 | “后来”的 Card 被删除，后续字幕回到新的 V1 播放时间。刷新后返回 `status: canonical`、`changedCards: 0`。 |

这一组证据支持的说法是：**ChatCut 后端/MCP 把 Script 的语义选择重新编译为 Item、源区间和帧位；Codex 没有在这次操作里逐项计算和写入后续 V1 的新坐标。** 但从外部接口看不到私有函数或服务边界，因此不能写成“已知某段 MCP 源码如何实现”。

### 9.4 同样删 1 帧：有 ripple 与无 ripple 的真实差别

两条隔离 Timeline 都先在 V1 的第 180 和第 181 帧切开，再删除中间精确的 `[180,181)` 这一帧。

| 测试版本 | V1 读回 | 全片长度 | V2 / A1 / V3 | 云端第 180 帧 |
| --- | --- | ---: | --- | --- |
| 不 ripple | `[150,180)`、gap `[180,181)`、`[181,270)` | 390 帧 | 都保持原绝对位置 | 主画面黑；右上角 V2 画中画仍可见。 |
| `ripple:true` | `[150,180)`、`[180,269)`；下一段 `[269,389)` | 389 帧 | 都保持原绝对位置 | 主画面、画中画、字幕都连续可见。 |

这里有两层不同的“成功”：

1. **机械成功**：ripple 把同轨空洞合拢，后续同轨片段左移；第 180 帧不再黑。
2. **编辑失败风险仍在**：字幕词级读回为“我”`[174,180)`、又一个“我”`[180,181)`、然后“最”`[181,186)`。它说明时间投影连续，却也暴露出切在汉字发音中间的 1 帧重复。

因此，物理删帧适用于明确的帧边界修正；口播、访谈、数字人台词的正常删改仍应优先走 Script 的完整语义单元。否则程序可以保证“帧没断”，却不能保证口型、听感和字幕阅读自然。

### 9.5 片段绑定 Zoom 与绝对时间 Zoom 的对照

为避免把“所有效果都会跟”写成猜测，分别读取了切分后的 V1 Item：

| 效果关系 | 实际读回 | 可下的结论 |
| --- | --- | --- |
| 片段绑定 `builtin:zoom` | `inspect_item` 在切点后的新 V1 Item、以及后续第三段 Item 上都返回 `Attached effect ... builtin:zoom`。无 ripple 与 ripple 两个版本均如此。 | 本次 Zoom 关系没有丢失；切分后它保留在包含效果范围的后半段，而非复制给切点前半段。 |
| V3 轨道范围 `builtin:zoom` | `preview_timeline` 始终读到 `fromFrame: 170`、`durationInFrames: 40`。 | 它记住的是 Timeline 的绝对帧范围；主线增删后不会理解要跟随哪一句。 |

**不能扩展的结论：**这只验证内置 Zoom。MG 动画、转场、LUT、B-roll、音乐、第三方效果是否继承，需要各自的隔离实验和合成帧检查。

### 9.6 浏览器与云端画面怎样交叉验证

本轮没有只凭 MCP 的 `success` 字样写结论：

~~~text
结构证据：read_project / preview_timeline / inspect_item / read_captions
像素证据：云端合成第 179、180、181 帧并逐张查看
编辑器证据：浏览器打开同一条 Timeline 副本，活动标签为“实测-1帧删除-涟漪-20260826”
~~~

浏览器画面中可见 V1 的切分片段、V2 画中画、V3 的 `1.5x Zoom` 范围和 A1 `clean-ding-r1` 波形；云端第 180 帧同时确认合成后的画面不是黑屏。两者的职责不同：浏览器证明 MCP 改动真实落在用户可见编辑器；云端精确帧图证明特定时间点的最终叠加像素。

### 9.7 本轮“谁做什么”的证据边界

| 层 | 本轮直接观察到的责任 | 不应过度声称的部分 |
| --- | --- | --- |
| Codex / 编辑 Agent | 选择插入位置、选择 `ripple`、在 Script 中删除完整语义、判断 1 帧切割不自然。 | 它没有通过手算把所有后续 Item 逐帧搬到新位置。 |
| ChatCut MCP / 后端 | 接受编辑操作，读回新的 V1 帧位、源区间、字幕投影及效果附着关系。 | 外部 MCP 无法揭示私有编译器、字幕服务或数据库中究竟由哪一段代码执行。 |

| 用户审片 | 判断语义、口型、听感、字幕可读性和包装是否仍服务内容。 | 不能用一张截图代替连续播放和听感审查。 |

| P1 | 锁轨、重叠、过期 Script、非法源范围 | 主动制造失败条件。 | 是否整批回滚；是否留下半完成 Item、字幕或效果。 |

### 每个实验都必须完成的五步读回

~~~text
1. 建基线：读 Timeline、相关 Item、Caption Card、效果与音频 Item，并保存关键帧画面。
2. 预检：能用 validateOnly 或 Script 预览时先预检；ripple 不能与 validateOnly 同用时，先复制隔离 Timeline。
3. 单变量提交：一次只改一个问题，例如只插一段 V1 视频，不顺手改字幕、音乐或 MG。
4. 结构读回：重新读所有相关轨道、Item 源范围 / 成片帧位、Caption Card / Token、效果和音频 Item。
5. 可见结果：查看变更点前、中、后的合成帧与浏览器播放；对声音改动还要实际试听，而非只看字段。
~~~

只有五步都留下证据，才能回答“谁自动重算、谁保持绝对位置、谁需要 Agent 重锚”。工具返回 success、Item 数量变化或一张单独 Timeline 截图，都不足以单独证明联动正确。

## 实验 11：当前接入面有没有可实测的“自动导演”执行入口

### 目的

区分两件常被混在一起的事：

1. Codex 这类外部编辑 Agent 可以根据素材、Skill 和 MCP 做导演判断；
2. ChatCut 当前 Hosted MCP / Web 是否另有一个可直接提交任务、自动完成导演规划的内置 Agent 入口。

### 操作与观察

- 审计当前 Hosted MCP manifest，未发现 `run_agent`、`chat_agent` 或同等的导演执行工具；
- 打开隔离项目的 Web 编辑器，能看到“剪口播”工作区，但没有可输入导演要求、提交任务并读取执行结果的明确对话面板；
- 尝试切换可见工作区后，仍没有得到可以提交一次“请为这批素材做导演规划”的完整入口。

### 结论

**[已实测]** 当前 Hosted MCP 与本次初始 Web 工作区，**没有暴露可供本轮执行和读回的自动导演入口**。  
**[不能扩大为]** ChatCut 产品一定没有自动导演 Agent。可能存在其它账号权限、版本、Desktop 工作面或尚未暴露给当前连接器的入口；本轮没有证据可以替它下否定结论。

本套文档中“编辑 Agent”默认指执行本次操作的 Codex / 调用方 Agent，除非明确写成“ChatCut 内置 Agent”。

## 实验 12：Duck 与 Whoosh 是否真的进入最终云端声音成片

### 目的

此前的轨道角色和 Item 字段只能证明“项目里写了 Duck / 音效设置”。本实验改为验证 ChatCut 云端真实导出的声音：人声出现时背景音乐是否确实下降，音效的物理 Item 起点是否等于人耳听到的主要起音。

### 受控导出

从同一 Timeline 导出三条真实 MP3，而不是用本地模拟波形：

| 导出版本 | 用途 |
| --- | --- |
| Duck 开 | 人声 Anchor 与音乐 Follower 同时存在。 |
| Duck 关 | 保持同一音乐与主线，关闭 Duck 关系。 |
| 仅 BGM 基准 | 用来对照没有人声覆盖时的音乐电平。 |

三条导出均约为 29.0337 秒。以人声 Anchor 的两个说话区间为窗口，对比导出波形后，Duck 开版本的背景音乐分别比 Duck 关版本低约 `-6.62 dB`、`-6.61 dB`；与 Timeline 读回的 `duckDepthDb=-6.6` 一致。开头无人声区两条导出基本无差异；人声停顿处可见恢复尾音，片尾基本恢复。

### Whoosh 的位置

Whoosh Item 在 Timeline 中的物理范围为 `[117,156)`，即约 `3.90–5.20s`；最终导出的主要声音能量约在 `4.35s` 附近出现。它说明：

> 音频 Item 的物理起点，不等于观众听到主要声音的起点。

文件前置静音、渐入或音色本身的能量爬升，都会造成两者不同。编辑 Agent 应锚定“希望观众听到什么的事件点”，后端再根据资源的 onset / 偏移安排物理 Item。

### 结论边界

**[已实测]** Anchor / Follower Duck 的设置会进入 ChatCut 云端最终导出，并在本轮样本中产生与 `duckDepthDb` 一致的背景音乐下沉。  
**[已实测]** Whoosh 的 Timeline 范围与最终主要听感起点可以不同。  
**[未验证]** 这些设置在所有音乐、人声、设备和复杂混音下都“自然”“好听”；本轮做的是渲染/波形机制验证，不是审美听感验收，也没有测试音乐生成质量。

## 实验 13：陈旧 Script、原子批量写入与副本隔离

### 13.1 陈旧 Script 会被拒绝，而不是悄悄覆盖新状态

先读取当前 Script；随后故意通过 Timeline 操作改变同一条 Timeline；再把旧 Script 提交。结果被拒绝，错误明确指出 Timeline 已被其它工具或用户修改。重新 `read_script` 后，新的 Script 可以正常预览和提交，字幕刷新读回为 `canonical`。

**[已实测]** ChatCut 会阻止这轮测试中的陈旧 Script 覆盖较新的 Timeline。  
**[未验证]** 两个真实用户或两个真实 Agent 同时编辑时的自动合并、冲突提示细节和版本选择体验。

### 13.2 批量 Item 写入是原子的

向同一批 `edit_item` 同时提交一个合法的淡入更新和一个非法的同轨重叠移动。整批请求失败后重新读回：原本合法的淡入仍为 0，没有留下“半套成功”的状态。

**[已实测]** 本轮 `edit_item` 批次在此失败条件下整体回滚。  
**[不能扩大为]** 所有类型的写操作、网络中断或跨项目事务都已经逐一验证。

### 13.3 Timeline 副本与原线隔离

在 Timeline 副本中修改 A1 片段范围，再读取原 Timeline；原线保持原始 A1 范围。

**[已实测]** 本轮副本上的该项改动没有回写到原 Timeline。  
**[未验证]** Web UI 的完整版本历史、一键恢复、跨项目回滚或多人协作版本图。

## 实验 14：Web 手动上传后，外部 Codex 能否接手同一个项目（2026-08-31 复核）

### 目的

这不是验证“网页能不能上传文件”这么简单。要验证的是用户最常见、也最容易被产品说明含混的一条协作链：

~~~text
用户在 ChatCut Web 上传素材、在 Web Agent 中提出要求
→ 再把同一项目交给 Codex
→ Codex 能否准确定位项目、看见已上传 Asset、知道该改哪条 Timeline
→ 改动是否回到同一个 Web 编辑器
~~~

### 已有的合同事实

**[工具 / Skill 合同明确]** 当前外部 MCP 提供了 `list_projects → target_project → read_project → browse_assets` 这一条项目接手链：项目列表返回 `projectId`，`target_project` 将外部会话绑定到明确项目，`read_project` 返回轻量项目地图，`browse_assets` 返回项目素材库的 Asset 卡片。第 11 篇据此解释了：editor URL / `projectId` 是外部 Codex 定位项目的依据，不是 Web AI Panel 聊天或文件名猜测。

这条合同能证明“**若同一账号、同一项目可访问，Codex 有一条受控的读项目 / 读素材入口**”；不能单独证明“Web 上传后的每个 Asset 已被当前 Codex 实际读到”。后者必须看真实读回。

### 本次复核实际停在什么地方

2026-08-31 重新调用 `list_projects` 时，当前 ChatCut MCP 返回 `Auth required`。随后执行 `codex mcp login chatcut`，命令输出 `Successfully logged in to MCP server 'chatcut'`；但立即重试本会话的 `mcp__chatcut__list_projects`，仍返回 `Auth required`。另一次受控的内置浏览器尝试打开授权 URL 时得到连接被拒绝；本轮没有提交浏览器授权表单，也没有取得项目列表、绑定项目或读取用户刚在 Web 上传的任何 Asset。

这条观察的正确表述是：

- **[已实测]** 当前会话的 ChatCut MCP 请求仍没有可用的项目访问凭据；命令行登录显示成功，并没有使这个已运行会话立即恢复读项目能力；
- **[未验证]** “Web 手动上传 → 当前 Codex 会话读到同一 Asset → 写入回同一 Web 项目”的完整实时闭环；
- **[不能扩大为]** ChatCut 不支持 Web / Codex 接手、用户的 Web 上传已丢失，或 ChatCut 内部一定是何种鉴权/会话刷新机制。这里首先是当前连接器会话没有恢复可用访问，不是对 ChatCut 产品能力的否定。

### 恢复授权后，什么才算把这条实验真正测通

恢复后应只做一次最小、可复核的闭环，不再用“上传按钮看到了”代替证据：

1. 重新建立能读取项目的 Codex ChatCut 会话；若刚完成登录，先在新的会话中用 `list_projects` 确认授权真正生效；
2. 在 Web 创建或打开一个测试项目，手动上传一条有唯一文件名的视频；
3. 将该项目的 editor URL 交给 Codex，用 URL 中 `projectId` 调用 `target_project`；
4. 用 `read_project` 与 `browse_assets` 读回同一项目和这条 Asset 的名称、类型、时长、处理状态；
5. 对该 Asset 做一项低风险可读回操作（例如请求转写或放置一个可撤回 Item），再读回项目 / Timeline；
6. 在同一 Web 编辑器确认该状态可见；最后记录项目、Timeline、Asset 三个身份是否一致。

只有这六步都完成，才可以把“跨入口素材接手”从工具合同升级成 **[已实测]**。即使测通，它也仍不证明 Web AI Panel 的聊天、@ 引用、原生 Agent 计划会自动同步给 Codex。

## 对本篇记录的正确使用方式

可以用它回答“目前我们真的看到了什么”；不能用它把每个 Skill 的理想流程都包装成“已验证的产品功能”。后续测试必须沿用本篇的证据链，而不是只记录一次工具调用的成功文本。
