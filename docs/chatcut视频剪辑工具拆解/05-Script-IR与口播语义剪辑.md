# 05｜Script IR 与口播语义剪辑

> 本篇定位：解释 Script 怎样成为“语义剪辑层”和“帧级执行层”之间的编译边界。工具合同和实机读回只用于验证这些职责；具体操作、帧位和字段样例集中在第 08 篇，编译器的私有算法不作源码式猜测。

## 一句话定义

**Script 是“观众最终会听到什么”的可编辑稿；Timeline 是“渲染器在第几帧播放哪一段媒体”的确定性结果。**

这是 ChatCut 处理口播和访谈的关键设计：让模型/Agent 擅长的“理解内容”与程序擅长的“维护帧、片段、轨道一致性”分开。

```mermaid
flowchart LR
    A[源视频的 ASR 段和时间锚点] --> B[read_script]
    B --> C[可阅读、可编辑的 Script]
    C --> D[Agent 判断完整观点
删、留、重排]
    D --> E[apply_script]
    E --> F[程序将选择编译为
Item、源范围、整数帧]
    F --> G[新的可播放 Timeline]
```

## 为什么不能让 Agent 持续手工算帧

假设一段口播的自动转写被拆成四行：

```text
大家好，今天想和你聊一个……
很多人剪短视频时都会忽略的问题。
这个问题就是开头太长。
所以我们先把结论讲出来。
```

第一行单独留下像残句，第二行单独留下又失去主语。人听到的是前两行合在一起的完整表达，而不是 ASR 服务恰好切出的行。

如果 Agent 每次都直接操作底层时间线，它需要同时做到：

```text
找出正确语义边界
→ 在对应帧切开视频和音频
→ 删除某段
→ 移动之后的所有片段
→ 维护源素材偏移
→ 避免切到词中间
→ 检查字幕、声音、B-roll、MG 动画是否失准
```

这既不是模型最擅长的工作，也很容易因为前一次修改改变坐标而在后一次写错位置。

## Script、转写、字幕：三者不是同一件事

| 对象 | 它回答什么 | 出错后怎样修 |
| --- | --- | --- |
| 源转写（ASR Transcript） | 原片里实际识别到了什么词，以及这些词在源素材什么时间 | 识别错了，用转写修正。 |
| Script | 最终版本要让观众听到哪些原有表达、按什么顺序 | 删、留、重排完整表达，然后 `apply_script`。 |
| 字幕 Card | 屏幕上显示怎样的一段字、何时出现、怎样换行和强调 | 改 Card 文案、样式、布局或 Token 时间。 |

例如：ASR 把“陈清泉”听成别的名字，应该先修转写；如果原话正确，只是希望屏幕上将一句长话压缩为更短的可读字幕，可以改 Card 文本；如果希望结论提前出现，应该在 Script 中重排保留的原始表达。

## `read_script`：把可听内容变成可讨论的编辑稿

`read_script` 的目的不是生成一篇与视频脱钩的新文章，而是让 Agent 看到“当前版本观众将听到什么”，同时保留回到源素材的锚点。

在底层文本中会出现类似 `[sN]` 的标记。它们是 ASR 分段引用，**不是一个个天然的剪辑单元**。对用户解释剪辑决定时，不应说“删了 `[s12]`”，而应说“删掉了重复的开场尝试，保留后面更完整的说法”。

## `clean_script`：只做低歧义的机械清理

它适合：

- 明显无意义的 `um / uh / er / ah / 呃 / 额`；
- 用户要求压缩或恢复已有的长停顿。

它不适合：

- “然后、所以、那个、嗯、啊”等依赖上下文的词；
- 判断哪次重拍更自然；
- 判断两个相似句子是不是刻意强调；
- 修复 ASR 听错；
- 代替人工做观点重排。

机械清理后必须重新读取 Script，因为当前可听内容和可用锚点已经变化。继续在旧版本文本上做大规模语义编辑，相当于依据过期地图写入时间线。

### 官方补充：清理、做版本和声音收尾的顺序

官方口播 Skill 将流程说得更具体：

```text
读当前 Script
→ （需要时）只清理低歧义口癖 / 长停顿
→ 重新读已更新的 Script
→ 再做“保留哪段话、怎样重排”的语义判断
→ apply_script
→ 重新阅读结果，检查听感与逻辑
→ 结构稳定后 smooth_audio
```

做“30 秒高光”“换一个 Hook”“另一版节目”时，也不建议从 `find_transcript` 找到时间戳后手工 split/move 一堆视频 Item。官方方法是先复制 Timeline，再用 Script 保留、删除、重排需要的完整表达。这样 Agent 始终在“观众会听到什么”的表面工作，帧和源偏移仍由后端处理。

`smooth_audio` 的职责是给硬音频切口加很短的交叉淡化，减少爆音；它应在 `apply_script` 或其它结构重排之后执行。字幕开启时，则应在一整批 Script / 转写修改完成后刷新一次，而不是每改一个词就刷新一次。

数字人口播的实际预检还补充了一个边界：如果每个硬切片段都已经用满源素材，系统没有多余声音可拿来重叠，声音平滑会退化为很短的淡出再淡入，而不是凭空制造交叉淡化。它能减少切口爆音，但仍必须靠听感审片判断是否自然。

## Agent 在 Script 上到底做什么

Agent 应编辑“完整语义单元”，而不是机械保留/删除一行 ASR：

- 从重拍中选一段完整、自然、逻辑不断裂的说法；
- 删掉失败起句、无意义停顿、被后文完全覆盖的重复；
- 保留理解一句话必需的主语、转折、条件或结论；
- 做短版时，保留可以脱离原片独立理解的片段；
- 重构时移动完整观点、完整回答或完整步骤，不把一句话前后两半拆到不同位置。

### 一个大白话示例

原片顺序：

```text
先解释背景
→ 说“很多人会犯一个错误”
→ 又绕了一圈重复解释
→ 最后才说结论“先删到只剩一个明确观点”
```

用户要“直接讲结论的 15 秒短版”。规划应是：

```text
先播结论
→ 再补一句“很多人会犯这个错误”的必要背景
→ 删除重复绕圈
```

它不是让 Agent 写一段新的配音，也不是让 Agent 说“第 12.34 秒删到第 19.16 秒”。`apply_script` 将这份内容顺序转换成具体的源片段与时间线 Item。

## `apply_script`：程序接管帧级写入

当前工具合同明确：`apply_script` 会比对编辑后的 Script 与实时状态，原子提交核心 Timeline 变更；核心行有错误时整次应用回滚，不留下半套切口。

它可被理解为一个“语义剪辑编译器”。从工具合同和提交后的读回，可以确认它承担以下类别的工作：

```text
验证 Script 锚点仍有效
→ 根据保留/删除/重排决定解析源范围
→ 将边界转换为时间线整数帧
→ 创建或调整连续的视频/音频 Item
→ 保存源偏移、时长、轨道位置
→ 检查核心时间线约束
→ 一次性提交或整体回滚
```

上面是职责级的实现推断，不是 ChatCut 公开的具体函数流程。真正关键的分工是：

| 谁 | 负责什么 |
| --- | --- |
| 编辑 Agent | 这句话是否完整、这次重拍选哪版、观点顺序是否更好、删了是否会误导。 |
| ChatCut 后端程序 | 帧换算、Item 拆分/拼接、源偏移、同轨连续性、原子提交和读回。 |
| 用户/审片者 | 判断听起来是否自然、逻辑是否成立、内容是否符合意图。 |

## 编译器在主线重排时维护什么

要看清 Script 的作用，可以把一条较复杂的 Timeline 想成：V1 是主口播，V2 有画中画，A1 有短促音效，同时还存在片段绑定与绝对时间效果。此时删掉 Script 中的一句完整表达，系统必须区分“重新编译主线”与“让所有对象一起移动”这两件完全不同的事。

Agent 的提交只表达：某个来源语义行不再保留；它不应提供“从第几帧删到第几帧”，也不需要计算所有后续 Item 的新起点。提交前可用：

~~~text
apply_script({ timelineMd, preview: true })
~~~

预览应该先给出语义层面的差异：V1 少了哪一个来源语义、主线将如何重排、哪些独立轨道仍保留。正式提交后的读回应给出帧级结果：

| 对象 | Script 提交后应如何理解 |
| --- | --- |
| V1 主口播 | 后端重新选择源范围、重排 Item 并计算新的成片帧；Item ID 可以被重新生成。 |
| 字幕 | 被删语义对应的 Card 应消失，保留语义应回到新的播放时间；结构稳定后刷新到当前 Timeline。 |
| V2 画中画 | 它是独立绝对时间 Item，不应因为 V1 少一句话而隐式左移。 |
| A1 Ding | 它保留自己的物理范围，不会自动改成“服务新的语义”。 |
| 绝对时间 Zoom | 它记住的是时间尺范围，应保持原位直到明确重锚。 |
| 片段绑定 Zoom | 只有明确附着到保留 V1 Item 的效果，才可能随该片段延续。 |

用大白话说：**Agent 只回答“观众不要再听到这句话”；ChatCut 把这个选择翻译成新的 V1 片段、源偏移和整数帧。** 但画中画、Ding、绝对时间效果不是“这句话”的孩子，它们只是同一根时间尺上的独立对象，所以不会替 Agent 猜它们应该跟到哪里。

### 这也解释了“删一句”和“删一帧”为什么不能混用

在同一批受控素材中，还做了物理删 1 帧的对照。开启 `ripple:true` 后，后半段 V1 被后端从第 181 帧推到第 180 帧，片长缩短 1 帧，云端第 180 帧没有黑画面；这证明同轨的帧重算确实由后端完成。

但词级字幕读回同时显示：原来 `[174,180)` 的“我”之后，又出现一个仅 `[180,181)` 的“我”，再从 181 帧继续“最近……”。程序做的是严格的时间投影，并不会知道“这一帧恰好切在一个汉字发音中间不自然”。

因此不能把 `apply_script` 理解成“模型完全不用审片”的魔法，也不能把 `edit_item + ripple` 当成口播语义剪辑的替代品：

```text
删完整句、重拍、口癖、完整观点：优先 Script。
已知需要精确改 1 帧、一个固定时长或一个画面边界：才用 Timeline 物理操作。
不管走哪种入口：结构变更后都要检查字幕、独立音画包装和实际听感。
```

## 跨 Asset 口播如何形成一条新的节目主线

数字人口播很容易让人误会成“把许多小文件丢给模型，模型一次就懂它们是一篇文章”。更准确的架构是：每段仍是独立 Asset；只有在 Timeline 中建立原始顺序、在 Script 中读取可播放语义后，Agent 才能组织一条新的节目主线。

输入是 18 段独立视频：每段约 10.125 秒、768×1344、24 fps，合计约 182 秒。它们都完成了转写，但在素材库里仍是 18 个独立 Asset，并不会自动被声明为“这一篇口播的 18 个章节”。

实际链路是：

~~~text
18 个独立 Asset
→ 按原始叙述顺序排入 V1，形成约 3 分 02 秒的长主线
→ read_script 读出 18 个来源区块、59 个可选择的语义段
→ Agent 判断哪些完整观点组成短版
→ apply_script 一次性重排
→ 得到新的可编辑 V1
~~~

本次保留并重排的来源顺序为：

~~~text
01 → 02 → 05 → 09 → 13 → 15 → 16 → 18
~~~

叙事上对应“提问 Hook → 书与核心问题 → 意义靠选择做出来 → 日常感受的价值 → 个人结论 → 收束”。提交后，结果从 18 段、约 182 秒变成 8 段、81 秒；读回仍是 24 fps，8 个保留片段均指向原素材的完整源范围。

这个例子说明了三件很关键的事：

1. **Agent 做的是内容编排。** 它决定哪几个观点值得保留、什么顺序更顺，而不是反复计算每个文件从第几帧开始。
2. **后端做的是时间线编译。** 它把跨 Asset 的选择变成新的 V1 Item 顺序、持续时间和源素材引用。
3. **语义短版不等于自动包装完成。** 合成帧显示 8 段之间是硬切；数字人的手势、镜头距离和姿态可能在切点处跳变。ChatCut 没有因为“语义重排成功”就自动补 B-roll、MG 动画、Zoom 或转场。

因此，对数字人口播更准确的理解是：

> Script 能把多段已转写素材组织成“观众该听到什么”的新主线；它不替编辑 Agent 决定“这一刀该用什么画面或运镜遮住”。

这里讨论的是语义骨架的编排边界，不等于已经完成 MG、Zoom、B-roll、转场、背景音乐或音效等包装层。它们必须在主线稳定后，通过各自的锚定模型再进入 Timeline。

## Script 不是万能遥控器

Script 负责的是“主语音内容结构”，不是所有时间线对象：

| 任务 | 应放在哪一层 |
| --- | --- |
| 去重复、删错误重拍、前置结论、按主题重排 | Script |
| 加 B-roll、图表、MG 动画、转场、Zoom | Timeline 与对应效果工具 |
| 放 Ding、Whoosh、背景音乐、淡入淡出 | Timeline 音频 Item / 音轨设置 |
| 修 ASR 原词 | 转写修正 |
| 调字幕框、强调某个词、改字幕显示文案 | Caption Card |
| 消除切口爆音 | `smooth_audio` 或音频处理流程 |

这也是为什么说“先做语音剪辑，再做包装”：下游包装依赖最终的说话时间，先做会在后续重排时频繁失效。

## 版本、并发和失败处理

`apply_script` 不应对过期的 Script 盲写。本轮做过一次受控验证：先 `read_script`，再故意用 Timeline 操作修改同一条线，最后提交旧 Script；提交被拒绝，错误说明 Timeline 已被其它工具或用户修改。重新 `read_script` 后，新的 Script 可以正常预览和提交，字幕刷新读回为 `canonical`。

因此可以说：**[ChatCut 已实测]** 本轮陈旧 Script 不会静默覆盖后来发生的 Timeline 改动。正确恢复方式是：

```text
重新 read_script
→ 阅读当前版本的实际内容
→ 重新做编辑决定
→ 再 apply_script
```

不要把旧文本再次硬塞回去；那样可能将正确的语义选择写到已经变化的片段位置上。

同一轮还验证了两条相关的安全边界：

- 向一个 `edit_item` 批次同时放入“合法淡入”和“非法同轨重叠移动”时，整批失败，合法淡入也没有半提交；
- 在 Timeline 副本中改 A1 片段范围后，原 Timeline 的 A1 范围保持不变。

这说明本轮能看到“陈旧状态拒绝、批次原子失败、副本局部隔离”三种保护行为；**仍未验证**两个真实用户/Agent 的并发合并、Web UI 完整版本历史、一键恢复或跨项目回滚。不要把这三项局部证据扩大成完整协作系统已经测通。

## 深度拆解：Script 不是普通文本编辑器，而是一份有版本的“编译请求”

“Script IR”听起来很技术，换成大白话就是：

> 它不是让 Agent 写一篇新文章，而是让 Agent 在一张**能回到原片的播放清单**上，表达“这次观众要听到哪些原话、按什么顺序听”。

### 1. 一份 Script 快照在概念上要带哪些信息

当前 MCP 返回的精确字段以运行时 Schema 为准。为了理解工作机制，下面用的是**解释模型**，不是在声称 ChatCut 对外暴露或内部正好存了这些字段：

~~~text
ScriptSnapshot
├─ 基于哪一条 Timeline、哪一个当前版本读取
├─ 一组可播放语义单元
│  ├─ 来自哪个 Asset
│  ├─ 回到原片的时间/转写锚点
│  ├─ 原始内容与当前播放顺序
│  └─ 是否保留、是否被清理或重排
├─ 与空白、停顿、重复播放有关的上下文
└─ 足以拒绝陈旧写入的版本条件
~~~

其中最重要的是“回到原片的锚点”和“读取时的版本条件”：

- 没有源锚点，Script 就退化成一篇无法落实到视频的文字稿；
- 没有版本条件，用户或另一个工具刚改完 Timeline，旧 Script 仍可能把错误内容写进去；
- 没有完整语义单元，Agent 就容易按照 ASR 行号把主语、转折或句尾切碎。

本轮陈旧 Script 被拒绝，证明运行时存在某种新旧状态校验；**[未验证]** 其内部版本号、哈希或锁的具体形态，因此本文不把上面的概念图当成私有字段结构。

### 2. 从“删一句”到“可播放 Timeline”的编译过程

~~~mermaid
flowchart TD
    A[读取当前 Script 快照] --> B[Agent 判断完整观点
删、留、重排]
    B --> C[先预览编译结果]
    C --> D{当前 Timeline 仍是这个版本？}
    D -->|否| E[拒绝陈旧 Script
重新读取并重新判断]
    D -->|是| F[后端解析源锚点和顺序]
    F --> G[生成 / 替换主线 Item
源范围、轨道、整数帧]
    G --> H[一次性提交，或整体回滚]
    H --> I[读取新 Script、Timeline、字幕]
    I --> J[对独立包装做影响复核]
~~~

每一格不是由同一个人完成的：

| 阶段 | Agent / 用户决定什么 | ChatCut 后端决定或校验什么 | 为什么必须分开 |
| --- | --- | --- | --- |
| 读取 | 要做哪个版本、是否应先清理 | 返回当前可听内容与可回源锚点 | 不在旧记忆上直接编辑 |
| 语义选择 | 哪句完整、哪版重拍更好、顺序是否成立 | 无法替人判断价值与逻辑 | 这是创作判断 |
| 预览 | 是否接受预计删留与顺序 | 将语义选择尝试解释为可执行主线 | 先看“会发生什么”，避免盲写 |
| 提交 | 确认这一轮选择 | 版本新鲜、源范围合法、核心时间线约束、原子写入 | 程序适合做确定性安全检查 |
| 派生层复核 | 是否重锚 Ding、B-roll、MG、音乐 | 字幕映射/刷新和已建模效果的处理 | 独立对象没有理由时不会自动理解语义 |
| 审片 | 听感、口型、叙事是否自然 | 提供结构和可见/可听结果 | “可编译”不等于“剪得好” |

### 3. 一次完整语义删除到底改变了哪些状态

以已测的数字人口播“删去首句、保留后两句”为例，下面不是精确字段日志，而是把读回事实翻译成状态变化：

| 层 | 删除前 | Agent 表达的意图 | 后端提交后 | 还要谁检查 |
| --- | --- | --- | --- | --- |
| 源 Asset | 原片约 10.1 秒仍完整存在 | 不删除源文件 | 源素材完全保留 | 无 |
| Script | 三句按原顺序可播放 | 第一完整句不保留 | 新 Script 从“不是等答案出现”开始 | Agent 确认逻辑不断裂 |
| V1 Item | 一个 Item 覆盖原片完整范围 | 不提供“后面左移多少帧” | Item 改为从源片约 5.6 秒取到片尾，并从新 Timeline 第 0 帧播放 | 读回源范围、时长和首帧 |
| Caption | 与旧可播放语音对应 | 不直接逐张搬字幕 | 被删句 Card 消失，剩余 Card 在新帧位出现 | 检查阅读节奏、ASR、口型 |
| 独立包装 | 本受控线没有额外包装 | 无法从 Script 自动推断新位置 | 本实验不据此声称全自动重锚 | 若有 Ding/MG/B-roll，必须单独检查 |

这张表回答了“是不是 Codex 重新计算了所有帧”：**不是。** Agent 的提交是语义差异；ChatCut 后端读出源锚点并计算新的播放范围。Agent 需要做的是检查编译后的结果没有把“完整表达”误剪成“看起来文字连着、听起来却不自然”。

### 4. Script 编译时应保持的几个不变量

这些不是对 ChatCut 私有实现的源码断言，而是从工具合同、失败读回和可播放结果可以归纳出的外部约束：

| 不变量 | 人话解释 | 本轮依据 |
| --- | --- | --- |
| 写入基于最新版本 | 不能把昨天读到的 Script 直接覆盖今天已改的 Timeline | 陈旧 Script 被拒绝 |
| 源引用必须仍有效 | 每个保留句必须还能找到实际 Asset 和源时间 | Script 必须能被编译为真实 Item |
| 主线必须可播放 | 不能产生非法源范围或同轨无法解释的核心结构 | 提交后可读回连续 V1 |
| 一批核心变更要么全成功、要么不写 | 不能留下“删了一半、字幕/Item 只写了一部分” | 非法批量 Item 编辑没有半提交；Script 合同也描述原子提交 |
| 下游不能被假装已修好 | Script 只保证主线语义编译，不等于每个独立包装仍正确 | V2/A1/绝对时间 Zoom 的隔离实验 |

其中最后一条尤其重要：Script 是降低帧级错误的工具，不是把所有创意与声音问题自动消失的黑盒。

### 5. 五类常见失败及恢复路径

| 失败或风险 | 它真正意味着什么 | 正确恢复 | 不该做什么 |
| --- | --- | --- | --- |
| 陈旧 Script 被拒绝 | Timeline 在读取后已经变化 | 重新读当前 Script，重新判断语义，再预览/提交 | 把旧文本强行重试 |
| ASR 词错了 | 源锚点的文字事实不可靠 | 修转写，再重新读取相关 Script / 字幕 | 只改屏幕字幕然后继续按错词检索 |
| 预览结果不符合预期 | 语义选择或源锚点理解有误 | 不提交，回到候选句和源窗口核对 | 用低层 split 连续补丁掩盖问题 |
| 编译成功但切口不自然 | 物理上可播放，不代表声音/口型自然 | 审听、换完整边界、保留呼吸或用画面覆盖 | 把 success 当作听感验收 |
| 主线重排后包装错位 | 独立对象仍占旧绝对帧或旧画面 | 生成影响清单，逐项重锚或明确保留 | 假定所有轨道会像 V1 一样自动移动 |

### 6. 对外看见的是 MCP，真正发生的是“语义 → 确定性”的边界交接

可以用下面一句话记住 Script 的职责：

~~~text
Agent 负责：“这句应不应该让观众听到？”
ChatCut 编译器负责：“如果应当听到，它在源片哪一段、最终第几帧播放？”
字幕与包装层负责：“观众如何看到、听到、被强调到这件事？”
用户负责：“这条成片是否真的符合我要表达的意思？”
~~~

第 04 篇解释主线改变后其它轨怎样分类；第 06 篇则把字幕、音效、音乐和 MG 的不同锚定模型展开。

## 小结

Script IR 的价值不是“更技术”，而是让人和模型专注于内容，让程序专注于坐标。它把“这句话该不该保留”与“第几帧怎么切”解耦，既能减少模型算帧错误，也能让后续字幕、声音和画面包装建立在稳定的语义骨架上。
