# Skillry 连续动效批量采集与拆解：Codex 执行任务

## 任务目标

我想学习的是：优秀动画怎样把一个状态连续地推进到下一个状态，而不是收集好看的封面、照抄提示词，或给现有视频换配色。

请在本机建立一个独立的研究目录，先完成“获取连续画面 → 验证画面质量 → 基于时间证据拆解 → 提炼可迁移方法”。不要修改 VideoFlowCut 的源码、现有 Skills、配置或正式视频工程，不提交 Git。本任务也不要求制作成片或立刻接入生产链。

输入网站：
```text
https://skillry.dev/ai-videos/opus-5-5
```

公开索引：
```text
https://github.com/yihui-dev/awesome-opus5-5-videos
```

从仓库的 `data/videos.json` 读取候选页面、作者、原帖和提示词信息。已检查的条目包含 `slug`、`author`、`post_url`、`category`、`prompt`、`prompt_partial`、`poster_url`、`skillry_url` 等字段。不要假定这些字段就是视频下载地址，不要把 `.webp` 封面改后缀猜测 MP4。以本次实际读取的字段为准，并保留索引版本。

## 当前已知与未验证状态

2026-10-08 的网页及公开仓库核查能确认：网站区分 Original 与 Remake，公开索引能提供条目和来源。

本文件不是已跑通的下载脚本，也不是已经完成的视频分析报告。聊天侧未获取到视频文件；执行环境连接该站下载失败。因此必须由本机实际验证播放器、媒体获取和分析工具的能力，不能写成“已确认全站可批量下载”。

## 一、先验证三条，不要上来全站抓取

先挑选三条候选，优先考虑有多个连续状态的 UI、物体变形或解释类动效，避免三条都是同一表现手法。第一次选取只是候选，不是质量排名；看过画面后再决定是否值得分析。

检查本机现有浏览器自动化、媒体处理和图像查看能力。优先复用已有工具。需要安装新依赖时，遵循本机授权和项目约定，不更换现有环境。不能仅因能读文件、运行 ffmpeg，就宣称模型已经看过视频。

对每个候选，先识别要分析的是 Original 还是 Remake。两者分别保存，禁止混用原作提示词为复刻效果背书。首页缩略预览也不能自动等同于详情页完整版本。

### 路径 A：优先获取实际播放器使用的媒体

使用已获授权的浏览器自动化打开详情页，定位目标播放器，触发播放和必要的懒加载，再检查：

- 对应 `<video>` 的 `currentSrc`、`src` 和 `<source>`。
- 播放触发的真实网络请求与响应类型；不要只按 URL 是否以 `.mp4` 结尾筛选。
- iframe 内的播放器，以及播放器属于 Original 还是 Remake。

普通公开 MP4/WebM 可尝试下载。遇到分段媒体，先判断是否为未加密且允许获取的媒体流；不能把单一分片或一个 `blob:` 字符串直接当作完整视频下载。不要绕过 DRM、付费、登录权限或验证码；遇到明确访问限制则记录并停止该条。不要导出用户 Cookie 或凭据到报告。

下载成功后，验证实际可解码、时长、分辨率和首中尾画面，确认不是网页错误内容、封面、空文件或截断片段。保存来源和校验信息，避免重复采集。

### 路径 B：文件获取失败，但普通预览可正常播放

在授权和站点允许的范围内，尝试用浏览器自动化录制目标播放器。不是要求用户逐条手工录屏。

录制时尽量让目标播放器单独显示，移开鼠标，避免控件、通知和其他视频干扰。核对从哪里开始、在哪里结束、是否缓冲、是否循环重复，以及声音是否实际保留。先录制并验证单条，再重复操作；不要同时播放大量视频。

必须标记为“预览录制件”，而不是原片。输出文件标称 60fps 不证明原始运动被完整保留；录屏可能存在重复帧、漏帧、缩放或声音缺失。质量不足时，只用于判断可见的状态变化和大致接续，不能据此认证精确缓动曲线、逐帧速度或原片流畅度。

若播放器支持可靠定位，也可以取得按媒体时间排列的密集画面。需要等待目标帧实际呈现，记录请求时间与可验证的实际媒体时间；不能简单每隔一段墙钟时间截图，就声称是精确视频采样。

对于 HTML/Canvas 动画，不假定存在 MP4 或 `seek(t)`。检查实际播放和时间控制能力；没有可靠时间轴时以实测录制为准，并保留时间误差说明。

### 路径 C：没有可用连续证据

保存获取失败原因和已取得的来源资料，标记“未完成连续过程分析”。若有作者官方允许获取的版本，可继续尝试该来源。不能根据封面、标题、作者提示词或复刻想象补写已观察到的过程。

三条验证中出现可复用的成功路径后，再按同一方法将本批扩展到最多十条。采用低并发、去重、断点记录；遇到限流按服务要求退避，不反复冲击。十条只是本批建议规模，不是动画时长或生产约束。

## 二、将连续画面转成模型真正能检查的证据

下载文件不等于完成视频理解。先确认当前工具如何把视觉输入交给模型：可用的视频理解工具，或确实支持查看的图片序列。只返回文件路径、媒体元数据、转写文本或工具“完成”状态，都不算模型已经检查运动过程。

先进行整体浏览，定位有价值的变化区间，再对这些区间加密观察。不要只按镜头切点分析：连续变形可能没有硬切，而主要设计恰好发生在状态之间。

建议采用以下初始观察尺度，而不是统一硬指标：

- 全片低密度概览：约每秒 1–2 帧，仅用于定位布局、状态和候选区间，不据此认证快速运动。
- 局部变化：保留变化前后的上下文，先按每秒约 10–15 帧提取实际画面。
- 对文字交叠、遮挡、回弹、短促接力等仍不明确的过程，回到源帧和实际时间戳继续检查；需要时逐帧检查。

原文件及原时间轴保持不变。不要插帧“补出证据”。不把整片几千张图一次塞进上下文；按连续事件分组，小批查看，保留相邻组的重叠上下文。每张图保留实际媒体时间，便于回看；关键证据应能单独放大，不仅存在于小缩略图拼图里。

可另做慢放片帮助观察轨迹，但慢放不增加原始信息，所有报告时间要换回源时间。原速主要检查节奏，密集画面主要检查轨迹和动作交叠。只有图片证据时，要明确没有验证原速播放体验。

使用视频模型也必须核对实际采样配置；不能假定上传 MP4 就意味着模型逐帧看过。没有音频证据时，不评价音乐拍点、音效峰值与运动的准确同步。

## 三、每个连续过程应该怎样拆解

为每个有价值的片段写一段可以回看核对的分析，而不是堆术语。

首先明确：这个片段让观众看懂了什么？跟随的是哪个主体、文字、边缘、窗口或运动方向？随后按可见过程说明上一状态如何给下一状态创造条件。

重点检查：

1. **什么保持连续**：同一可见主体、轮廓、颜色、位置、运动方向、视线锚点，还是遮挡后的视觉接续？视觉看起来是同一物体，不证明源码使用同一 DOM 对象。
2. **什么实际发生变化**：尺寸、形状、位置、内部内容、遮挡关系、观察尺度或前后景关系怎样变化？不要只写“丝滑变形”。
3. **动作如何交叠**：谁先启动，谁尚未结束，下一状态何时开始可读？前一动作的收势有没有被下一动作接住？
4. **注意力怎样交接**：旧重点何时退让，新重点怎样接管？阅读时刻是否停稳？持续运动不等于持续有效。
5. **为什么适合当前内容**：设计是在表达数量、因果、选择、放大观察或层级关系，还是只是装饰？
6. **怎样迁移而不套壳**：换成其他主题或真实素材时，需要保留什么关系，重新设计什么内容，哪些场景不适用？

每条关键判断都附源时间范围和至少一组能看到中间过程的证据。每个报告清楚分开：直接观察、设计解释、实现猜测。无源码时，不断言作者使用了哪条贝塞尔曲线、某个弹簧参数或特定 Remotion API。

以下仅演示报告写法，不是本次已观察到的作品：

> 卡片还未完全停稳时，右边缘已经继续向外伸展；旧文字先降低显著度，新文字在扩出的空间中建立。观众无需重新寻找主体，因为卡片的左侧位置保持稳定。可迁移的方法是“保留一个空间锚点，让下一状态从现有对象内部展开”，而不是“给新页面增加淡入转场”。

## 四、保存结果，不要立刻改现有 Skills

使用简洁的本地研究目录，例如：

```text
motion-study/
  manifest.json
  cases/
    <条目slug>-original/
      source.json
      media/                 # 实际取得的源文件或明确标注的录制件
      evidence/              # 带时间记录的过程画面与必要片段
      analysis.md
  continuous-design-patterns.md
  acquisition-report.md
```

这是建议的新研究目录，不是 VideoFlowCut 现有目录结构。未获取到的文件不要创建空壳冒充完成。

`source.json` 只需保存作者、页面、原帖、Original/Remake、获取方式、实际本地文件、取得时间、覆盖范围、质量限制和提示词来源状态等必要信息。原始媒体不要随意上传公开仓库。

`analysis.md` 保存单条真实观察。`continuous-design-patterns.md` 将多个案例中同一种机制归纳在一起，并链接回各案例的时间证据；只有一个案例支持的方法标为单例，不包装成普遍规律。不要把“缩放、平移、淡入、弹簧”几个技术词当成方法总结。

`acquisition-report.md` 说明每条究竟取得了原视频、预览录制件、带时间画面，还是只有文本；哪些条目确实被模型查看，哪些判断仍未验证。

先交付这批研究结果。后续是否提升为正式案例 Skill、如何复现和接入 VideoFlowCut，另行确认；本次不要擅自覆盖旧案例。

## 五、验收标准

本轮成功不以“抓到多少 URL”为准，而以是否交出了可回看核对的连续过程分析为准。

至少应明确展示一个案例：取得了什么画面 → 检查了哪些时间区间 → 中间变化是什么 → 为什么形成连续感 → 哪个设计方法可迁移。获取失败时交付真实诊断，不用文本推测填满报告。
