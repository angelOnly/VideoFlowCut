日期：2026-10-14

状态：已完成 Bridge 代码、字幕技能更新、开发验证和正式服务部署；原视频字幕恢复尚未执行。实现与部署结果见文末。

## 1. 本次只解决两个问题

| 问题 | 解决办法 |
| --- | --- |
| 识别已经返回文字和时间，字幕却生成失败 | 修正 Bridge 的文字比较规则，使大小写等格式差异不会被误判为内容缺失 |
| 字幕出现 `deepsick` 等错字 | 使用已有纠错接口，落实生成后的逐段校订，正确显示为 `DeepSeek` |

完整流程是：**实际配音 → 生成带时间的字幕 → 必要分屏 → 逐段校订 → 真实预览检查。**

本次改动集中在 Bridge 接入层、对应测试和字幕操作流程。原方案中的诊断系统建设、主程序代码整理等已移出实施范围，见第 7 节。

## 2. 为什么之前正常，这次却失败

### 已确认的原因

原错误为：

```text
FunASR 全文与字幕段文本不一致；拒绝猜测补齐
```

FunASR 返回的全文经过标点模型，其中的 `capitalize()` 会调整英文大小写；带时间的字幕段则来自原始识别文字。Bridge 的 `_alignment_content()` 比较时忽略空白和标点，却保留大小写，因此把两份实际内容相同的文字判成了不同。

主程序已有的比较规则包含 NFKC（统一全半角等形式）和小写处理。问题出在 Bridge 与主程序的规则不一致。

调用链中的失败位置是：

```text
实际配音 → FunASR 全文与带时间字幕段
         → Bridge _provider_caption_segments()
         → _alignment_content() 比较失败
         → 字幕 Job 失败，尚未进入画面渲染
```

### 复现与成功对照

用本片约 328.133 秒完整配音在独立 CPU 进程复现，得到 183 段、2054 个带时间词元。两份文字只存在四处大小写差异：

| 全文 | 字幕段 |
| --- | --- |
| Deepsick | deepsick |
| Ai | AI |
| Critical | critical |
| Open | open |

在进程内统一比较规则后，现有解析和词元检查通过，所有原始词元时间戳不变，结果为 `tokenEvidence=verified`、`tokenPrecision=provider_token_timed`。这证明失败并非因为没有时间数据；其中的错误拼写仍需单独校订。

同日较早的机票视频使用同一 v4 工作流成功生成 27 段字幕。本片部分短片段也能成功，另一些仍失败；调查时相关 FunASR 文件与发行包一致。

这些证据支持：**既有比较缺陷被这次内容触发。** 没有依据认定整个新版字幕功能失效，切短音频也不能根治。

此前复现只留下工具输出摘要，完整识别返回没有落盘。实施时重新采集测试样本，注明输入音频哈希和环境；不能将新样本当作原失败 Run 的历史原始数据。

另外，制作会话后来按“继续剪辑，先不修”的指令隐藏了 10 张过长整段字幕，因此后续预览没有字幕还包含这一操作。恢复时需检查隐藏状态与替换关系。

## 3. 生成失败：具体怎么修

**核心修改是一处 Bridge 比较函数。**

定位文件：`E:/ai/comfyui/ComfyUI-aki-v2/ComfyUI/custom_nodes/Comfyui-AppApi/local_voice_nodes.py`。

该路径是运行副本的位置；开发在独立候选副本进行，通过验证后再按既有流程部署。

实施内容：

1. 修改 `_alignment_content()`，与主程序现有顺序一致：NFKC → 忽略约定空白与标点 → 统一小写 → 比较。
2. 核对全文、字幕段及词元比较是否均经过该函数；相关调用统一使用它，不改原始文字、显示文字或时间。
3. 保留现有真实缺字、重复、覆盖及时间检查。合法段级输出原本没有完整词元证据的情况，也沿现有规则处理。
4. 补回归样本，覆盖本次大小写差异、全半角与空白，以及真正内容不同、时间损坏的情况。Python 的空白和大小写行为要用样例与现有 TypeScript 规则核对，不能直接假设所有 Unicode 行为相同。

删除范围仅为该函数内不一致的比较逻辑；保留 v4 输出结构和现有验证。无需修改 FunASR 模型，也无需抽取三处 TypeScript 公共模块。

比较结果只用于对齐一致性。既有规则忽略标点，可能使 `3.1` 与 `31` 得到相同比较结果，因此数字、单位与符号仍需按原文校订，不能用技术比较代替内容核对。

## 4. 错别字：使用现有能力完成校订

### 如何处理 DeepSeek

大小写修复只让 `Deepsick/deepsick` 通过一致性检查，不会把它变成正确的 `DeepSeek`。

已有 `edit_captions` 支持修改显示文字并记录依据，本次复用它：

- `text`：写入整张字幕卡的纠正后全文，专名使用 `DeepSeek`。
- `sourceText`：保留原识别文字。
- `source_text_review`：记录真实纠正依据。
- 起止时间、对齐引用、词元范围和源音频保持不变。

不把错误拼写加入技术判等白名单，也不直接用整篇原稿覆盖所有字幕。

### 谁来校订，按什么依据

字幕作者逐卡核对，制作主任务通过正式接口提交并读回。重点检查专名、英文缩写、数字、日期、单位、否定和条件；未修改的卡也需要核对。

| 已有依据 | 使用条件与必要信息 |
| --- | --- |
| `confirmed_script` | 对照实际使用的配音稿；记录 `note`、`scriptRevision`、与该卡时间相交的 `speechSegmentIds` |
| `user_instruction` | 用户明确纠正；记录 `note`、`instruction`、`source`。本片 DeepSeek 可使用这一依据 |
| `listening` | 确实回听对应声音；记录 `note`，不能凭稿件假称听过 |

原稿匹配要结合字幕时间和上下文，片段 ID 精确对应此卡，不能填入全片所有片段。现有接口继续负责检查依据和版本。

如果只是识别错字，改显示；如果实际声音读错或漏读，回配音处理并重新对齐受影响范围。存在歧义时局部回听，不猜。

### 操作顺序和失败处理

先完成必要分屏，再校订；每次正式写入使用最新 Revision，提交后读回。版本冲突时核对实际差异，不能只替换版本号重提。

已有校订后若还需重分屏，沿现有保护处理：保留旧卡纠正对照，明确范围后重建，再逐卡核对。不能按卡片下标搬移记录，也不能静默覆盖人工修改。

纠错后检查真实预览中的拼写、换行与同步。原稿校订和实际回听分别记录；有纠错记录不代表整片已核对完成。

## 6. 验证、部署与视频恢复

### 必须验证的结果

| 验证 | 通过条件 |
| --- | --- |
| 本次完整配音的固定复现样本 | 旧解析能重现失败，修正后通过；样本原始时间戳不变 |
| 较早成功的机票配音 | 原成功路径继续可用 |
| 真实内容差异与损坏时间 | 仍按现有规则拒绝或明确证据不可用，不能伪装成完整验证通过 |
| DeepSeek 显示纠错 | 文字正确，来源、时间和音频不变，依据可读回 |
| 无依据或版本不匹配的编辑 | 继续由现有校验拦截 |
| 完整配音生成、校订后的真实预览 | 字幕覆盖完整，拼写、换行和同步正常，无旧字幕重复或隐藏残留 |

固定样本可以核对 183 段、2054 个词元；模型重跑可能有差异，不能只凭数量一致验收。

### 实施顺序

1. 在独立候选副本修 Bridge，保存复现样本，跑对应回归；不热改生产目录。
2. 在隔离项目、端口和队列中，用完整音频走通生成、已有接口纠错和预览；字幕技能补充随之验证。
3. 按既有安装流程部署通过验证的 Bridge，保留备份并避免无关依赖升级；技能沿现有同步发行流程更新。不为本次新增诊断或健康接口。
4. 用既有健康检查及真实调用确认服务加载修复。Bridge 修复需要单独部署，更新 VideoCut 插件不会自动修改它；也无需因此改造或强制重发未变更的主程序业务代码。
5. 由制作会话重新连接，读回最新项目和字幕状态，沿既有工单与恢复接口继续原视频。已失败 Job 保留，不手改成功；结果未知时对账原 Job/Run，不换键重放。

本次实际代价是一次 Bridge 修复部署、完整音频验证及逐段校订时间。新失败沿现有 Job、Run 和服务日志定位，不新增诊断存储系统。

完成判定分开报告：代码与测试通过、部署验证通过、该视频字幕生成并校订完成。正式导出的黑帧问题仍是独立事项，字幕恢复不等于整片已交付。
