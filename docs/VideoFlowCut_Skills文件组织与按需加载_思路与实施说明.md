# VideoFlowCut：技能文件组织与按需加载——思路与实施

**目标：从原项目的完整知识出发，删去未认可的业务范例，让工作入口、专业方法、执行细节与已认可案例各归其位。**

先读第一部分，理解为什么这样组织、哪些内容要保留、怎样避免再次丢失知识；再读第二部分，查看全部技能的文件去向、完整案例迁移、按需读取方式和工程验收。两部分构成同一份实施说明，不需要再拼接其他方案。

**文档状态：** 本文是组织设计与实施说明，不是已经迁移完成的Skills包。本次仅整理文档，沿用第二部分所列的核对基线与资料依据，不表示仓库或已安装插件已被修改。

## 第一部分｜整体判断与设计思路

这一部分先解释为什么要这样整理，再说明各项选择之间的关系。后面的文件树、拆分位置和验收要求，都是这些判断的落实，不是另一套方案。

### 一、这次要做的是知识重组，不是把长文改写成摘要

**整理应当从原项目的完整文件开始，而不是继续在已经删减过的阅读稿上补内容。**

原来的文件长、混乱，并不意味着其中的内容都没有价值。美术推导、动作设计、材料反馈、裁切公式、源时间和错误处理，分别解决不同问题。问题在于它们经常交错出现在同一个入口里，作者需要先穿过大量无关内容，才能找到当前要用的方法。

如果把这些内容统一压成“视觉要有主次、动画要保持连续、实现要符合接口”，文字确实短了，但具体做法也消失了。那不是结构优化，而是把执行知识改成结果要求。

因此，这次应当坚持：

> **让角色少读不相关的内容，不是让项目少拥有专业知识。**

“短入口”与“完整知识”并不矛盾。入口说明当前工作怎样开始、有哪些关键决定、遇到哪种问题去哪里；专业方法和执行参考保留完整的推导、公式、边界及返修办法。需要这些内容时，作者能够直接找到，而不是重新猜一遍。

这里也不要求把所有原文原封不动恢复。重复内容可以合并，过时说明需要核对，用户明确不认可的业务教学应当删除。**区别在于，每一项处理都有理由和去向，而不是因为一段文字长就概括掉。** 原长文件中的不同内容及其拆分依据，见第二部分第1、5、10章。[S3][S11][S12]

### 二、先分清“技能被发现”和“案例全文被读取”

在本说明采用的项目核对基线中，根目录有42个技能入口：13个具体案例，以及包含案例检索入口在内的29个工作技能。这是目录结构的事实，不是一次任务的实际读取量。[S1]

Codex通常先发现技能名称、描述和路径，再在选中后读取完整正文。所以，目录中存在十几个案例，并不能直接证明它们的全部内容已经进入上下文。[O1]

但这不代表现有组织没有问题。每个案例都作为一个独立Skill出现，会与导演、美术、动画等正常工作能力一起参与选择；如果描述相近，或者上层指令再要求逐一参考，就会增加不必要的读取和误用机会。

**因此，本方案不是根据“它们已经全部加载”作判断，而是主动消除案例与工作技能的身份混淆。**

> 技能告诉模型“怎样工作”；案例告诉模型“某个已验证作品具体怎样做”。两者不再以相同的入口身份出现。

这比只给每个案例追加“请按需读取”更明确：案例仍然可以被找到，但不再各自占据一个工作技能入口。目录中的数量减少，是身份划分后的结果，不是本次优化的唯一目标。

### 三、为什么把13个案例完整放进一个检索入口，而不是缩短每个案例

用户确认的 `motion-case-*` 案例需要保留。**保留的应当是完整案例知识，而不只是一个名字、几句摘要和一条旧目录链接。**

一个已认可案例包含多种不同用途的材料：内容发展和原始要求帮助导演理解讲法；图像、字形与构图帮助视觉作者作选择；动作过程帮助编排；源码、参数和绑定帮助实现。它们不能互相替代，也不需要在每次任务里一起全文读取。

现有 `motion-case-library` 已经承担自有案例与120条库的导航和使用说明。沿用这个入口，把13个完整案例放进它的参考目录，就能继续使用项目现有的资料和同步方式，不必再建立一个案例管理代理或新的检索平台。[S2][S6]

建议采用三个层次：

| 层次 | 负责什么 | 不负责什么 |
|---|---|---|
| `motion-case-library/SKILL.md` | 说明如何根据当前问题寻找、读取和采用参考 | 不把全部案例细节复制进来 |
| 轻量目录 | 让作者知道每例的中文名称、适用关系与实际资料入口 | 不以摘要代替选中案例的完整教学 |
| 每例的 `CASE.md` 与原资料 | 保留完整案例正文、原始输入、媒体、源码和记录 | 不再作为一个独立工作Skill注册 |

原案例 `SKILL.md` 改为 `CASE.md`，是改变资料身份，不是改变原设计。仅把文件夹放深一点，却继续留下活动 `SKILL.md`，不能可靠实现这里想要的边界。具体改名、链接及资源保护见第二部分第2章。

**用户明确指定案例时，直接读取该例；未指定且当前确实需要参考时，再通过目录寻找。** 已采用的参考继续服务当前稿，不要求每位作者在每个阶段重新搜索一次。

120条Skillry库维持现有位置、索引和媒体。它与13个自有案例都是可选参考来源，不需要把120篇分析抄进技能正文，也不因为这次组织调整重做媒体库。[S10]

### 四、为什么删除未认可的业务教学，却仍保留具体专业方法

用户提出的问题不是“所有例子都不能出现”，而是：一些没有经过其审阅、并非自己接入的业务设定，被迭代过程写成了常用教学。模型可能不断借用这些故事、物体、色板和节奏，使不同主题趋向同一套表现。

当前美术文件里的A/B座椅与票规练习，以及另写案例集中的团队数量、日照通勤和配件装包等，属于需要清理的具体范围。这些不能因为链接过已认可案例，就被视为那个历史案例本身。[S3][S4]

**这些业务范本应退出活动技能及其引用链，而不是移到另一个默认会读取的 `examples/` 目录继续发挥同样作用。** 历史记录可由Git保留。

但删除时必须把下面两类内容分开：

| 应移除的业务设定 | 应继续保留的专业知识 |
|---|---|
| 虚构人物、票规、价格、完整台词与特定场景 | 从句意推导可见内容、从使用方式反推材料需要 |
| 未认可的固定配色、对象布局和示例时间表 | 主体尺度、真实字形、主次、遮挡与关键中途的判断 |
| 把假设场面包装为制作范本的长指令 | 条件—判断—动作—返修的工作方法 |
| 为上述业务编写的整段演示成稿 | 裁切公式、点映射、源时间、事件计算与必要技术测试 |

不能因为一份文件包含案例，就把整份文件里的公式和有效方法一并删除。也不能只把业务名词抹去，留下一个无法理解的空壳：有独立价值的方法需要重新接成正常专业说明，但不补造新的业务故事。

**你已经确认的直播案例，其直接对应的字位侧转、手机交接、同源镜片教学，可以随该案例完整保留。** 这样，具体教学仍在，需要时可深入学习；通用入口不再把它们作为所有任务的默认外观或必读长文。具体删除范围与保留边界见第二部分第3章。

### 五、为什么保留29个工作入口，而不是把它们合成少数几个大Skill

**文件越少，不等于一次任务读得越少。**

字幕、转写、素材导入、声音、导出，本来就可以被单独请求。若为了减少目录，把这些内容都塞进一个“全能导演”，局部任务反而需要进入一个更大的混合入口。

本方案保留29个工作名称，是为了保留可独立调用的工作边界，不是把它们排列成29个制作步骤。简单、完整的工作可以自包含；确有多个实质分支的工作，再把详细方法和操作放进参考文件。[O2]

同时需要分清三种数量：

**中文角色数量**是用户理解工作分工的方式；**Skill数量**是可使用的工作能力数量；**子代理数量**是当前任务实际派了多少执行者。三者不需要相等。

同一位视觉作者可以连续使用美术、动效和Remotion实现方法，从构思一直做到修订。拆开资料，不应变成每到一个文件就新建一个人、重新讲一遍完整背景。

各类技能真正要划清的是下面这些决定：

| 工作 | 应当负责的主要决定 |
|---|---|
| 导演 | 整片怎样发展、每段为何这样接、材料怎样改变讲法 |
| 文案 | 怎样把发现组织成准确台词、哪些语言与画面互补 |
| 视觉美术 | 面对什么主体、离它多近、背景从哪里来、如何共同构图 |
| 动效编排 | 对象怎样演、关键中途谁主导、何时显露和交接 |
| 动效实现 | 怎样落实当前设计、媒体和时钟如何正确运行、实际错误怎样修 |
| 主任务协调 | 怎样完整传递选择、实际调用工具、把结果续接给原作者 |

导演的六步取材方法应完整归入导演的 `asset-briefing.md`。它是一般工作方法，不应只藏在某一个案例里。需要学习具体实例时，再通过案例入口取得对应的原材料和演出。

全部29个工作入口的详细归属，见第二部分第4章。保留名称不是承诺任何入口永不调整；本轮先完成明确的资料归位，不同时制造一轮无关的改名和调用重构。

### 六、美术与动效为什么要拆成“设计、演出、实现”，而不是一起压短

这几类内容紧密相关，但面对的问题不同。

**美术解决当前画面是什么样。** 主体的轮廓、比例、观察距离、字形、材料、光影和空间，决定它是不是一幅有具体选择的画面。

**演出解决这幅画面怎样发展。** 谁先发起、谁跟随、什么需要保留、新旧如何共处、阅读何时成立，决定连续过程是否有表现力。

**实现解决这些选择怎样准确发生。** 源坐标、裁切、父子变换、作品时间、视频源时间、声音事件和绑定，决定设计是否在实际作品里被保留。

如果把三类内容和发行历史放在同一入口，作者很难找到当前最相关的知识；如果全部概括成“先设计、再实现、注意连续”，又丢了关键方法。

所以，这次按问题归位，而不是按字数切割：

```text
本片的表达与当前材料
    → 美术方法：形成主体和共同构图
    → 演出方法：安排变化和最关键的中途
    → 实现参考：把坐标、源时间、文字与事件落实
    → 实际预览：按问题回到对应层修改
```

这里的箭头表示各项工作如何相互承接，不是要求所有任务都固定串行。已有美术只改视频重播，就直接处理源时间；已有作品只换一段文字，就检查相应排版和预览，不重启整套创作。

原来的 `scene-art-and-motion.md` 需要完整分解：美术归 `art-direction.md`，动作归 `performance-design.md`，指定案例的具体练习归案例资料，纯技术公式归实现参考。迁移完成后退出原混合文件，不同时维护两套长教材。

尤其不能丢掉以下知识：`cover/contain/fill` 的计算、源点进入窗口后的映射、边缘目标的处理、同源局部观察、真实视频时间与作品时间的关系。**“按需查Schema”只能补当前字段，不能替代这些行为说明。**[S11][S12]

针对实际问题，保留清楚的返修方向：构图弱，改主体、字形、面积或材料关系；两端好看但中途混乱，改中途和注意交接；标注漂移、视频重播，修坐标与源时钟。不能把它们都归成“再丝滑一点”。具体文件树与迁移位置见第二部分第5章。

### 七、按需加载靠明确工作分支，不靠一句“需要时阅读”

**把资料放进 `references/`，只是具备了按需读取的条件；入口与调用方怎样写，才决定作者实际会读什么。**

如果入口要求“先完整读取全部共享合同和案例”，文件即使拆成十份，模型仍然会读十份。反过来，如果只写“详见参考资料”，作者也可能不知道哪个文件能够解决当前问题。

每一个详细资料入口，都应同时说清：**什么情况触发、读取哪个文件或章节、读完要完成哪个决定或产物。** 入口本身仍要保留普通任务能正常前进的完整骨架，不能只剩跳转链接。

以当前动效工作为例：

| 当前工作 | 本次需要的资料 | 没有必要同时启动的工作 |
|---|---|---|
| 新建或实质重构场面 | 当前完整稿、美术和演出方法、实际采用案例 | 所有视频类型与全部案例 |
| 只修改已有文字、颜色或位置 | 当前源码、相关属性与预览 | 整片主线重写、风格重选 |
| 修复标注漂移 | 当前裁切、坐标映射和绑定 | 所有美术教学 |
| 修复手机移动时视频重播 | 作品时钟、源时间与当前源码 | 重新搜索素材和重写故事 |
| 调整新旧接管 | 当前演出、相邻画面和声音 | 全部平台发行历史 |
| 只提交、放置或处理Job | 当前状态与提交恢复方法 | 重新作一遍设计 |

这不是限制作者只能看几页。必要信息还不够，就继续读取相关资料；导演需要理解整条案例的发展，就应完整读该例。**按需的依据是当前问题，不是人为规定只能读摘要。**

已读资料没有变化、当前任务仍可使用时，继续承接已有结果；不在每个阶段重新从全库开始。也不假设读过的长文会因为阶段结束自动从上下文消失。降低负担靠避免提前加载和重复传递，而不是依赖不存在的“自动卸载”。

阅读网站可以让用户完整通读全部资料；执行中的模型仍然可以只读取当前有关部分。**人的完整阅读与模型的按需使用，可以共用同一套完整文件。** 具体入口正文和任务读取表见第二部分第7—8章。

### 八、只改技能文件还不够：共享约定和当前稿也要各归其位

一个短Skill若链接到几份必须全文阅读的共享长文，阅读负担只是被转移，没有消失。共同约定应当保证大家说的是同一件事，不意味着每个人都要掌握所有接口和历史事故。

共享目录应保留少量真正跨角色的依据：当前稿怎样表达上下文，已有观察和材料如何回传，作者之间怎样续接。具体观察方法归素材，具体美术归视觉，坐标归实现，Job写入和恢复归主任务。

**还有一种内容尤其不能再混回通用Skill：当前作品已经作出的具体决定。**

这条片选了什么素材、用了哪些字、某场何时接管、哪个字体已经采用，应留在当前声画稿与项目记录。后续角色读取的是这些实际决定，不是每人重新从主题猜一遍；但它们也不能因为这次用得顺手，就被追加进所有作品的通用入口。

主任务的交接需要保留导演与作者的完整选择。把“当前对象为什么让位、哪些参照保留、新内容怎样取得注意”缩成“做一个高级转场”，会让下游重新设计，并丢掉前面已经完成的工作。

根 `AGENTS.md` 同样要与新的组织一致。原规则中以“专业解释和案例为主体”的表述，需调整为以有效专业方法为主体、已认可案例按需使用；否则上层仍可能鼓励继续把业务案例堆进常用正文。[S5]

**共享的是一致依据，传递的是当前作品；不是把全部旧资料复制给每位作者。** 共享文件去向和上层入口调整，见第二部分第6、9章。

### 九、为什么实施顺序必须是“先完整迁移，再清理，再同步”

这次不是只改阅读网页。文件位置变化会影响实际加载、案例媒体、相对链接、调用配置、测试和插件发行。

项目现有 `.agents/skills/` 是唯一技能源，再同步到插件目录；同步器会清理源中已经不存在的目标内容。[S6][S7][S8] 因此，如果先删旧案例，再发现新位置只有一个索引，下一次同步就可能把原来的完整资料一起清掉。

正确顺序是：

```text
核对原始文件与资料身份
    → 完整迁移案例、方法和技术内容
    → 更新链接与调用入口
    → 检查原件、公式、接口语义与测试
    → 清理旧入口和重复内容
    → 沿原流程同步插件
    → 用实际任务验证读取与作品
```

保留29个工作名称可以减少无关调用调整，但不能免除路径核查。Markdown、案例索引、默认提示词、测试和包装脚本，都可能引用旧位置；不应为了兼容而恢复13个独立案例Skill。

迁移也不能通过手改已安装缓存完成。源文件与发行副本保持一条清楚的更新链，实际会话加载到哪里、是否出现同名入口，需要从运行结果核对。仅在VS Code里看到目录变了，不证明模型已经读到新资料。

详细工程检查见第二部分第9章，执行顺序见第11章。

### 十、如何证明这次是整理成功，而不是又一次知识缩减

**先完成原内容去向，再编写短入口。顺序不能反过来。**

每段原内容都需要明确归属：保留、完整迁移、合并重复、删除不认可业务范例，或归档过时说明。所谓“合并重复”，要确认不同段落中的独有条件和处理办法仍然在；不能因为语句相似就删除不同情况。

内部核对应当检查能改变行为的知识，而不只是核对标题和文件名：什么时候使用，为什么这样判断，具体怎样做，什么情况下改用另一种处理，出现问题如何返修，以及必要的公式和接口含义。

最终验证分成三层：

**知识层：** 已认可案例完整，未认可业务范例退出；专业推导、实现公式和有效合同能够在明确位置找到。

**使用层：** 新片、局部改字、补素材和时钟修复确实读取不同资料；应读的没有漏，不相关的没有被一并加载，当前稿没有在交接中缩成几个标签。

**作品层：** 文案发展、素材契合、构图、中途和声音在实际结果里得到改善。文件更短、链接可用和工具成功，都不能单独证明成片变好了。

迁移核对记录属于实施者的内部工作，用户最终阅读的是正常组织的完整技能，不需要自己翻几十份文件找漏项。人的阅读页应由最终实际文件生成，不再维护一份独立摘要冒充正文。

> **这次要减少的是混乱、重复和无关读取；要保住的是产生设计、落实设计和修好设计的能力。**

### 7. 入口正文应该怎样写，才真的会按需读取

#### 7.1 每个入口保留一个能工作的最小完整流程

入口不是只剩链接的路由表。它至少说明：适用任务、拿到哪些现成输入、本次关键决定、正常执行过程、完整产物和当前分支的必要依赖。完成简单任务时，凭入口与当前作品就应能前进。

详细参考也不是“补充阅读”。每一条入链要写触发条件、解决的问题、明确文件或章节。避免“先读所有共享文件”“为了质量全文阅读案例库”“每次重启先看所有历史输入”。[O2]

#### 7.2 动效实现入口的具体分支文字

以下正文是实施时可用的分支段；完整正常流程和必要合同还要保留，不能只拿这张表替代整个Skill。

> 接收当前作品和实际修改范围。新建或实质重构场面时，先确认当前美术与完整演出；尚未形成则由原作者使用相应专业方法继续设计。只改已有文字、颜色、位置或切口时，直接读取当前源码与被影响的参数，不重新启动整片主线和案例检索。
>
> 用到真实视频、图片、字体或事件时，在写对应代码前读取受管合同中的相应部分；需要裁切、局部观察、附着标注或视频接续时，读取素材坐标与时间的方法和公式。提交、放置或结果异常时，才读取提交与恢复。
>
> 预览回来后按问题继续：构图和字形问题回美术，关键中途和注意交接问题回演出，漂移、重播、范围和绑定错误回实现。保留当前已成立的选择，不因局部问题把全部资料再次加载。

#### 7.3 案例检索入口的具体正常流程

> 先读取当前创作问题、已经采用的设计和参考。用户明确指定案例或当前稿已有相关采用项时，直接进入它的资料，不重新搜索。
>
> 没有指定且需要参考时，读取已认可自有案例的轻量目录。用当前问题理解相近的内容关系或表现方式；必要时按现有方法进入120条库。目录用于发现，不把未命中的关键词当排除依据，也不把所有分析和源码一起读入。
>
> 入围后打开对应 `CASE.md`。根据当前工作读取原输入、所需媒体范围或实现代码：导演关注内容与取材，文案关注叙述和材料改稿，美术关注造型与共场，动画关注中途和接点，实现关注真实源码与合同。需要理解整条作品关系时完整读该例，而不是预先限制为几段摘要。
>
> 将已采用的关系、资料位置、实际已看范围和本片具体变化放回当前声画稿。它是当前作品的设计，不是给各作者再复制一遍整个案例。引用结果不足以完成当前工作时继续读取；没有匹配也按专业方法完成，不为用案例改题。
>
> 不创建独立的“案例代理”，不把一个历史原始输入当作新任务命令，不将临时生成的新业务例子写回技能。

#### 7.4 索引应包含什么

13例轻量目录只需要真实ID、中文名称、可供借鉴的简短关系、CASE路径，以及原输入/成片/源码是否存在。每例几句即可，避免复制色号、坐标和时间表。后面是完整原件，目录不是专业方法的替身。目录中的关系从已有资料抽取，不新写假设作品或“成功概率”。

已有120库继续使用现有卡片集合和分页；开放检索是否覆盖更多卡片取决于问题与现有候选。不要求每个作者或每个新阶段从头重读120条。相同任务已看过且未变化的条目与部分可以复用；素材、方向或代码变了，再补读受影响部分。

### 8. 一次制作实际读取哪些文件

| 当前工作 | 读取什么 | 不应顺带触发什么 |
|---|---|---|
| 用户给主题，开始完整创作 | 项目基础、协调；导演选择一个视频主流程，文案与美术按当前任务进入 | 其余两个视频主流程、全部案例与所有接口 |
| 导演提出取材 | 当前句群、前后画面、asset-briefing；已采用例的对应取材与演出 | 全部案例源码、渲染故障和声音字段 |
| 素材作者取得旅客/界面等材料 | 导演具体请求、已有观察、当前来源获取操作 | 自行规定全片风格或固定原创路线 |
| 美术安排主体、字形和背景 | 当前材料、art-direction；相关案例的图像与说明 | 全部媒体公式或发行日志 |
| 动画组织一次交接 | 当前构图、performance-design、真实声音接点；相关案例片段 | 重新搜素材全库或重新写导演故事 |
| 修同源窗口重播或标签漂移 | 当前源码、绑定与material-space-and-time | 整片创作、所有美术案例 |
| 只换一个已确定词 | 当前文本、源码/属性与相应预览 | 重选风格、重扫案例、重录无关声音 |
| 准备导出 | 当前项目与输出目标、导出方法、必要技术核验 | 全部案例审查或把审美辅助意见当必须全部关闭的门禁 |

表中“读取”并不承诺某个宿主自动按该顺序执行，必须用真实任务日志验证。Skill数量也不等于子代理数量；同一作者可在当前工作中按需使用多份相关方法。

#### 指定直播案例的完整使用示范

导演处理这条直播任务时，先理解完整内容发展，再将第2.1取材表与第6、7节对应演出相连。需要知道椅子为何要有完整轮廓，就读2.1、6.1和7B；需要直播内容怎样整体更替，就读2.1、6.2和7C；压力到节目组的接管，读第3节语义标记和7D；同源观察镜实现，读第8、9节及当前工程坐标合同。

这不是将案例拆成多个独立成功范本，也不要求每个作者都从第一字读到全部源码。局部阅读必须保留理解所需前后文；导演理解整条发展确有必要时完整阅读原指令。案例第9节本来就强调同一作者完成构图和实现、从实际源码取得关键帧、源时间独立于对象移动。学习的是这些方法，不是本例固定近黑或字幕白条。[S13]

### 9. 不能只改Markdown：项目里要同步检查的入口

#### 9.1 根AGENTS与每个Skill里的重复执行声明

根 `AGENTS.md` 当前规定主任务、导演和子代理边界，并明确源目录唯一；其中“创作型Skill以连续专业解释和案例为主体”的句子，应该改为“以有效专业方法为主体；已认可案例是按需资料”。字体选择、Job失败等专门操作用明确触发链接，不让各Skill重复一份。[S5]

同时检查所有“本次共同参考”“首次先全文阅读某案例”的泛化文段。当前项目确已指定某例时读取合理；普通任务不能被旧的“一次任务”措辞绑定这个例子。执行约定可以短写一句链接，不把输入Revision、审计、模型观察等长文复制到29份入口。

#### 9.2 同步与插件

编辑源仍然是 `.agents/skills/`。改完由现有 `npm run plugin:sync-skills` 生成 `plugins/videoflowcut/skills/`，不手工维护两套规则。[S6][S9]

`sync-tree.mjs`会删除发行目录中源目录已不存在的对象。迁移应先确认新案例位置的文件完整，再清理源旧入口并执行同步，不能先删旧案例再发现新位置只存了索引。[S7]

当前校验会比较源与发行副本的全文件路径和哈希；案例放在检索Skill下仍可沿这套机制同步。增加“案例目录内没有独立SKILL入口”的专项测试，以及所有相对链接和案例资源的可达性检查。原共享内部入口的生成/校验保持一致。[S8]

#### 9.3 注册、UI与缓存

检查实际运行的Skill发现路径，而不只看VS Code目录。官方机制允许多个源中的同名Skill同时出现，不会自动合并，因此需要核对仓库源和已安装插件是否都被当前会话暴露。[O1]

本提交的 `.codex/config.toml` 没有Skill注册清单，不能假设必须在里面删除13项；实际可能的注册路径应先读回。不要为目录整理更改权限配置。旧插件中的案例入口通过正常更新与会话重载退出，不手改已安装缓存。

中文目录页按“角色→工作入口→方法→操作→案例入口”展示。已认可案例在案例区完整阅读，不列入待审。页面由最终实际文件生成，不维护一份与文件不同的说明摘要；人可以完整阅读，模型仍只按实际任务读取。

#### 9.4 程序与测试中引用了旧路径的地方

全仓搜索具体旧路径与案例ID，包括注册表、测试、文档生成器、案例索引、包装脚本、agents默认提示词、历史模板和配置。只改运行中的引用；历史来源记录保留其历史含义，需要时另记录新资源位置，不伪改过去的工作目录。

保留现有29个功能名字可减少无关调用调整，但不免除链接检查。原测试若以“包含某一大段业务示例”为通过条件，应改为验证有效方法与引用存在；不可为了删例把时间、几何和媒体测试也删掉。

### 10. 怎样保证信息不再丢

#### 10.1 逐段迁移记录是实施者的内部校验，不是交给用户的阅读正文

对每份原文本先保留完整快照和hash，再按标题/段落记录去向：保留、完整迁移、合并重复、删除用户不认可范例、归档过时说明。每个“合并”都要列出保住的独有判断和例外；每个“删除”都要有本轮范围依据。

不能把“新文件有这个标题”当完整保留。检查的最小单位是能改变行为的一条知识：触发情况、判断理由、具体动作、异常与返修、必要公式/操作语义。**简单同义重复可以合并，不同情况不能因为语句相似就删除。**

#### 10.2 迁移完成应具备的证据

| 检查 | 应看到的实际结果 |
|---|---|
| 已认可案例 | 13例都有完整CASE正文与原资源去向；原始输入、媒体与源码hash对应；新位置无活动SKILL入口 |
| 未认可业务例 | 活动入口和引用资料不再包含已决定删除的范例；旧内链、默认prompt与目录也清理 |
| 方法不丢 | 造型、字形、关键中途、改稿、材料反馈的具体判断能在唯一详细位置找到 |
| 技术不丢 | 裁切、点映射、源时钟、事件/起音计算、真实接口语义及相应测试仍在 |
| 调用不乱 | 新片、只改字、补素材、修源时钟等任务读不同的必要资料；不出现全库前置 |
| 结果不假 | 目录、语法和测试通过不替代实际声画验证；没有跑的视频不称已优化 |

不设置“少于多少字一定合格”的门槛。可以记录入口长度与本次实际读取量，但更重要的是选择是否准确、动作是否能落实、返修是否有效。

### 11. 可直接交给实施Codex的执行顺序

1. **从当前原文件开始。** 读取实际工作副本，核对与本说明基线的差异；保存原文本和已认可案例完整清单。不要以先前精简稿为底。
2. **先迁案例资料。** 逐个完整移动13例，改入口文件名和引用；保留原件、代码、参数和反馈，建立轻量目录。120库不重做。
3. **去除非认可业务范例。** 按第3章清理全部出现位置及反向引用；混合文件只去业务内容，保住通用方法与纯技术代码。
4. **按第4—6章归位知识。** 完整迁移后再写入口，不能先把入口压短、后面再临时填方法。原段落去向逐项对账。
5. **改加载与交接。** 入口写真实触发分支；根AGENTS、跨Skill指令与默认prompt一致。当前项目已作选择留在当前稿，不写回通用方法。
6. **同步插件与静态检查。** 走项目既有同步和校验；验证链接、原件hash、已删除路径、元数据和目录数量。29个工作入口加现有内部共享适配项的口径分开。
7. **实际任务验证。** 测新片、局部文字修改、素材取得失败换源、同源视频移动、跨段声音修改等已有任务类型；记录真正读取的文件与实际结果，不新增业务教学案例。
8. **交付完整可读文件。** 输出实际已修改的文件树、同源生成的中文阅读页、迁移校验结果与已运行/未运行测试。不是替换段落包，不是把旧文件留在别处就称完整。
