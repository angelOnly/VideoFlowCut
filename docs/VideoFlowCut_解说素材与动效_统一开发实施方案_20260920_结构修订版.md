## 0. 从哪里开始：只按一条开发顺序执行

**不是“先执行完整审计，再执行完整方案”。** 审计是发现问题的依据，不是一套独立产品需求。它提出的修复已经并入本文件，在哪个模块开发，就先处理那个模块直接依赖的旧问题。

默认由一个开发任务按下表推进，不要求用户每阶段再确认一次。阶段内的测试随实现完成，阶段 4 汇总工程联调与发行验证，阶段 5 才判断普通入口能否产生并可靠修改实际成片。

### 0.1 依赖只限制相关模块，不把所有工作一起卡住

文案与创作交接可用现有本地材料先验证，不等外部来源服务。混合动效可先用几何普通、预算适用的本地素材试作，但不能用这一结果宣布旋转、非方形像素或历史任务兼容已经通过。

没有研究 Key 或某个外部来源不可达时，记录具体未验证项，继续不依赖它的工作；不能把“配置缺失”写成“没有素材”，也不能把跳过的外部验收写成完成。确有多位开发者时，素材分支与动效分支可在共享合同明确后并行，最后统一合并测试；单人照上述顺序即可，不必自行拆成多个项目。

### 0.2 本次继续使用的主架构

保留现有 Script、NarrativeMap、Story、Scene、Asset、Job、EffectCue、受管渲染、声音及 Revision／Impact 链。不新增编剧微服务、导演引擎、素材数据库、渲染平台或另一套工具协议。

现有问题与新能力分别处理：Pexels 类型、旧缓存和显示几何属于相应链路必须修正的问题；来源研究、解码尺度和内部视频采用属于本轮明确扩展；原创稿整稿提交与真实原话保护属于要遵守的现有边界。代码能提交、单件能渲染、实际采用正确和作品好看，是四个需要分别验证的结论。

## 1. 本次优化要解决什么问题

本次优化从三个成片问题出发：解说像平铺的介绍，缺少吸引力与节奏；检索到的实际视频偏少，使用时又经常缩在画面中间；动效虽然在运动，却仍像一页页说明卡，真实素材没有充分参与解释过程。

要改变这些表现，不能只要求模型“写得更精彩、找更多素材、动画更高级”。本方案分别补充写作方法、材料获取与使用能力、连续场面的设计与实现，并让三项工作在同一次剪辑中相互配合。

### 1.1 三个成片问题与对应的建设目标

| 成片中要改善的问题 | 开发后应发生的实际变化 | 对应实施内容 |
|---|---|---|
| 解说朴素、平铺，缺少节奏 | 根据主题和实际材料写出完整台词；让观察、行动、比较或认识逐步发展；配音和画面回来后能具体改稿 | 第 3—5 节：写作方法、新增 `narration-writing`、导演交接与现有 Script 接入 |
| 素材偏少，长期居中小窗，画面空旷 | 按需要看见的动作与过程找材料，能够继续检索、查看原内容并取得可用文件；使用时按观察重点决定面积、裁切和布局 | 第 6 节：来源研究、候选检索与受管取得；第 7 节：素材进入画面的方式 |
| 动效有 PPT 感，与真实素材割裂 | 使用实际文字和素材共同设计主体、构图与连续变化；让实拍、录屏或真实页面持续参与，再由图形帮助指认、比较与解释 | 第 7 节：视觉与动效 Skills、案例迁移、混合素材示范及必要代码修正 |

这里的目标不是增加固定的台词套路、素材数量或动画数量。需要看到的是：讲述有值得跟随的内容，材料能支持正在讲的事情，画面能清楚而有表现力地把它呈现出来。

### 1.2 三项工作怎样共同改善同一段视频

三项工作处理的是同一段内容，不是分别完成三份互不相干的结果。文案提出要讲什么、需要让观众看见什么；素材研究确认实际有什么、能支持到哪里；视觉与动效再把采用的台词和真实材料组织成具体画面。材料与预览也会反过来改变写法和分镜。

例如，沿用本文“介绍网页里的复古桌面”的教学情境，某一段准备展示主题切换。以下只说明协作方法，不表示已经取得对应录屏或验证了某个产品：

**写作时，先提出值得展开的观察。** 不停在“它支持多种主题”这一句功能介绍，而是准备让观众跟随一次切换，观察窗口和任务栏是否一起变化。此时可以提出想核对的问题，但不能提前把尚未看过的结果写成事实。

**选材时，寻找能完成这次观察的过程。** 需要的是打开设置、选择主题、看到结果的连续录屏，而不是一张电脑图片。若实际只有截图，就把这个缺口交回，继续找材料或调整讲法；不把截图说成已经验证功能可用。

**制作画面时，让找到的过程真正成为主体。** 先让界面可辨认，再靠近发生变化的区域，必要的标注与同一界面保持位置关系，最后让观众看清实际结果。不是播放两秒录屏后，就换成另一套独立图标重新讲一遍。

**放在一起审阅时，按实际效果修订。** 台词抢在操作结果之前、界面太小、放大后文字不清楚，分别修改稿件、构图或对应工程问题。不能只因为文案写完、素材下载完、动画渲染成功，就认为这一段已经成立。

因此，本次建设的关系是：**讲述提出观看需要，实际材料支持或改变讲述，视觉设计把二者做成场面，再用真实声画检验并修订。** 总导演负责整片取舍与前后关系，主任务负责分派和正式项目操作，具体工作仍由对应作者完成。

明确这层关系后，下一章再说明由谁负责、先交出什么、结果怎样传到下一步。第 2 节描述开发完成后的剪辑工作方式；软件开发本身仍按第 8 节推进。

## 2. 一次剪辑任务怎样把这些能力用起来

本章承接第 1 节的三项建设目标，把它们放进同一次剪辑任务：先确定用户这次要做什么，再让写作与材料研究共同形成内容，由导演组织分镜，随后制作声音和画面，并根据实际预览修订。

### 2.1 谁来完成这些工作

文案、研究选材、视觉动效分别需要明确的负责人；导演把各自的结果组织成整片，主任务负责实际交接与工具提交。下表中的“作者”和“导演”是现有代理协作中的工作职责，不是要求用户另外组建团队。

| 负责人 | 承接哪部分工作 | 交出什么，交给谁 | 责任边界 |
|---|---|---|---|
| 文案作者 | 发展讲述角度，写开头、展开和结尾，安排口语节奏；把材料发现写进台词 | 完整可朗读正文，以及逐段“讲什么、看什么”的声画稿，经主任务交导演；材料或预览改变判断时交回新稿 | 不代替研究者核实未看过的来源，不代替导演决定整片最终采用 |
| 研究／选材作者 | 查原始资料、找并查看真实操作或场景，确认源范围与取得状态 | 原文或实际观察、来源、支持的说法与限制、可用素材及范围，经主任务交文案作者和导演，再交具体使用者 | 不只交链接，不把尚未取得的文件说成可用素材，也不自行编写最终解说结论 |
| 视觉／动效作者 | 使用采用稿和实际素材，设计主体、构图、重点变化、运动及声音接点；完成源码与修订 | 当前场面的完整制作说明、布局、源码／参数／绑定，交导演协调并由主任务提交；查看实际预览后继续修订 | 不独自改变整片结论或人物原话，不以图标替代本来需要的真实过程 |
| 总导演 | 从收到需求起负责整片方向、删留、分镜、主次、前后镜头、声音和跨段节奏 | 采用的完整讲述与分镜、具体修改要求、后续制作安排，经主任务交相关作者 | 不只是最后审阅，也不需要在作者开始前包办终稿和全部动效源码 |
| 主任务 | 与用户沟通，读取项目事实，真实启动或续接负责人，转递完整材料，排序执行正式工具写入 | 实际 Project／Revision／Job／Asset／Preview，以及交回原作者的工具结果和预览 | 不在装配参数时删台词、换镜头、压缩完整制作说明或代替导演作采用决定 |

后文的“专项”指这些具体专业任务。例如“文案专项”由文案作者承担；同一位视觉作者可以按需读取 `visual-treatment-planning` 和 `remotion-production`，连续负责美术、运动、源码与修订，不因读取两个 Skill 就拆成两个新角色。配音与审片等既有职责继续在相应步骤参与。

有了以上分工，下面按一项需求从进入到交付的顺序说明工作怎样推进。各步骤需要时可以回到原负责人修改，不是只准向下走的流水线，也不是多轮用户审批。

### 2.2 从用户需求到成片的完整流程

#### 第一步：读取需求，确定本次需要做哪些创作

主任务先读取用户原始要求、现有项目、稿件、声音和素材，启动负责整片的导演。导演明确观众、用途、初步表达方向，并根据这次委托安排写作与制作范围。

| 用户提供的内容与要求 | 本次怎样处理 |
|---|---|
| 只有主题、受众和剪辑目标，没有稿子 | 由文案作者原创讲法与台词，必要材料研究同时开始 |
| 有粗稿，要求优化 | 按授权调整结构和台词，保留正确事实、原本立场与明确要求；需要重大改变主题或观点时回导演协调 |
| 数字人需要新口播 | 先形成完整解说，导演采用后进入配音和人物生产 |
| 已经录好真实口播，只剪重复或重排 | 沿 `semantic-continuity` 编辑真实原话，不替人物编造新说法，也不把整稿转成原创 Script 来绕过来源 |
| 锁定稿件、声音、某两句话，或者只做包装 | 保留明确锁定的部分，其余按委托调整；不自动重写整片 |
| 无旁白的生活记录 | 不强制写解说；确实需要新增旁白时只处理相应范围 |

这些范围来自用户要求，不是导演额外制定的一套审批规则。用户没有锁定的初稿、第一版配音长度和分镜顺序，仍可以根据材料与预览调整。事实、引用和真实人物原意的准确性始终需要保持，与用户是否锁稿是两回事。

环境声、动作声可以与原创旁白共同使用；已经进入 Script 的真实人物原话则必须保留来源与语义身份。本轮仍不接通“在真实口播 Script 内混合追加原创过桥句”的写入能力，不能用完整 authored 替换冒充支持。涉及该需求时，先保留原话并交回具体创作方案，正式能力边界见第 5.7 节。

**本步交出：** 导演的初步方向、给文案作者的具体任务、需要保留的内容，以及已有材料。此时不要求终稿与全部分镜已经确定。

#### 第二步：发展讲法，同时查资料和找画面

文案作者根据同一版需求和材料构思开头与后续内容，提出会影响台词的具体问题；研究／选材作者查看已有原片，查原始说明，寻找能展示所需过程的画面。互不依赖的研究可以并行，实际发现尽早经主任务回传文案作者与导演。

需要优先查清的，是答案会改变讲法的问题：操作是否真的完成，条款有没有重要条件，视频有没有拍到从输入到结果的完整过程。尚未选择强调色，不必因此停止写作；尚未确认操作成功，却准备在台词里说成功了，就需要先核对材料。

前期可以直接提出“看看这个网页有哪些能连续演示的操作，查作者说明确认支持范围”。先得到实际材料，再决定跟随哪个过程、比较哪些状态；不必提前填写最终 Scene ID、镜头坐标和精确秒数。方向明确以后，再提出“补齐这次点击前后的连续范围，确保文字可读”这样的定向请求。正式工具接法见第 6.3 节。

这一步既不是漫无目的地找素材，也不是先写死结论再寻找支持。已有材料足够就继续成稿；确有缺口就围绕缺口研究，不要求搜齐所有来源，也不在没有采用稿时批量渲染。

**本步交出：** 已查看的原文或画面、真实来源与范围、能够支持什么、还有什么缺失，以及这些发现会怎样改变台词和主要画面。

#### 第三步：形成完整稿，由导演组织分镜

文案作者把实际发现写进完整台词，同时给出逐段声画稿：准确说什么，主要看什么过程，语言与画面各自承担什么。材料与最初设想不一致时修改正文，不用一份已经写好的结论强套素材。

导演收到全文与实际材料后，决定采用、提出具体改稿意见，或者继续补材；采用后将主要画面组织为完整分镜，明确观看重点、前后接续、声音配合和大约秒数。适合连续表现的相邻内容一起交给视觉作者，不按句号拆成一次次从头入场的小画面。

进入全面制作前，需要有能直接朗读、主要观看过程明确、重要事实有依据的当前采用稿。这不等于永久锁稿：后续配音、视觉深化和预览仍可以推动具体修订。

**本步交出：** 当前采用的完整稿、导演分镜、定向补材任务，以及给声音、人物和视觉制作的完整输入。

#### 第四步：沿现有链路制作声音、画面与动效

主任务读取当前 Revision，按本片适用的现有合同提交采用稿，读回真实语义对象与 Impact，再组织声音、Scene、素材及动效的制作。原创稿的正式提交按第 5 节执行；真实原话编辑保持原有路径。

视觉／动效作者收到本段全文、实际素材及源范围、前后画面、当前声音信息和人物／字幕占用，使用真实内容一起设计主要构图和运动中途。先做最影响效果的接点，完整深化稿回导演协调后，仍由同一作者继续源码和修订。需要新增素材或改变主要讲法时交回具体请求，不在实现中悄悄删句或更换解释对象。

声音的实际时间成为本版编排依据；在声音未最终确定时进行的必要试排，不冒充已经精确同步。第一版 TTS 的长度也不自动成为新的硬限制。主任务沿既有受管作品与预览入口提交完整参数，并把实际产物交回原作者。工具、版本和源时钟的细节见第 7 节。

**本步交出：** 实际声音、素材与作品版本，以及可放入上下文检查的代表段或粗剪；不是只有设计说明或“渲染成功”的回执。

#### 第五步：看真实合成，把问题交回原负责人修改

把旁白、字幕、人物、源视频、图形、原声和前后镜头放在一起检查。文字空泛或结论抢先，回文案作者；原片缺少过程，回研究／选材作者；构图平淡或源码漏做动作，回视觉／动效作者；跨段衔接与整片节奏由导演统筹。声音与人物问题继续交相应原负责人。

反馈说明本版具体哪里有问题、需要改什么，而不是只写“更有吸引力”或“更丝滑”。原作者交回修订产物，主任务提交后再看新版本。改稿和换素材带来的项目失效按第 2.4 节处理，不能让新画面继续配旧声音，或把旧版审阅当作新版已经通过。

**本步交出：** 实际修订后的版本、已观察范围与结论，以及仍需处理的具体问题。代表段的作用是验证制作方式，不是代替整片交付。

#### 第六步：继续整片制作，完成任务范围内的审阅与交付

沿已经验证的制作方式继续剩余内容，导演与审片负责人检查当前整片，主任务完成技术检查、导出与交付。最终结论对应实际观看的版本和用户本次要求；未审范围如实说明，不用单件无声动画的通过结果代替整片声画检查。

这六步是剪辑任务的工作顺序。软件功能按第 8 节分阶段开发，工程测试和普通入口的成片验证仍分别进行，不增加每段都必须让用户批准的流程。

### 2.3 贯穿全流程的完整交接与正式写入

上述步骤能否接起来，取决于下一位负责人拿到的是完整产物还是一句摘要。文案作者提交的完整正文、声画稿和具体素材观察，经真实宿主消息交给导演及相应作者。主任务不能自行缩成“有悬念、有反转、采用某案例”；确实超过单次消息承载时分段传递并明确篇次，接收者取齐相关范围后再工作，不悄悄截断。

采用的朗读正文写入现有 Script；导演采用后的分镜信息进入现有 Story／NarrativeMap／Scene 等对象。CreativeDecision 记录决定、理由及引用，不装整篇声画稿，也不承担附件存储。

当前平台没有专门保存并读回任意长篇声画稿的受管附件接口。未提交的设计全文仍依赖原任务消息；仅恢复 Project 快照不能保证恢复这些设计。缺全文时回原负责人取回，不发明 `fullDesignSpec`、任意磁盘路径或不存在的保存工具。若之后明确要求跨会话完整恢复初稿，再单独设计通用创作文档持久化；这不是本轮新增文案 Skill 的前置条件。

正式项目写入、生成提交、渲染和审阅保存由主任务统一执行。排序针对会改变 Project／Revision 或完成时回写的工具操作，不要求所有阅读与思考串行；两位作者可以同时研究不同材料，但不能各拿同一个旧 Revision 提交相互覆盖的修改。

平台已有的委派职责 `director / specialist / reviewer` 继续使用，文案作者沿 `specialist` 承接，不为中文职责名称新增角色枚举。委派记录中出现 agentId 只证明记录存在，不能代替宿主实际启动作者、转交全文和续接修订的证据；这些行为在阶段 5 的普通入口验证中确认。[S12](#audit-s12)

### 2.4 改稿时怎样更新现有项目

对采用原创稿的项目，`apply_authored_script` 当前是整稿替换。文案作者可以只创作局部差异，但提交前必须合并为完整采用稿，保持不需变动的段落与身份信息，依实时 Schema 由主任务提交。已有真实原话 Script 的编辑不走这条替换路径。

当前实现能为未改文字复用部分语义对象与段音频，但整稿更新仍会影响当前声音组合、Dialogue、字幕及其他下游对象。不能向用户承诺“改一句就会自动只重做一句”。主任务读取实际 Impact 和对象状态，再将受影响范围交原作者；配音、人物、字幕、声音包装、动效绑定与接点按实际依赖重新确认。没有必要扩大到无关创意，但技术失效也不能仅靠保留旧 ID 忽略。具体对象与接口处理见第 5.1—5.2 节。

前两章说明了优化目标和完整工作方式。接下来进入各项能力的实施细节：第 3—5 节先展开文案怎样写、怎样交接并进入现有 Script；第 6 节接通支撑讲述的材料；第 7 节把采用稿与真实素材做成具体画面。各章是在深化同一套流程，不是再建立三套独立流程。

## 3. 文案 Skill 必须提供的专业能力

### 3.1 写稿时实际做出的决定

1. **选择讲述角度。** 明确本片围绕哪项观察、任务、比较或体验展开。选择依据是受众、材料和用户目的，不统一套“悬念—反转—总结”。
2. **把材料变成内容。** 写出实际发现、它支持到哪里、它使哪句话改变。具体条款、操作、结果、人物行为进入正文；搜索摘要不能直接变成确定结论。
3. **把重要概括展开为过程。** 选择需要看懂的动作，给观众建立前状态、变化和结果。不是给每个术语都制作一段动画。
4. **组织口头语言。** 使用清楚的主语、具体动词和自然句群。方向句简短，复杂关系给足前提，结果在可理解的位置落下。保留必要限定，不靠堆反问或口头禅制造网感。
5. **分配声画工作。** 画面演操作、比较、结果和关系；声音补充动机、因果、条件、态度或下一处关注。需要听辨、阅读或感受时，现场声和画面可以接管。
6. **安排层次与节奏。** 整片决定重点和删留；段落安排前提、变化、结果；句群处理口语、呼吸和辨认。大约秒数只是首版尺度，实际声画回来后调整。
7. **根据作品改稿。** 发现结论说早、画面来不及辨认、过程缺失或重复讲述时，返回具体新台词和新声画安排，不只说“加强节奏”。

### 3.2 六个动效案例与新文案案例怎样共存

现有六个动效案例继续教主体造型、构图、对象关系、动作接续和源码实现。新文案参考教“材料怎样成为讲述、句子怎样推进、画面怎样参与”。两者在具体场面处接上：文案稿明确要让观众看懂的过程，导演采用，视觉作者再选适用案例深化。

新文案案例至少应完整展示：输入需求；已有材料与未知；平铺初稿；材料带来的发现；修改后的整段台词；逐句群声画对应；修改理由；换题材时哪些方法可保留。参考视频分析与原创教学示例分别标清，不把教学稿标成已经生成并通过的成片。

### 3.3 之前拆解的视频，怎样同时用于文案和动效

源方案读取的是仓库保存的拆解记录与案例源码，没有重新连续播放参考片，也没有取得创作者原始写稿过程；本次合并沿用该证据边界。下面把可观察的表现转成拟采用的方法；不能据此宣称已经听审了原片的重音、配乐或逐词时序。原记录入口见第 10 节“既有参考片拆解”。

```markdown
# 解说文案与声画稿创作

## 执行角色与代理交接

本 Skill 运行在专项子代理中，由主任务通过 production-coordinator 真实分派，并遵循 [代理角色与交接](../_shared/PROJECT_REVISION_AND_HANDOFF.md#代理角色与交接)。输入包含真实 Project、输入 Revision、对象与源范围、用户约束和已有事实；尚无对象时如实说明。

文案作者返回完整产物与参数、选择理由、影响范围和必要材料请求。正式项目写入、生成提交、渲染和审计保存由主任务统一执行；本作者不直接改正式项目。需要其他专项时交回具体工作请求，不递归分派。实际声音与 Preview 经主任务回传后由原作者修订，输入发生变化时先核对差异，不仅更换版本号码重发旧稿。

## 何时使用

用户只给主题或剪辑需求、需要新增解说，或允许实质改写既有稿件时使用。总导演提出本片方向和写作范围，主任务将该范围交给文案作者；完整稿回总导演用于整片分镜和采用决定。

用户锁定原稿或原声时，保留锁定部分，只在允许的范围调整讲述组织、补充说明和画面配合。不为没有旁白需求的观察片强加解说。只有错字、术语读音等局部修正时，不重写整片。

纯原创旁白与已有真实口播的项目合同分开。apply_authored_script 用于完整原创稿，不能拿它向真实原话 Script 里追加一句过桥话；本次没有可用混合写入 Schema 时，只交回拟增加的内容与能力请求，保留原话项目，不宣称已完成放置。素材里的环境声与动作声继续按现有音频用法处理。

本 Skill 负责准确台词和可供导演深化的主要画面过程。镜头、美术、运动与声音专项继续完成各自设计；作者不代替总导演决定整片最终采用稿，也不擅自执行正式项目写入。

## 先读取当前任务

读用户要求、总导演当前方向、目标观众、必须回答的问题、可改与锁定范围，以及已采用的事实和材料。已有稿件和配音必须区分当前版本与硬约束；存在一份音频不代表其长度不可调整。

材料充分时先看实际内容，找出完整动作、重要差异、具体条件和真实反应。材料不全时可以开始构思，同时交回具体研究与素材请求。不要等待“所有素材齐全”，也不能把想象中的资料和操作写成已取得证据。

首次需要从题目发展成稿，或当前稿件主要是并列知识点时，读取 [写作与改稿方法](references/writing-methods.md)。
采用“提出疑问—实际操作—按结果判断”的讲述方式时，完整读取 [浏览器核对教学例](references/browser-investigation-example.md)。
以人物或日常行为为主体时，完整读取 [日常观察教学例](references/daily-observation-example.md)。
借鉴示例的判断与改稿过程，按当前材料重新写作；不要只替换对象名，也不要把示例中的假设结果当作事实。

## 先找到可以展开的内容

把主题写成观众能跟随的一项具体关注：要完成什么操作、辨清什么差别、核对什么说法、跟随怎样的经历，或认识怎样的人与空间。接着试写实际开场与紧随其后的发展，确认第一段能带动下一段，而不是只产生一句吸引人的标题。

对重要材料明确：实际出现了什么；它回答了哪部分问题；它改变了什么判断或产生了什么下一步。由这些发现安排主线。可以使用条件变化、层层深入、行动结果、有效比较、逐步积累或空间发现，不强制疑问、反转、冲突与升华。

向研究与素材专项提出具体任务，例如“取得从点击到加载结果的连续操作，屏幕内容可辨认”，而不是“找手机视频”。注明这份材料将支撑哪句话或哪次画面变化。候选回来后重新判断主线：新发现值得展开就改稿，原结果不成立就改结论；不要仅给旧稿填入一条素材链接。

## 写完整解说，并同步安排主要画面

先写从开头到结尾的连续口播。每段都要有实际内容发展，不能将知识目录加上连接词直接当作成稿。

写作时同时决定观众大致看什么、哪项变化值得被看见、旁白补充什么。画面能演出的动作可以交给画面；旁白主要补充关系、动机、条件、理解方向和意义。字幕可保留必要复述，重点文字按当前观看任务安排，不把整段答案提前铺满屏幕。

让同一对象、操作或场面承接多句，必要时一句跨多个镜头；句号不决定镜头和 Scene 的边界。所需素材可为连续实拍、录屏、照片、真实页面、原理示意或组合，按表达与事实要求选择，不预设“实拍负责情境、动画负责解释”。

主要画面说明写到导演能继续做分镜的程度：当前看什么、发生什么、重点怎样改变、前后怎样接；不用在此提前规定每个像素或缓动参数。

## 做实际改稿

沿初稿执行以下修改，不只给原稿加修饰词：

- 将缺乏作用的并列介绍删、并或重排，把时长留给本片最有价值的实际过程。重要的“影响、提升、处理”等抽象词，要展开为观众能理解的前状态、变化与结果。
- 将专业术语放在它第一次帮助解释的位置。一个句群需要多个前提时，先建立必要前提，避免旁白在解释新机制、画面却同时要求阅读陌生条款。
- 连续几句都在下定义、列原因或重复结论时，检查是否该进入操作、比较、例证、结果或人物反应；有积累作用的重复保留。不要把所有句子改成反问与感叹。
- 连读口播，把难以一次听懂的长句分开，明确代词指向，删掉空泛铺垫，保留决定含义的条件、单位和限定。不要用夸张语气掩盖内容空缺。
- 将相邻段落首尾放在一起读，修正接不上的关注、重复建立的背景和没有根据的“所以”。并列内容可以直接按共同维度组织，不制造不存在的因果。
- 结尾落在本片真正完成的认识、选择或感受上；必要回顾保留，已经看懂的知识不再完整重讲。没有后续材料时，不承诺下一步即将揭晓。

## 用声音与画面修订节奏

整片决定哪些过程展开、哪些背景压缩；段落安排前提、变化与结果；句群调整口语呼吸和信息落点。用秒表达首版参考节奏，并说明时间主要用于说话、操作、阅读、反应还是体验。秒数不是必须填满的时间槽。

读稿和初步画面能够判断时先修订，必要时由主任务组织临时配音或代表段试排。实际声音回来后，检查口语是否自然、关键画面是否有时间发生、文字是否已经可读、声音与画面是否争抢注意。技术合成成功不能代替这些判断。

需要修改时交回准确的新台词及受影响句群，并说明材料或画面要怎样一起调整。未锁定的稿件和配音可以局部重写、重配或重排；不能自动删掉主要视觉过程以服从第一版 TTS 的长度。已经锁定的声音按授权边界处理。

## 交接合同

交回一份自洽的当前稿，不让导演从多条修改留言拼出最终台词：

1. 完整可读的解说正文；明确无旁白、现场声接管及必要读音说明。
2. 与正文对应的句群声画说明：准确台词、主要画面过程、重要文字与声音分工、当前材料依据和待补项、秒级初始节奏、前后承接。
3. 影响采用的事实与材料缺口，以及缺口会怎样改变台词或主线。已有依据与待查事项分清，不用一份脱离正文的清单掩盖正文里的断言。
4. 本轮具体取舍与修订范围，供总导演统筹；不要求另建评分、句型配额或镜头数量表。
5. 实际输入版本、对象及影响范围；采用后准备符合当前工具合同的完整产物与参数，由主任务提交。声音、画面与稿件已经观察到哪里、哪里仍未知，按真实证据说明。

主任务完整回传给原总导演；总导演决定整片采用、主要分镜和下一轮素材/制作安排。素材发现、专项设计与配音结果改变表达时，继续回本作者修订稿件，再由总导演协调相关场面。不能让下游各自删句、换结论或补画面来掩盖同一份稿件的问题。
```

### 4.2 新增参考 `references/writing-methods.md`

将本小节下列十项方法保存到新 Skill 的这个参考文件。它教“为什么这样写，以及具体怎样改”，从主题成稿或结构性改稿时读取。参考观察来自已有拆解；它们不构成每条视频必须满足的固定结构。


#### 1. 把题目变成一项观众能跟随的任务

**参考观察：** 网速从一个熟悉的卡顿处境进入；浏览器从“到底能不能用”进入。对象和当前疑问都具体。

**为何成立：** “介绍某项技术”没有明确终点；“跟着完成一次核对”让观众知道自己在等待什么结果。

**写作操作：** 先写一小段真正的开场台词，再写紧随其后的实际行动，检查开场是否带得动下一段。把“今天介绍网络的影响因素”改成“页面还没打开，信号格却没变。先看看这两件事到底是不是在说同一件事。”这里的下一步必须真的建立这两个观察的区别。只有口头疑问而无后续行动，不能算完成。

**画面配合：** 第一眼给出能辨认的对象及当前状态；下一画面沿同一关注展开。必要时用示意，但不要把尚未取得的操作素材写成已经拍到。

**适用和失效：** 适合解释、操作、调查与体验。平静记录可以用一个正在发生的行为进入，不必提问。开场承诺超出材料能回答的范围、把主题硬说成“震惊内幕”，会损伤后面所有段落。

#### 2. 从材料中寻找可写的发现，再把发现组织成台词

**参考观察：** 网速片的套餐页面和具体条款改变追问；浏览器的操作结果决定下一句怎样判断。

**为何成立：** 材料能提供具体名词、条件、动作和意外细节。这些东西使讲述具有独特性，也产生真实的后续问题。

**写作操作：** 对准备采用的材料写三句话：“这里实际出现了什么；它回答了原问题的哪部分；它还没有回答什么。”然后写台词。例如不能停在“要看条款”，应推进到“这页写的是满足什么条件以后会改变什么；我们还缺哪项信息才能知道它对当前体验的影响”。没有查到该条款时，这段只能是研究任务，不能以想象的条款补齐成稿。

**画面配合：** 展示足够上下文让观众知道证据来自哪里，再进入关键部分。搜索结果缩略图通常不能直接替代正文；库存手机照片不能替代屏幕上的真实操作。

**适用和失效：** 适合有事实、产品、操作或真实经历的内容。小说化、纯抒情片另按创作边界处理。不能为了验证事先喜欢的结论，只寻找支持它的图片。

#### 3. 建立比较基线，再让一个新条件改变判断

**参考观察：** 外骨骼先建立可举重量，再引入自重；游戏片先让任务完成量成为关注，后来转向自己的时间。

**为何成立：** 新条件不是突然插入一个知识点，而是要求观众重新理解已经看过的内容。

**写作操作：** 写出原来成立的判断及其适用条件，再选择真正改变判断的材料。台词可以先承认眼前优势，再补重要约束。禁止为了“反转”故意隐藏观众理解当前结论所必需的条件，也不把相关性说成因果。

**画面配合：** 保留先前对象或数值作为参照，新条件作用在同一对象上；比较尺度和单位清楚。两张互不相干的标题卡很难形成一次判断变化。

**适用和失效：** 适合取舍、评测、机制解释、人物选择。不是每个主题都有反转；连续成功、空间发现、感官体验也能形成有效推进。

#### 4. 把抽象结论展开成能被看见的过程动词

**参考观察：** 浏览器通过打开设置、改变主题、请求联网来验证；API 通过保留输入、展开后台、显示额外路径来解释。

**为何成立：** 观众能够预测过程、观察结果，讲述因此拥有进行中的东西。

**写作操作：** 在稿中圈出“影响、提升、优先、拥堵、自动处理”等抽象词，问当前观众能看见的前状态、变化和后状态是什么。将重要的一项展开成一组句子，而不是给所有术语都加解释。例如“它会优先处理”还需要知道谁先被送入哪里、另一个对象怎样等待、先后顺序与原论点是什么关系。

**画面配合：** 保持关键对象可追踪，让动作真的到达结果。旁白说“到达”，画面就不能是终点另行淡入一份同色图形；旁白说“变慢”，就需要有可比较的传输变化，不能只换一条文字。

**适用和失效：** 用于本片最需要理解的过程，不要求把每个连接词都演成动画。缺少合法或可取得的实拍时可用明确的原理示意，但不能伪造实测。

#### 5. 按观众当前需要的理解层次释放信息

**参考观察：** API 先有稳定表层参照，再进入内部，随后展开更复杂路径。芯片先是元件，再是板卡和整机用途。

**为何成立：** 新信息总是挂在已经认识的对象上，理解成本较低；深入的理由来自前一层尚未解释的事。

**写作操作：** 将专业术语移到它第一次确实帮助解释的位置。先用可辨认的行动或关系建立对象，再给名称和必要限定。删除“先把所有名词介绍完”的长前言。上一句已经回答的问题，下一句要么深入、验证、限制、应用，要么自然结束。

**画面配合：** 随解释进入对象内部、改变观察尺度，或切到具有明确关联的新材料。保留必要参照，不要求所有解释都使用一镜到底或变形。

**适用和失效：** 适合机制和系统说明。熟悉领域的专业观众可直接进入较深层；紧急操作指南应先给明确动作，不能为了悬念推迟有用答案。

#### 6. 让旁白、画面和重点文字各承担确切工作

**参考观察：** 游戏片大字跨句保留，底字幕继续推进；外骨骼三窗内部动作持续，标签依次引导。浏览器录屏本身提供操作证据。

**为何成立：** 观众不必同时阅读三份不同表述，也不会听一句抽象结论、看一张无关插图。

**写作操作：** 写稿时旁边就注明：这句让观众看什么；声音补充画面看不出来的哪层意义；哪些字必须读清。画面已经清楚演出的动作可以少解释，把旁白留给动机、关系、条件或意义。必要的字幕复述用于理解和无声观看，不机械删除。

**画面配合：** 同一场面可以连续承接多句；一句也可以跨镜头。画内重点文字只保留对当前关注有作用的内容，不能同时出现全段结论列表。

**适用和失效：** 适用于各种解说；无障碍描述、教程细节仍可能需要明确说出动作。不能为追求“声画不重复”，把理解信息拆得过碎，导致只听或短暂漏看就完全断线。

#### 7. 用句子的工作变化形成节奏

**参考观察：** 网速片中现象、机制解释、对自己的追问、查找与修正交替；浏览器在怀疑之后连续操作，不重复发表怀疑。

**为何成立：** 单调往往来自十句都在下定义或下结论，单纯把长句切短并不会改变这种单调。

**写作操作：** 在改稿时临时标记每句的功能，例如观察、提出行动、解释、限定、判断、感受。连续几句功能相同且没有积累时，实际删、并、挪或补一个过程。通常先让一句提供明确方向，再让下一句展开，遇到重要结果给短而清楚的判断；这些选择按内容决定，不设长短句比例。功能标签只帮助编辑，不必进入正式项目字段。

**画面配合：** 观察句让观众辨認；行动句提前指向操作；解释句追踪关系；结果句在结果已可見时落下；需要看清的文字期间减少其他竞争信息。不能逐句都做一次主体进场。

**适用和失效：** 适合多数解释和叙述。故意重复可以建立幽默、负担或韵律，应保留有用重复。不能把每句都改成反问、感叹或悬念。

#### 8. 整片、段落、句群分开调节快慢

**参考观察：** 参考既有密集机制段，也有条款阅读、驾驶体验和稳定多窗。节奏不等于持续高速变化。

**为何成立：** 观众接收一句新信息后，需要辨认、比较或感受；如果所有段都同样密、同样响、同样动，重点会消失。

**写作操作：** 整片确定哪些过程值得展开、哪些背景压缩；段落确定何处建立前提、何处见到结果、何处需要吸收；句群调整呼吸、重复、转折和信息落点。先按自然口语读，再同画面连看；只有真正可读、可辨认后才计算必要停留。秒数是首版预计，实际配音和画面回来后重排，不给每段平均分配时长。

**画面配合：** 复杂新画面出现时，旁白可先引导一个重点；关键原声和实际动作可以短暂接管；读条款时无需让旁边主体持续漂移。若是用户已锁定旁白，则在既定时间里调整内容覆盖、画面接管和信息密度。

**适用和失效：** 适用于所有片型。不能把“有停留”一律视为空等，也不能用背景微动证明停留有价值。配音重音与停顿最终需真实听审，不靠标注文字认定实现。

#### 9. 让段落结尾改变下一步，而不是每段重新开场

**参考观察：** 网速先解释影响，再转向自己的卡和条款；API 深入后仍保留同一消息路径；直播人物离开后，观看关系继续发展。

**为何成立：** 观众不必每隔几秒重新理解另一张说明卡；前一段的产物成为后一段的起点。

**写作操作：** 将相邻两段首尾放一起读，检查后一段究竟接住了前一段留下的哪件事。没有联系时，删去无效桥句、改变顺序、改成明确的并列比较，或承认已进入另一部分。不能只把“另外”换成“所以”伪造逻辑。

**画面配合：** 可由同一对象、实际动作、保留问题、声音或地点承接；有充分关系时也能直接切。跨段持续的东西只保留确有用途的部分。

**适用和失效：** 适用于连续叙述；合集、清单和主题并置也可以成立，应清楚组织共同维度，不强造因果关系。

#### 10. 结尾兑现当前承诺，减少重复总结

**参考观察：** 各片通过核对、真实用途、观点变化或体验落点完成局部段落，不是所有段落都重复知识清单。

**为何成立：** 一次明确的认识、可执行选择或感受，比再次朗读已经看过的所有知识点更有结束感。

**写作操作：** 先写“看完这一段，观众已经实际知道或经历了什么”，再保留仍有用的一句结果。若给建议，要对应片中已经展开的情况，不能在最后突然追加一串没有展示过的操作。结论范围要与证据相称；证据只排除一种可能，就不要说已查明全部原因。

**画面配合：** 停在能确认结果的实际状态、前后差异或反应上；需要余韵可保留真实动作与声音。不要为了达到预设总秒数再停一张结论卡。

**适用和失效：** 教程可保留必要步骤回顾，复杂内容可给精炼总结。重点是总结是否帮助用户形成行动或理解，不能把任何重复都删掉。


### 4.3 新增参考 `references/browser-investigation-example.md`

本小节提供完整正文。它适合疑问、操作、结果与判断类题材；材料 A—D 是教学假设，不是可提交项目的 Asset ID。


#### 1. 用户需求

> 给普通观众介绍一个在网页里操作的复古桌面，做成带解说的视频。希望好懂、有实际体验，不要只介绍一串功能，也不要替产品做夸张宣传。总时长没有硬限制。

总导演给文案作者的初步范围：围绕“外观复古之外，实际能做什么”展开，采用真实操作与资料。先写能支持整片初步分镜的声画稿，再根据素材和试听修订。

#### 2. 作者先提出的研究与素材问题

此时不预先写“它就是套皮”或“它完整复刻了系统”。先查清：

- 网页的作者怎样描述它，明确支持什么，是否说明不支持的部分。
- 哪些操作可以连续完成，能否取得从点击、输入到结果的录屏；窗口出现与功能可用是两件事。
- 如果出现报错，是否有足够上下文；这次失败能证明什么，不能证明什么。
- 这次展示最值得保留的过程是什么，是否足以撑起所选关注点。

给素材专项的请求应当是具体过程：保留浏览器上下文的桌面录屏；打开设置并改变主题的完整操作；实际输入并得到结果的应用录屏；与操作相关的作者说明全文及位置。不是“复古电脑、键盘、程序员”三个搜索词。

#### 3. 教学假设：已经取得并核对的材料

**下面是为了演示写作而设定的一组假设材料，不是本项目已下载的文件，不是对真实参考片的逐字记录。正式任务必须用实际材料替换；不能照抄表中结果冒充实测。**

| 教学材料 | 假设实际可见或可读的内容 | 能支持的台词范围 | 不能支持的结论 |
|---|---|---|---|
| A，连续桌面录屏 | 浏览器标签与网页桌面同屏；可以打开设置，换主题后窗口和任务栏改变 | 桌面位于网页内；本次主题操作产生了可见变化 | 不能仅凭外观判断内核、模拟器或完整系统兼容性 |
| B，应用录屏 | 在页面内计算器输入一项简单算式，显示对应结果 | 展示的计算器在本次操作中可以响应输入与计算 | 不能推断其他程序、全部运算与任意旧软件都正常 |
| C，访问录屏 | 在网页里的浏览窗口尝试打开某页面，出现明确错误提示 | 这次访问没有成功，可以描述原始提示 | 不能单凭它认定所有网络功能都不支持，更不能编造失败原因 |
| D，作者说明 | 为教学假设，说明只承诺桌面交互与部分内置应用，没有承诺完整软件兼容 | 可以按作者实际措辞说明项目范围，区分展示功能和未作承诺的能力 | “没有承诺”不等于“永远做不到”，也不能扩大成质量评价 |

真实任务中的材料记录要保存对应来源或项目 Asset 及实际范围。此处 A—D 仅用于讲解，不是要开发的新字段，也不是实际可提交的素材 ID。

#### 4. 平铺版本

> 这个网站有一个复古的桌面，支持更换主题，还可以使用内置应用。它的界面很还原，部分功能可以正常使用，但也有一些限制。下面我们依次看看桌面、设置、计算器和浏览器。

问题并非文字太短，而是它先宣布“有功能也有限制”，然后把四个界面依次播放。下一句只是在增加一个功能名，没有形成一次可跟随的认识过程。

#### 5. 采用什么发展关系

这一版选择从外观进入实际操作，再区分“某项功能确实可用”和“完整系统兼容”两种不同结论。

作者首先让观众认出网页里的桌面，随后跟着做一组逐渐深入的操作。访问失败让讲述转向证据范围，作者说明补上项目本来承诺什么，结尾回到观众应当怎样理解这次体验。

这是按当前材料作出的选择。如果实际功能或说明不同，主线和结尾都要跟着改；不能为保留这一套故事而寻找或制造一次报错。

#### 6. 完整口播稿

> 这张旧桌面，藏在一个浏览器标签里。
>
> 图标做得像，倒不稀奇。点进去，还能不能用？
>
> 先换个主题。窗口和任务栏，真的一起变了。
>
> 再打开计算器。输入、运算、结果，都能接着做。
>
> 到这里，它已经不只是一张可以点的图片了。
>
> 但能用这几个功能，还不等于搬来了一台完整的旧电脑。
>
> 我再试着打开一个网页。这一次，没有成功。
>
> 原因先不猜。回到作者说明，它承诺的是桌面交互和部分内置应用，没有说所有旧软件都能运行。
>
> 所以，这个网页最有意思的地方，是让你重新操作这张旧桌面。至于想用的某个程序能不能跑，还得单独确认。

这是基于 A—D 假设材料的一版可试排稿，并非已经证明比所有其他写法更好。最后一句完成“该怎样理解它”的观看任务，不承诺一份本片没有展开的完整评测。

第一人称操作只适用于确实为本片进行了该操作的情况。采用外部作者录屏时，改为“录屏里接着尝试打开网页，这一次没有成功”，并保持来源语境；不能将他人的操作说成“我试了”。

#### 7. 句群与主要画面怎样对应

| 句群 | 在讲述中完成什么 | 主要画面过程与注意位置 | 旁白、文字、原声如何分工 | 节奏处理 |
|---|---|---|---|---|
| “这张旧桌面……浏览器标签里。” | 建立可辨认的反差和当前对象 | 旧桌面先可辨认；浏览器边界也能看清，必要时从局部拉开到含标签的位置 | 旁白指出关系；不再打一整段“网页复刻操作系统”结论 | 给到足以认出两层界面的时间，避免快速切换多个复古画面 |
| “图标做得像……还能不能用？” | 把观看转成实际核对 | 同一桌面继续，光标准备进入设置 | 台词只提出接下来的行动方向，不连续追问多次 | 问题说完就进动作，不等待固定悬念时长 |
| “先换个主题……” | 用一个直接结果建立第一层认识 | 保留打开设置、选择主题、全局变化；窗口和任务栏可同时辨认 | 可轻微指认变化区域，真正变化仍由原录屏提供 | 点击到结果需要看得清；操作已熟悉后可压缩重复菜单路途 |
| “再打开计算器……” | 从外观变化走到输入响应 | 同一空间打开计算器并做实际输入；必要时只放大当前应用，仍保留来源关系 | 旁白补“输入—运算—结果”的联系；不用大字幕遮住算式 | 实际输入与结果决定长度，不能只播应用图标和打开瞬间 |
| “到这里……” | 让观众确认刚才积累起来的认识 | 计算结果继续可见，可以略退回桌面，不必换总结卡 | 一句判断足够，底字幕完成口播复述 | 给结果短暂确认，随后继续，不拖成长结论停留 |
| “但能用这几个……” | 区分局部可用和完整兼容 | 保留已经验证的应用，同时进入下一项实际操作 | 台词承担限定，不能用黑红警示画面暗示产品欺骗 | 限定应自然接上已知结果，不突然加快读过去 |
| “我再试着……没有成功。” | 展开一次更深入的操作及真实结果 | 访问操作到错误提示连续可追踪，提示关键内容可读 | 现场提示声如有可保留；不新增假错误弹窗或夸张失败音效 | 真正结果出现后再落下判断，避免先说失败、画面仍在操作 |
| “原因先不猜……作者说明……” | 按资料约束结论范围 | 实际说明页先交代出处，再进入有关支持范围的段落；保留必要上下文 | 旁白概括，关键原文可短暂高亮；不全屏同时放三份大段文字 | 信息量较高，画面先到可读位置，旁白读到重要限定时让注意集中 |
| 最后一句 | 给出范围明确的观看结果 | 回到仍在运行的桌面或当前应用，接住开头对象 | 不再列桌面、设置、计算器、浏览器清单 | 结论读清并完成自然收势后结束；不为预设总长补空白 |

表中句群不是固定镜头、固定 Scene 或固定长度。首版大约秒数应在取得实际源范围并读稿后填入；如果总长过长，先判断哪些过程值得保留，不能将整段统一倍速。

#### 8. 材料不足时怎样实质改稿

**情形 A：只有录屏，没有作者说明。** 删除涉及作者承诺的台词；不能把一般常识冒充这个项目的实现说明。完整后半段改成：

> 到这里，换主题和计算器都能接着操作。
>
> 再试着打开一个网页，这一次没有成功。
>
> 但这次失败，解释不了整个项目是怎么实现的。
>
> 目前能确认的，就是刚才实际走通的这些操作。想把它当成完整的旧电脑，还需要继续核对软件兼容和其他功能。

原稿的“查资料获得范围”变成“明确本次体验能证明到哪里”。如果片子的承诺本来就是解释实现原理，这份材料仍不足，必须继续研究或与导演协调收窄主题，不能把上面这段冒充原任务已经完成。

**情形 B：没有访问失败，只有主题和计算器两项连续操作。** 不为制造起伏剪出一个假故障。将中后段改为：

> 窗口和任务栏一起变了，计算器也能接着输入和运算。
>
> 这就比一张复古截图多了一层：你能在里面做事。
>
> 但这次我们只看到了这两项功能。它能不能运行你记忆里的那个程序，不能凭这几个画面下结论。

整段转成一项功能体验，实际可用的过程得到更多展示空间，不必硬凑调查结构。

**情形 C：只找到一张桌面截图。** 不能继续说“窗口跟着变了”“可以计算”。先向素材专项请求可操作网页或连续录屏；如确实不能取得，由导演决定改做界面设计赏析、换一个能实际体验的对象，或暂缓这一段。不用库存键盘、老电脑照片掩盖关键过程缺失。

#### 9. 配音与画面回来后怎样修订

如果计算操作很短而台词偏长，先改为“再算一笔，结果也出来了”，保留观众看得见的过程，不把原录屏长时间冻结。

如果作者说明较长、实际高亮后仍读不清，应减少本段引用的信息，只保留足以支持结论的一段并给阅读时间；不能让配音高速扫过，也不能缩小成无人能读的纸片。

如果实际试听中“但能用这几个功能，还不等于……”显得突兀，可前移一个明确的测试目标，或减弱过度对抗的语气。修订的是准确台词和场面，不只写“语气更自然”。

是否需要这些修改，应由真实配音和连续画面判断。教学文字本身不证明表演与节奏已经通过。


### 4.4 新增参考 `references/daily-observation-example.md`

本小节提供完整正文。日常、人物行为与情绪观察使用此例理解怎样减少旁白、保留真实行动；不要机械照搬误会结构。


#### 需求与材料条件

用户想记录猫把球叼来找人互动，允许少量旁白，保留日常感。教学假定有真实先后发生的镜头：球放到脚边；人把球放回篮子；猫后来再次叼来；人把球滚出去；猫追球。不能重复播放同一个动作冒充“又来一次”。

#### 平稿

> 我家的猫很喜欢玩球，经常叼着球过来。有空我就陪它玩，非常可爱，也能增加互动。

#### 完整改写稿

> 它又把这个球放到我脚边。
>
> 我以为是落在外面了，就顺手收了回去。
>
> 过了一会儿，它又叼来了。
>
> 这回，我没有收。
>
> 我忙着把球放好，它大概只是想找个人玩。
>
> 这一次，球没有再放回篮子里。

#### 声画与节奏

前两句跟随同一个球从脚边进入篮子，第三句依靠第二次真实行动形成认识变化。第四句结束后，让人滚球、猫追球的实际过程接管，旁白可以暂时停下；第五句才轻轻表达新的理解。结尾落在继续互动的真实状态，不补一段道理总结。

它同浏览器例共同借鉴的是“观察与行动让认识发展”；具体语气、句子数量和画面密度完全不同。日常体验不用科研式证明，也不把动物动机写成确定的心理结论。

#### 只有一次叼球时怎样改

删掉“又”和整段“误解—重复—理解”的故事，改为跟随这一次实际行动：

> 球先到了，我才看见它。
>
> 放下以后，它还站在我脚边。
>
> 那就先玩一会儿。

后面用真实追球与环境声继续。若素材没有“站在脚边”等状态，连这句也按实际画面重写。少写几句、保留真实体验，比用无关镜头补齐一套精巧故事更可靠。


## 5. 接入现有导演、协调与正式 Script 链路

### 5.1 正式文稿怎样提交

`apps/server/src/mcp.ts:1085–1113`：

```text
project_id：可选；提供时必须为真实项目 ID
base_revision_id：必填，正整数，使用刚读回的项目版本
source_note：必填，1～2000字符，描述真实新稿来源
units：必填，1～200个完整语义段

每个 unit：
  text：必填，1～2000字符
  kind：必填，以下之一：
    statement / question / answer / cause / conclusion / contrast /
    list_item / setup / payoff / retake / intentional_repetition
  dependencies：可选，实际语义对象 ID 数组
  preceding_context：可选，最多2000字符
  following_context：可选，最多2000字符
  confidence：可选，0～1
  pause_before：可选
    duration_ms：0～10000 的整数
    reason：sentence / contrast / emotion / breath / chapter
```

unit 是 strict 对象，不允许随意附加 `visual_plan`、`narration_direction`、`source_url`、`duration_seconds`、`full_script`。分镜说明、来源列表和表演说明通过完整交接及对应现有对象保存，不能塞进 `text` 让 TTS 一起朗读。

`units` 是完整语义段，不等于一段一个镜头，也不等于每句必须独立 TTS。文稿作者完成专业分段和语义核对，不应由协调者在装配时自行删改、压缩或拆成碎句。尚未产生的语义对象不能用草稿段号冒充真实 `dependencies` ID；可以先通过上下文说明依赖，写后用真实 ID 建立 Story 等对应关系。

这条命令是**整稿替换**。只改一段时，提交的仍然是采用版完整 units，而不是把那一段当追加文本发出。首次新稿无需音色 Asset、转写候选或虚构时间戳。用户已经有真实口播、且任务是编辑原话时，继续用候选与语义编辑入口，不能用 authored 抹掉真实来源。

### 5.2 改稿后，哪些下游要重新确认

依据 `packages/edit-application/src/index.ts:4548–4612`、`:4672–4705`：

1. `applyAuthoredScript` 根据文本一对一复用已有 authored SemanticUnit 的 ID；重复句仍保持不同身份。新改文本生成新语义身份。
2. 替换语义列表；从已有 StoryBeat 关联中移除已不存在的语义 ID。新增语义不会自动被合理分配给原来的 StoryBeat，需要导演/负责专项确认并更新。
3. `reconcileScript` 重新编译 SpeechSegment。语义身份和文本未变时可以复用原 Segment ID；相应已有段音频可继续保留供重新组装使用。
4. 当前 `speechAsset` 被清空，旧系统旁白在 Dialogue 上的 Timeline Item 被移除。即使部分段音频可复用，也必须按新稿重新组装完整旁白。
5. 当前词级对齐失效并清空。非 `source_audio` 的旧字幕移除并进入 stale；真实原声字幕不因原创脚本变化被误删。
6. 与旧 Script 版本不符的生成式 ActorPerformance 被标记 stale。
7. 绑定已消失 SpeechSegment 的 EffectCue 被标记 stale；不是所有视觉内容都能仅凭该自动标记获得完整语义复核。
8. 主声音相关音乐、Duck 与音效通过 `staleAudioCuesForMainline` 失效，需要重新确认。

因此可写“优先复用未改段音频，按真实 Impact 重组和复核”，不能写“改一句就只重做一句，其他自动不受影响”，也不应反过来要求每次全片全部重生成。当前代码只能保证部分依赖失效，意义变化、画面与新台词是否仍相配需要原负责人判断。

`tests/authored-script.test.ts:49–66` 包含改稿后旧 SpeechAsset、系统 Dialogue 和字幕失效、历史版本可读的测试覆盖。源方案及本次文档整合均未运行这些仓库测试，不能把读取测试源码写成当前版本已通过。开发需实际运行相关测试，并检查正文改变后的 StoryBeat 分配、画面语义、声音重组和当前 Impact；这也不等于某条实际影片会完全自动局部重剪。[S11](#audit-s11)

```text

【导演给出的完整任务、用户原始要求与锁定范围】
【当前准确稿件、实际材料、已查看范围及来源；待核与待取得分别标清】
【实际 Project / 输入 Revision；已有相关预览和具体反馈】

先判断这条内容最值得经历的观察、比较、过程、调查或感受是什么。
不要将主题自动展开为“定义—原因1—原因2—建议”的知识目录。
若原有并列结构最合适，可以保留，但要明确比较关系和观看进展，

已有依据先写，缺失部分标明会影响哪句话和哪段画面；
不把未取得的材料描述成已经看见或亲测。

交回以下完整产物：
1. 简短说明采用的讲述角度、观众关注怎样发展、结尾回应什么。
2. 从头到尾可直接朗读的准确解说正文。
3. 和全文逐段对应的声画稿：准确台词；看见的具体对象与变化；
   画面、语言、原声各自承担什么；实际材料或待找过程；
   必要的辨认、阅读、反应与下一段接点；大约秒级初始节奏。
   同一场面可跨多句，不按每句换一个镜头。
4. 影响采用的事实/材料缺口，以及取得不同结果后要怎样改稿。
5. 若导演要求提交当前采用版本，按实时 apply_authored_script 合同准备完整 units；
   朗读正文与内部设计说明分开，不填不存在的接口字段。

每次关键材料或预览返回，核对实际结果是否改变讲述。
需要修改时交回完整新稿及具体差异；不只给建议列表。
用户未锁定总长时，秒数是初始设计，不为了既定总长重复解释或留空等待。

只返回专业产物与执行参数；正式项目写入、配音与渲染由主任务统一提交。
```

### 5.7 正式提交次序与能力边界

正常执行时，导演采用当前完整稿后，主任务读取当前 Revision，再提交完整 `apply_authored_script`，读回 Script、真实语义/Segment ID 和 Impact；文案作者核对正文，导演/Scene 专项据真实 ID 更新对应 Story 与场面；声音生成后依据真实时间重排，继续原流程。不要并发提交几个都会变更项目 Revision 的写入，也不把首次生成 TTS 作为用户未要求的时长锁。

上述提交顺序适用于纯原创稿或用户授权整体转为新解说的任务。`apply_authored_script` 会整体替换语义列表；当前 `apply_semantic_units` 又要求真实转写候选。本轮未核到同时保留真实原话身份、再插入 authored 单元的统一入口。因此本轮不把“在真实口播 Script 内插入新旁白”列为已支持的正式路径，也不要求开发顺手重构混合脚本模型。遇到该任务时保留现有原话，交回具体新增内容与受影响范围，单独明确最小混合写入扩展后实施。已有素材的环境声配合一份纯原创旁白，不属于这个混合 Script 问题。

仍需要明确的三个能力边界：

1. 完整声画长稿的跨会话持久化：当前宿主全文交接有效，但现有报告不等于全文存储；若作为产品功能要求，需要单独最小扩展。
2. 自然语言的句中声画落点：文稿可设计，但现有 segment_exact 只能证明段级真实时间。没有实测更细时序时，不声称每个词已精确同步。
3. 真实素材可取得与否：写作 Skill 可以提出研究和镜头请求，不能凭指令补齐搜索/下载/感知工具缺口；实际能力不足应返回具体事项，不将所有内容默默改成通用图解。

## 6. 素材研究、检索与获取如何落地

### 6.1 采用哪一种接入方式

**默认：在 VideoFlowCut 的正式 MCP 内发布来源搜索、原文读取和选定材料获取入口。搜索/原文读取由一个 Tavily HTTP client 对接托管 API；页面截图复用平台已部署的 Chromium；现有视频 Provider、Asset、EvidenceCapture、Job、素材观察和采用链继续使用。**

不要求用户再部署 Docker 或另一个爬虫服务，也不为每个网站实现一套 Provider。需要配置 Tavily Key，调用有 API 费用；本方案不代表已经配置、购买或启用。以后替换搜索服务，只替换该 client 的适配，不改变解说、导演与素材的交接。

这符合当前 AGENTS 的正式剪辑边界：开发任务实现、测试、发布能力；原剪辑任务重新读取 MCP Schema 后使用。不能在搜索工具缺失时，让剪辑代理临时用 shell、HTTP 或浏览器脚本绕过。宿主 Web/browser 可以用于本次开发研究，但不作为正式剪辑的隐式备用通道。无需为这项接入放宽 AGENTS。

Tavily Search 与 Extract 分别负责发现和正文提取。Search 关闭自动答案（`include_answer=false`）；Extract 不带 query，获取页面正文而非仅与某个提问相关的片段。原文提取失败逐 URL 返回，不用摘要替代原文。Extract 不等于截图、网页交互或视频下载。

源方案记录的官方接口依据（本次合并未重新联网核查）：
- [Tavily Search API](https://docs.tavily.com/documentation/api-reference/endpoint/search)
- [Tavily Extract API](https://docs.tavily.com/documentation/api-reference/endpoint/extract)

#### 拟新增工具的最少输入与输出

以下是建议的工具合同，**不是当前可调用 Schema**。

`search_sources`：输入项目、查询，可选域名范围和当前确有必要的时效条件；返回有来源 URL 的结果列表、标题、来源类型、可取得的摘要、时间信息及失败/不完整说明。返回摘要是发现依据，不是已读原文。工具可以接受产品名、动作、拍摄形式、官方站点限定等查询，不限定于 Stock 图库。

`read_source`：输入来源 URL；重复读取可使用返回的缓存引用与后续文本位置。返回最终来源 URL、标题、提取时间、正文内容及原文定位信息（服务确有提供才填写）、实际覆盖说明和失败原因。完整保存本次服务返回的正文到项目 `cache/source-research`，单次工具响应可以分页；分页读完只表示本次提取结果已读完，原网页的实际覆盖还需结合原页核对，无法确认时保留未知。不能因 HTTP 成功或没有 query 就断言整张网页正文完整，也不能静默截断。缓存引用由平台产生并校验项目归属，不接受任意本机路径。

`acquire_source_material`：输入当前 Revision、已选 URL/研究引用、类型（公开网页快照/直接 PDF/直接图片）、真实来源及使用依据；返回 Job ID。完成后返回 Asset ID、来源 URL、取得时间、哈希、实际截图范围或原文件身份、媒体分析 Job。它不直接建立 Scene、EvidenceCapture 或 Timeline。

这三个入口分别做“发现、读取、取得”，不建立第三套素材状态机。搜索和正文缓存是操作资料，不装进每次 ProjectSnapshot；已有 Asset/Provenance/EvidenceCapture 保存正式采用的必要信息。

### 6.3 从搜索请求到材料进入讲述的操作顺序

**前期没有分镜，仍然可以使用现有素材搜索。** 当前 `manage_asset_requirements` 创建需求只需真实项目和版本，以及 `action="create"`、`title`、`purpose`、`visual_brief`；不要求 Scene、Beat 或固定时长。下面是专业任务的示例内容，不是虚构项目 ID 的可直接执行请求：

```text
title：寻找可展开的真实操作
purpose：判断哪个操作过程能支持本片主线
visual_brief：寻找能看清输入、操作、等待和结果的连续记录
```

主任务以当前真实 Revision 创建需求，读取返回的新 Revision 和 `state.snapshot.assetRequests` 中的新需求 ID，再调用 `search_media_candidates`，提供该 ID、当前版本、实际 Provider、query 和需要的 `media_type`。需要视频时明确传 `video`，不让默认混合结果替代视频探索。需求中的默认 `fallbackPlan="keep_presenter"` 不等于导演已经同意放弃原表达。

拟新增的 `search_sources` / `read_source` 不需要先建 AssetRequest，使用真实 Project 承载研究缓存即可；尚未建项目时先按原协调流程建项，不编造项目 ID。现有探索需求入口的依据是 `apps/server/src/mcp.ts:684–729` 与 `packages/edit-application/src/index.ts:2598–2629`。

1. **用户需求进入项目后，导演给解说规划专项初步范围。** 文案专项交出想发展的主线、必须核实的疑问和可能的可视过程，此时未锁定全文台词、Scene 或所有秒数。
2. **主任务分派研究/素材专项。** 同一专项可执行事实来源和画面候选探索，避免把“找依据”与“找画面”变成互不交流的流水线。
3. **先看现有材料与真实能力。** 读取项目素材、已观察范围、Provider目录及研究入口状态；已有原片能回答的问题不重复全网找。缺能力由正式修复处理，不把不可用工具当做找不到内容。
4. **并行探索互不依赖的方向。** 事实/规则通过 `search_sources → read_source`；公开实际操作/记录也用来源搜索定位单页；通用生活镜头可直接走 Commons/Pexels；用户原片使用已有观察与 `search_media_fragments`。不机械要求每次搜齐全部方向。
5. **先向文案专项和导演回传真实发现。** 回传原文或已观察过程、来源、支持到哪一步、候选范围、与原设想不一致的地方、可发展的下一问题。不要只交一串 URL，也不要把下载成功等同采用成功。
6. **文案专项据材料写声画稿，导演确定采用方向。** 正文台词和大致观看过程一起回来；材料支持原稿可以保留，材料改变判断就重写相应台词。无需强制每次改稿，但要能说明实际材料怎样参与判断。
7. **对采用方向定向取得。** Commons/Pexels 已是 Candidate，按既有获取；YouTube先把选定 URL 交其 Provider；公开网页/PDF/图片用新获取入口。仅为研究的来源无需全都下载成为 Asset。
8. **查看原文件，交可执行的源范围。** `analyze_media → track_job → read_media_observations`用于定位，必要实际范围用`inspect_asset`/已提供的连续观察复核。确认动作、文字、声音、前后余量和裁切后，`adopt_media_fragment`保存采用依据。网页证据实际截图/文件取得后登记 `manage_evidence_capture`。
9. **回到声画稿和导演。** 原文件与预览不一致、构图不适合或动作被剪断，回原素材专项/文案专项调整；不直接用一张相关照片悄悄替换原先的真实操作。导演决定继续找、改变过程或改变表述。
10. **Cutaway/动效/声音细化并进入成片。** 素材专项不规定统一小窗。具体使用方根据观察重点与素材内容决定全屏、局部放大、同屏比较、受管动效绑定和原声；放置后沿既有 `bind_media_adoption` 关联实际用途。

默认收敛依据：关键观察、事实和过程已有可取得、可读/可看材料，足以试排当前故事；继续找只增加同功能替代品时可停止。未解决的是内容缺口、文件取得失败还是正式采用未完成，分别明确。搜索次数和素材数量不是收敛依据。

#### 一次交回应该写成什么

> 目标：表现点击导出后，并非立刻得到文件。
> 实际发现：某真实操作片在选定范围内连续显示按钮状态变化、等待和结果出现；具体源时间以原文件复核填写。官方帮助页说明该功能的处理步骤，但没有给出固定耗时。
> 文案影响：可以写“按下按钮后，处理还在继续”；不能写“后台固定需要十秒”，也不能凭进度动画猜测内部算法。
> 画面方向：从原界面的操作进入，保留同一状态框作为锚点，图形补充原文支持的关系，再回到同一次操作的实际结果。
> 剩余：需要取得完整视频，确认等待未被原片剪接；若只取得示意录屏，改为明确示意而不冒充测量。

这里没有假定示例文件已取得。这个交回同时能用于文案、导演、动效与后续审阅。

##### 旧结果升级：Provider 修好了，也不能继续返回旧 JPEG 会话

已核查的 `recordAssetSearch()` 会在需求版本、Provider、query、mediaType 相同，且未过 30 分钟、结果完整时直接返回旧 `existing.candidates`，不采用本次新传入的候选。因此，旧版写入 JPEG 封面后，即使新版 Provider 返回 MP4，同一项目再次搜索仍可能得到旧 JPEG。需要同时满足上述缓存条件，并非每次升级必然失败。[S01](#audit-s01)、[S03](#audit-s03)

```text
旧 Provider 返回 JPEG 封面 → 保存新鲜搜索会话
新版 Provider 返回真正 MP4 → 同需求、同查询、第一页再次搜索
应用层若只按旧条件命中 → 返回的仍是 JPEG
本版要求：新结果格式不复用旧会话 → 返回新 MP4 候选并保存新会话
```

**实施规定：** 给操作层搜索会话增加由服务端生成的结果格式版本，用于标识预览语义与候选归一化方式。具体内部字段名按现有类型命名；不是创作代理可填写的新 MCP 参数，不是 Project Revision，也不需要重建 Candidate／Asset 表。

新搜索的缓存资格同时核对结果格式版本与原有条件。缺少该版本的旧会话允许查看，但不具备复用为新版结果的资格；不得在读回时为旧数据补一个“当前默认版本”。第一页新旧 cursor 都缺省时，也必须被结果格式版本区分。新增分页、需求更新和部分结果恢复仍保持各自语义。

| 现有状态 | 升级后的处理 |
|---|---|
| 仅保存在操作缓存中的旧会话 | 历史可读，不作为新格式搜索结果；第一次新格式搜索建立新会话 |
| 已提升到 ProjectSnapshot 的旧候选 | 保留真实身份及已有状态；不要以相同 Provider 原始 ID 覆盖为另一份预览，需要时重新搜索获得新候选 |
| 旧候选的封面／预览观察 | 仍只证明旧 preview 身份及已看范围，不能迁移成“已看过新 MP4 视频” |
| 已排队或运行中的旧分析 Job | 固定输入不静默改写；确需新预览时沿现有流程建立对应的新输入和任务 |
| 已正式取得且通过校验的原视频 Asset | 不因搜索结果格式升级而自动重下或重做历史采用 |
| 同一新版会话再次搜索 | 在版本、需求、页码和媒体类型等条件满足时，正常复用新版缓存 |

**修改位置：** `packages/asset-acquisition/src/index.ts` 的 Provider 结果归一化；`packages/edit-application/src/index.ts` 的 `recordAssetSearch()` 及候选读回衔接；搜索会话类型与 `packages/media-intelligence/src/store.ts` 的保存／读回；必要的旧候选状态说明。它们沿同一个正式搜索入口完成，不新增另一套搜索工具，也不靠清空全部项目缓存掩盖兼容问题。

**本项完成条件：** 预置一个未过期的旧 JPEG 会话，新版 Provider 返回 MP4，同需求同查询的首次新搜索得到新 MP4 候选，随后可命中新版缓存；同时覆盖第二页、不同需求版本、不同媒体类型、部分响应、旧候选查看和旧分析任务不变。上次审计的独立匹配脚本只复现问题，不代表数据库或正式搜索已经修好。

#### D. Pexels 预览类型

问题：`packages/asset-acquisition/src/index.ts:309`把`video.image`封面写入video候选的previewUrl；`apps/job-worker/src/media-understanding.ts:42–44`按候选kind下载，遇到图片MIME会拒绝。

具体修法：Pexels从真实`video_files`选择一个符合现有预览预算、可获取的MP4作为previewUrl；正式下载仍按原有文件选择取得合适原片。没有合适视频预览就省略previewUrl，明确只能先取得原文件再观察，不能把封面冒充video。若界面以后需要封面，可独立引入缩略图信息，但基线核查未发现现有web界面依赖该字段显示候选图，无需为修复提前设计图库组件。

预览下载的允许域名仍按真实媒体来源验证；不为个别URL失败关闭检查。预览分析记录保留preview身份，正式采用仍需要原文件身份与范围复核。

本修复与 6.4.C 的旧结果格式升级作为同一项交付验收：不能只在空项目／空数据库里测试 MP4 成功。必须携带升级前 JPEG 缓存验证正式搜索，再验证受控视频预览分析；不放宽 MIME、文件头或允许来源来让封面冒充视频。[S02](#audit-s02)

#### 配套新增 references/research-and-footage-example.md 的完整示例

目标位置为 `.agents/skills/visual-asset-sourcing/references/research-and-footage-example.md`。下面是完整教学正文；方括号表示任务中的实际对象，不能原样作为未替换的生产查询。

> 任务：给普通观众介绍一个网页内的复古桌面。文案作者想知道，外观相似之外，哪些操作能实际完成；导演希望主要使用真实界面，并用图形帮助观察。
>
> 首先查看用户原片和现有观察。如果原片已经包含主题切换与应用输入，就直接核对这两段的前后范围，外部只补作者说明和缺失操作。不要为了“做了素材检索”而重复下载同类画面。
>
> 如需外部发现，事实查询可以从“[实际产品名] 官方 功能 说明”或限定已确认的作者站点开始。打开实际说明正文，辨认明确支持范围、版本及没有解释的部分；搜索摘要里的“完整复刻”暂时不能作为确定台词。
>
> 画面查询从“[实际产品名] 主题切换 完整录屏”或“[实际产品名] theme change walkthrough”开始。如果候选只是宣传剪辑，只有几个漂亮窗口而没有点击到变化的过程，记录具体缺口，改找“[实际产品名] full demo screen recording”。有合适作者时继续查看其同源完整版本，避免用不同版本界面拼成一次操作。
>
> 若得到的是可下载的 YouTube 单条来源，主任务沿现有单 URL Provider 取得候选。其他站点的链接只有在平台发布了相应取得能力时才可沿该能力获取；不能把“搜索到链接”标为“视频已到手”。取得原片后查看实际操作范围。视频只显示计算器窗口打开时，继续找输入和结果；找不到就把拟写的“计算器可以使用”收窄成“可以打开这个窗口”。
>
> 作者说明足以支持具体结论时，读取相关段落的前后文。需要把原文放入成片，再由主任务取得实际页面快照，并登记来源、摘录和范围；只有正文提取文本时，不能画一个自制页面冒充官方截图。
>
> 给作者和导演的回传应包含：“主题切换有连续操作，可以展开这一段；应用只看到窗口，尚不能宣称输入有效；作者说明只承诺部分内置功能，没有承诺完整兼容。建议先跟随主题变化，再核对一个真正有输入响应的应用，最后按说明限定体验范围。”这是一项会改变稿件的发现，不只是一张素材表。
>
> 如果第一轮已经找到足够材料，可以直接采用和细化。候选缺过程时继续沿缺口找，不要求固定三轮搜索。对同一图库查询需要看更多结果时，使用返回的 nextCursor；换产品、动作词或 Provider 后重新开始查询，不沿用上一个查询的游标。
>
> 最终用于剪辑的范围应保留观众认出界面、看到关键动作和确认结果所需内容。设计先让真实界面成为观看主体，再靠近发生变化的区域；指认图形跟随真实对象，必要解释完成后回到原界面结果。不要将每一条材料都缩进相同大小的窗口，也不要裁掉证明操作确实发生的上下文。

证据专项“当前能力”则改为：已有 EvidenceCapture 登记、高亮和 EvidenceDocument 的相应编译／页面渲染；来源发现、正文读取与材料取得按实际发布状态说明。Cutaway 的“接收已采用方向与选材结果”补充接收本段完整声画稿；“Fit、Crop 和 Reframe”补充按本段观看任务决定观察尺度，不能只为了完整容纳而让关键对象与文字长期过小。既有裁切保护、源范围与声音合同继续保留。

#### 7.2.2 到底什么时候用哪条渲染路径

|---|---|---|

| 实拍要从主画面缩成参照，再与其他内容重新排布，且源动作不停 | 同一受管作品内用 `BoundVideo`；外框、源视频与图形共同设计 | 当前正常速度、静音、最多四路；处理局部帧与源范围，不暗中冻结或循环 |
| 看真实票面、官方条款、网页或截图的局部 | `imageBindings`＋`Img`；原图与高亮放在同一坐标体系 | 先取得真实图片 Asset；不能用模型画的假页面代替原文；阅读与清晰度必须成立 |
| 两个真实过程需要比较 | 采用可比较的实际片段，同屏或顺序显示；需要窗口运动时使用受管视频 | 同条件、单位和时间参照明确；不把不同测试剪成同一次过程 |
| 数字人在讲，图形只需辅助 | 保留人物为主；在实际可用区域做短图形，或由导演安排素材／解释暂时接管 | 不强行永远留一个中央小人物，也不默认每段都让人物退出；无 Mask 不设计穿过身体的遮挡 |
| 原片已经有足够好的动作、构图和节奏 | 直接使用原片，必要时只调整切口和声音 | 不为了调用动效 Skill 把它重新装进一个设备框 |

这是作者作选择的依据，不是新增到 `VisualTreatment` 的六种强制枚举。现有类型字段继续表达当前系统已经支持的值，完整创作说明通过既有交接传递。

### 7.2.3 案例库的“产品扇开”不等于内置 `ProductFan`

基线代码确实存在两条不同路径，不能凭近似名称代替能力核对：

| 路径 | 基线实现 | 对本轮设计的含义 |
|---|---|---|
| 内置 Registry 的 `ProductFan` | `CueVisual` 将至多三张绑定素材放在固定角度、位移上；可以受外层 Cue 的整体运动控制 | 不等于内部产品之间会按案例展开、聚合和回收 |
| 案例 `.agents/skills/motion-case-product-fan/assets/motion.tsx` | 有随帧发展的 `fan / gather / drop`，产品间距、旋转、缩放及数字让位一起变化 | 这是设计与源码教学，应迁移其关系变化，而不是只选同名 Cue |
| `ManagedMotion` | `CueLayer` 读取固定版本 PNG 帧，按作品画布播放，不再套内置模板的通用进出场 | 所需过程由当前完整源码实现；生成、放置和合成分别检查 |

依据：[S06](#audit-s06)、[S07](#audit-s07)。

非 `full_frame` 默认布局下，内置 `DeviceShowcase` 宽度为 26%、最大 360；`ProductFan` 为 32%×27%；`EvidenceCard` 宽度为 31%、最大 500。全屏锚点可以绕过这些默认小尺寸，因此不能说所有模板都只能小窗；但默认值也不应反过来决定本段创作目标。[S08](#audit-s08)

**选择规则：** 简单强调、现有组件确实能够完成的关系继续用现有组件；需要对象持续、构图发展、观察尺度变化或内部真实视频共同运动，而该组件未实现时，沿已有受管原创作品路径实现。保留好的原片，不强迫全片都用 ManagedMotion，也不新增动效引擎。

**验收看实际分支：** 读回代表段的 Cue.type、作品绑定、源码和真实预览。要求展开、聚合与重点转移时，确认对象之间确实发生这些变化；“读取了某案例 Skill”“创建了 ProductFan”或“出现了对应事件名”都不足以证明。默认小窗不适合时调整实现与构图，不在空白处补装饰。

这是路径风险的核查结论，不是对用户问题成片的已证实归因。没有该片实际 Cue、源码和连续预览时，不认定它一定误用了内置模板。

不用让用户填一张新表。下面是**主任务给作者的任务模板**，用于替换“按案例做得高级一点”这种失去内容的交接。

```text

【当前 Project／Revision、Scene／Beat、声音时间及其实际精度】
【已有本片视觉语言、人物／字幕占用、用户真正锁定的内容】

先完成当前内容的场面设计，而不是先挑一个组件填文字。
把主要构图和它们之间的运动一起设计；重要的过渡要用真实材料试作。
同一个真实对象能承担连续发展时让它持续参与；不必每句换素材或换卡片。
材料缺少关键动作时，把缺口交回，不用图标表演冒充实际操作。

1. 一份完整的场面制作说明，包含本段观看过程、具体美术、主要构图、
   动作中途、阅读／观察时机、源视频如何持续，以及前后声画接点。
2. 用实际文字和素材形成的必要关键画面／试作请求；说明实际看过什么。

   按本版秒数换算的 durationInFrames，以及有用的命名事件。

```

**制作说明写到什么深度？** 例如“视频缩小，条款出现”还不够。至少要解释原视频向哪里退、退到多大后仍有何用途；条款来自哪张真实页面；哪一部分首先可读；它如何取得主要面积；两者是否同时抢眼；下一步怎样回到同一观察。需要源码实现的精确值由作者依据实际画幅和材料确定，不能把示例百分比变成全片统一规格。

**关键画面不是静态 PPT 草稿。** 它可以是动作途中的构图，也可以是供阅读的稳定状态。对最影响效果的接点，直接先做包含必要前后过程的短试作；这不是另造一个预览 API，而是按现有作品提交和预览链取得实际证据。试作如果切掉前因或后果，就不能证明完整接点成立。

#### 7.6.1 用户任务、素材条件与讲述

任务：用实际收拾物品的过程，讲清楚“这一次需要带走的是机身加配件的一整套”，不只依次显示电脑、电源和线材三个图标，不做缺少测量依据的重量或价格结论。

假设有一段固定机位的竖屏俯拍：桌面上先有笔记本，人依次放下这次确需携带的电源、转接头和线材，最后开始收纳。镜头本身连续，原画面包含后续配件的位置；不是靠生成模型补出原片未拍到的物品。物品放定后有短暂稳定范围，可供标签指认。

试排台词可以是：

> 只带一台电脑？先把电源放过来。还有转接头、这根线。刚才看的是机身，现在这次要装走的，是这一整套。

这不是所有笔记本的通用携带清单，也不是“这台产品必须搭配所有配件”的结论。实际素材只有电源，就删除不存在的配件；不是本片自己完成的操作，不写成“我实测／我带过”。讲述、来源和使用语境由文案作者与导演确认。

#### 7.6.2 为什么不采用平铺卡片版

平铺版会先播电脑两秒，再切电源图标、转接头图标、线材图标，最后列一张清单。观众得到三个名词，但原片真实的手部动作、物品集合形成和收纳结果都被丢掉了。

本版让**同一段实拍持续发展**：开始主要看机身；配件接近原观察范围时，视野逐步扩大；标签只帮助认出当前物品；一条范围线由机身范围扩展到整套物品；最后图形退让，让真实收纳动作接管。构图由实际物品改变，而不是每句重新建立一张说明卡。

这里借鉴产品扇开的“集合形成和回收”、机票案例的“原对象留场和观察尺度变化”。没有照搬扇形、手机、历史配色或固定总秒数。

#### 7.6.4 首版时序：只示范怎样把变化落实，不当作永久时长

为便于讲解，下面假设实际选段恰好约 10 秒，30 fps。这个“10 秒”不是生产规则；真实收纳需要 15 秒时，不能仅为套用此表把它压成 10 秒。

| 参考范围 | 实拍中实际发生什么 | 画面与图形怎样配合 | 为什么这样安排 |
|---|---|---|---|
| 约 0—1.2 秒 | 机身已经可辨认，手准备带入配件 | 从允许裁切的观察区域认识机身，原桌面仍在 | 先建立明确对象，不先给全部清单 |
| 约 1.2—5.5 秒 | 配件依次进入并落定 | 同一视频持续播放，视野逐步扩大；标签在各物品确实放定后进入 | 真实动作形成集合，构图随着需要改变 |
| 约 5.5—7.5 秒 | 整套物品暂时稳定 | 保留机身参照，范围线从机身扩展至整套；其他标注退让 | 让“机身”到“整套”的关注变化可见，而不只换一句字幕 |
| 约 7.5—10 秒 | 开始实际收纳 | 图形在物品移动前退出，源片继续；结尾由真实动作完成 | 不用示意回收替代现实结果 |

实际计算标签的开始和结束，以原片观察为依据，不根据文案中“电源”一词猜测它已经落桌。若标签与手部冲突，先移动或推迟标签，而不是切掉真实动作。若旁白讲完了但收纳仍值得看，可以让原声接管，不把余下时间叫作“空等”。

#### 7.6.5 坐标与源时钟怎样处理

把整个原画面当作一个“源坐标平面”：原视频、物品位置、范围线都在这个平面里。这个平面使用第 7.8.1 节确定的、方向与宽高比正确的归一化显示坐标；不能把旋转前的编码宽高直接当作旋转后画面的坐标。观察范围改变时，只改变这个平面到作品画布的映射。标签可以通过字号补偿维持最终可读大小，但它与被指对象的归属不能漂移。

假设作品局部帧为 `F`，帧率为 `fps`，素材绑定的起点为 `sourceStartMs`。本例 `BoundVideo` 放在根场面中、不额外套时间偏移，所以读取第 `F` 个已按作品 fps 重采样的源画面。对应的名义源时间为：

```text
sourceStartMs + 1000 × F / fps
```

该式用于理解映射，不把源 VFR 视频当作恒定原始帧号。真实取帧仍由平台按时间戳解码。改变画面位置和大小，不改变 `F`；素材不会因为缩放而从头播放。

固定坐标只适用于物体在已观察范围内确实停稳的情况。镜头平移、手持透视变化或物体继续运动时，本模板不提供自动跟踪，需要换素材范围、减少标注，或另行提出真实跟踪能力需求。

#### 7.6.6 完整技术试作源码

以下源码展示同一视频实例、共同坐标、连续观察范围和定时标注的实现。**它是需要实际素材驱动的工程试作模板，不是顶级美术效果的自动保证，也不是可以不填参数直接提交的 MCP 请求。** 参数是普通作品 `props`，不是新平台字段；素材仍通过当前 `videoBindings.footage` 绑定。

```tsx
import React from 'react';
import {AbsoluteFill, useCurrentFrame, useVideoConfig} from 'remotion';
import {BoundVideo} from '@videoflowcut/motion';

type Box = {x: number; y: number; width: number; height: number};
type Mark = {
  id: string; text: string;
  x: number; y: number; labelX: number; labelY: number;
  startSec: number; endSec: number;
};
type Props = {
  sourceWidth: number; sourceHeight: number;
  viewBefore: Box; viewAfter: Box;
  cameraStartSec: number; cameraEndSec: number;
  scopeBefore: Box; scopeAfter: Box;
  scopeStartSec: number; scopeExpandedSec: number; scopeEndSec: number;
  marks: Mark[];

};

const mix = (a: number, b: number, p: number) => a + (b - a) * p;
function progress(t: number, a: number, b: number) {
  if (!(b > a)) throw new Error('Invalid time range');
  const u = Math.max(0, Math.min(1, (t - a) / (b - a)));
  return u * u * (3 - 2 * u);
}
function blendBox(a: Box, b: Box, p: number): Box {
  return {
    x: mix(a.x, b.x, p), y: mix(a.y, b.y, p),
    width: mix(a.width, b.width, p), height: mix(a.height, b.height, p),
  };
}
function visible(t: number, start: number, end: number) {
  if (!(end > start)) throw new Error('Invalid visible range');
  const fade = Math.min(0.2, (end - start) / 3);
  return progress(t, start, start + fade) *
    (1 - progress(t, end - fade, end));
}

// 使用与画面相同的参数计算事件。事件表仍不代替真实观看。
export function resolveMotionEvents(
  p: Props, c: {fps: number; durationInFrames: number}
) {
  const frame = (s: number) => Math.round(s * c.fps);
  return [
    {id: 'view-expands', meaning: '观察范围开始扩大',
      startFrame: frame(p.cameraStartSec), endFrame: frame(p.cameraEndSec)},
    {id: 'whole-set-visible', meaning: '范围线到达整套物品的观察范围',
      startFrame: frame(p.scopeExpandedSec)},
    {id: 'graphics-yield', meaning: '图形让位给后续真实收纳',
      startFrame: frame(p.scopeEndSec)},
  ];
}

export default function Motion(p: Props) {
  const frame = useCurrentFrame();
  const {fps, width, height} = useVideoConfig();
  const t = frame / fps;
  const view = blendBox(p.viewBefore, p.viewAfter,
    progress(t, p.cameraStartSec, p.cameraEndSec));
  if (!(p.sourceWidth > 0 && p.sourceHeight > 0 &&
        view.width > 0 && view.height > 0)) throw new Error('Invalid geometry');
  const k = Math.min(width / view.width, height / view.height);
  const tx = (width - view.width * k) / 2 - view.x * k;
  const ty = (height - view.height * k) / 2 - view.y * k;
  const scope = blendBox(p.scopeBefore, p.scopeAfter,
    progress(t, p.scopeStartSec, p.scopeExpandedSec));
  const scopeOpacity = visible(t, p.scopeStartSec, p.scopeEndSec);

  return <AbsoluteFill style={{background: p.background, overflow: 'hidden'}}>
    <div style={{
      position: 'absolute', left: 0, top: 0,
      width: p.sourceWidth, height: p.sourceHeight,
      transformOrigin: '0 0',
      transform: `translate(${tx}px, ${ty}px) scale(${k})`,
    }}>
      <div style={{position: 'absolute', inset: 0}}>
        <BoundVideo slot="footage" offsetInFrames={0} fit="contain" />
      </div>
      <svg width={p.sourceWidth} height={p.sourceHeight}
        viewBox={`0 0 ${p.sourceWidth} ${p.sourceHeight}`}
        style={{position: 'absolute', inset: 0, overflow: 'visible'}}>
        <rect x={scope.x} y={scope.y}
          width={scope.width} height={scope.height}
          rx={12 / k} fill="none" stroke={p.accent}
          strokeWidth={2 / k} opacity={scopeOpacity} />
        {p.marks.map((mark) => {
          const alpha = visible(t, mark.startSec, mark.endSec);
          // 标签尺寸在最终画布上保持；归属位置仍来自同一源坐标。
          const labelWidth = (mark.text.length * 30 + 28) / k;
          const labelHeight = 48 / k;
          return <g key={mark.id} opacity={alpha}>
            <path d={`M${mark.x} ${mark.y} L${mark.labelX} ${mark.labelY}`}
              stroke={p.ink} strokeWidth={2 / k} fill="none" />
            <circle cx={mark.x} cy={mark.y} r={4 / k} fill={p.accent} />
            <rect x={mark.labelX} y={mark.labelY - labelHeight / 2}
              width={labelWidth} height={labelHeight}
              rx={6 / k} fill={p.labelFill} />
            <text x={mark.labelX + 14 / k} y={mark.labelY + 10 / k}
              fontFamily="Microsoft YaHei, sans-serif" fontSize={30 / k}
              fontWeight={600} fill={p.ink}>{mark.text}</text>
          </g>;
        })}
      </svg>
    </div>
  </AbsoluteFill>;
}
```

**参数怎样填写，才能不是一份空源码：**

| 参数 | 取得依据与填写规则 |
|---|---|
| `sourceWidth / sourceHeight` | 当前素材用于画面观察的实际显示尺寸，核对旋转与宽高比；不是随意填一个理想尺寸 |
| `viewBefore / viewAfter` | 在完整源画面上选定的两个观察区域；保护机身和后续物品，按目标画幅验证，不把示例坐标当实际测量 |
| `cameraStartSec / cameraEndSec` | 当前选段局部秒数；配件接近原视野边缘时开始扩大，按实际动作与阅读调整 |
| `scopeBefore / scopeAfter` | 机身与整套物品的实际观察包围范围；只表达观察范围，不作为精确测量数据 |
| `scopeStartSec / scopeExpandedSec / scopeEndSec` | 物品稳定后开始说明整套关系；范围线建立、到达与退出的局部秒数；退出应先于无跟踪的物体移动 |
| `marks` | 每个标注的实际对象位置、文字位置、放定之后到再次移动之前的显示范围；可少于或多于教学假设，不编造对象 |
| 四个色彩参数 | 从本片视觉语言和实际桌面决定；保证可辨认，不强制历史案例的黑底荧光配色 |

纯几何调试时，可以用人为设定的源尺寸 `1080×1920`、入口视域 `{x:90,y:200,width:900,height:1600}`、出口视域 `{x:0,y:0,width:1080,height:1920}`，检查两者在 `720×1280` 画布上的映射。这些数值**不描述一份已取得的素材**。标注坐标、实际源 ID 和源时间必须等待对应材料；没有材料时停在教学／工程测试，不冒充正式作品。

提交前由作者检查：时间严格有序、各事件在当前帧数内；标注 ID 唯一；标签在完整运动中不越界、不挡物体和字幕；真实字体下文字宽度适用。源码用字符数估计标签宽度只是中文短标签的试作做法，不是通用排版测量；长文本和混排需要按实际字形另行安排。

本例只有一次根级 `BoundVideo`，图形与视频共同变换；没有调用浏览器、网络、文件、音频或外部依赖。是否被当前平台校验器接受、是否达到预期观感，仍须实际提交与渲染测试。本轮没有运行项目依赖，所以不将这份源码标为测试通过。

#### 7.6.7 生成之后，怎样据实际问题改，而不只加缓动

| 实际观察到的问题 | 修改什么 | 复核什么 |
|---|---|---|
| 第一件配件进入时被裁在画面外 | 提前或重新定向扩大观察范围，调整入口视域 | 放入到落定的完整动作是否可见，机身是否仍可辨认 |
| 标签在手还遮着物品时出现 | 根据真实放定时刻推迟标签，或改标签位置 | 指认是否依附正确物品，手部动作有没有被遮挡 |
| 全部标签都在抢戏，整套关系不明显 | 已完成指认的标签提前退出；范围线阶段降低其他标注对比 | 观众是否能从单品切换到整套关系 |
| 拉远以后留白仍无用途 | 按实际物品调整出口视域与标签布局；必要时换更适合的素材构图 | 是否只是换了一个居中小框，还是实际对象改变了构图 |
| 放大后纹理或接口模糊 | 先核对原片细节与解码尺寸，再按第 7.8 节请求足够像素；必要时改观察范围 | 实际输出尺寸下细节是否恢复；不能以增大文字或锐化假装找回原像素 |
| 收纳时范围线与标签悬在空桌上 | 在实际物体移动前撤去图形，保留真实动作和原声 | 是否让现实过程完成结尾，而不是无根据的静态标注 |
| 台词结束得太早或重复解释动作 | 回文案作者调整准确台词，或让原声／动作接管 | 声画整体自然，不以冻结画面填满 TTS |

#### 7.6.8 换成真实录屏时，迁移什么，不照搬什么

网页或软件题材可以保留共同坐标与源时钟，但不照搬物品集合的范围线：先让实际界面建立对象，靠近将操作的区域；点击和状态变化继续由原录屏演出；图形指认真实变化，再退回能核对结果的画面。

需要引入真实说明页时，可以让仍有参照价值的录屏缩退，实际说明页取得主要阅读面积，再回到相关结果。是否两者同屏取决于阅读负荷，不固定使用左右分栏。原页面文字、高亮和视域共用坐标；没有原文截图时不能绘制一个看似官方的页面冒充来源。

这种迁移重新设计主要画面、阅读时机与出口，不只是把源码标签“电源”改成“设置”。

### 7.7 进入正式工程：工具、版本、时间与预算的衔接

#### 7.7.1 一次正式提交和修订的顺序

| 准备 | 读取当前 Project／Revision、正式素材与采用稿，读取实时 Schema | 原作者确认输入版本、完整内容、素材范围及前后接点 |

`creativeBrief` 当前最多 6000 字符，source 最多 60000 字符，props 的 JSON 最多 24000 字符。这里的完整制作说明应在合法大小内包含当前必要决定；超限交原作者重新组织，不由主任务静默截断。长篇案例教学放入本例参考正文，不把整本案例库塞进一次提交。未提交设计的跨会话恢复仍按第 2.3 节边界处理，本次不另建全文存储服务。

同一完整场面跨多句或多个相关 Beat，可以由一件作品承担，并用已有覆盖声明表达，不必按字幕句号拆成多个从头入场的小作品。Cue 控制放置和语义归属，不能靠外层 Props 或变速覆盖偷偷改变内部动画；内部布局、时序或绑定变化要生成新版本。

#### 7.7.2 跨 `Sequence` 时，为什么容易重播

当前 `BoundVideo` 使用所在位置的 `useCurrentFrame()` 加 `offsetInFrames`。如果后段 `Sequence` 从作品第 90 帧开始，该段局部第一帧是 0，不是 90。

```tsx
// 同一绑定从作品开头起持续播放；后段在作品第90帧接管：
<Sequence from={90}>
  <BoundVideo slot="footage" offsetInFrames={90} />
</Sequence>
```

这只演示偏移，不是完整防重影实现；前一显示分支要在接点停止或让位，避免两份视频同时覆盖。同一作品中无需切换实例时，直接像第 7.6 节一样保持根级实例更简单。

一般关系为：

```text
后段应该读取的解码帧 = 后段局部帧 + 后段起始时应接续的源偏移帧
项目全局帧 = Cue.startFrame + 作品局部帧       （当前匹配 fps 的合同下）
```

不要把 `sourceStartMs` 再换成帧加到 `offsetInFrames`：平台已经按绑定起点裁过源片，再加一次会错误跳过内容。切换到另一段素材时，偏移按新绑定自己的范围计算。当前支持的正常速度不因写了一个偏移而变成任意变速。

实际依据：[项目的 BoundVideo][motion-compiler]；Remotion 的局部时钟说明见 [useCurrentFrame][remotion-frame] 和 [Sequence][remotion-sequence]。本方案仅使用项目白名单中已确认的基本 API，不因为最新版官方文档出现其他能力，就默认项目也已发布。

#### 7.7.3 预算检查放在哪里

当前单作品时长上限 30 秒、帧数上限 900，并受画布像素帧预算约束；视频源和解码还分别有预算。它们是技术边界，不是建议把每一段都做满 30 秒。

以教学试作 `720×1280`、30 fps、10 秒为例：

```text
作品输出像素帧：720 × 1280 × 300 = 276,480,000
单路原画1080×1920按原尺寸解码：1080 × 1920 × 300 = 622,080,000
```

两者分别低于当前对应的 650,000,000 像素帧上限，但**仍不保证运行成功**：所有源文件合计与所有解码 PNG 仍各受 512 MB 限制，还需满足其他渲染预算与超时。上述只是一项算术核对，不是实际耗时、内存或磁盘测量。

**源文件字节与选段解码量不是同一预算。** 源文件合计 512 MB 检查的是实际绑定文件，缩短 `sourceStartMs/sourceEndMs` 不会让这个文件变小；缩短范围只会减少需要解码的帧量。文件超限应选择预算内的实际文件；没有已发布的受管裁片入口时，不让剪辑代理临时用 shell 绕过。必要裁片能力另行明确，不随本轮扩成媒体转换平台。

若原动作需要更长范围，重新计算资源和查看实际画质。优先减少无用绑定、采用真正需要的源区间；需要拆件时在有意义的接点拆，并核对两侧状态。不能为了通过预算静默降画质、剪掉动作、循环素材或把设计退回小窗。更大能力扩展单独评估，不在本轮直接取消安全预算。

### 7.8 工程修改一：先修正显示几何，再保留局部观察所需像素

本节包含一组有先后依赖的修改：**显示几何正确 → 固定引擎版本选择实际算法 → 计算观察尺度与解码预算 → 真实解码 → 固定产物与尺寸读回。** 不单独增加 `decodeScale` 后再靠目测补方向与比例；也不为了修几何，重构整个媒体服务。

#### 7.8.1 前置修复：编码宽高不等于正确显示后的宽高

基线 `probeMedia()` 返回视频流编码 `width / height`，没有在这一返回合同里提供旋转、像素宽高比（SAR）或归一化显示尺寸；`prepareMotionVideos()` 随后用这些宽高计算偶数尺寸，执行 `trim → setpts → fps → scale → setsar=1`。素材分析 Worker 额外读取过 rotation，也不代表动效解码链已经消费了它。[S02](#audit-s02)、[S04](#audit-s04)、[S05](#audit-s05)

上次审计在合成素材上复现：编码 `320×180`、旋转 90° 的源正常显示为 `180×320`；按现行尺寸公式进入 `180×320` 作品后，输出却为 `180×100`，白色正方形由约 `60×60` 被压成约 `60×18`。SAR 为 2:1 的另一测试，显示比例也由应有的 32:9 变成 16:9。这些是命令级证据，不是完整 Motion Job 或用户 Runtime 已测；详细边界在 10.4。

**第一版实施规则：**

1. 明确本次使用哪个视频流，让探测、尺寸计算和实际解码使用同一个流。取得编码尺寸、有效 SAR、旋转／显示变换；优先复用既有探测或增加小型共享函数，不默认全项目迁移 MediaMetadata。
2. 建立方向正确、方形显示像素下的归一化显示尺寸和坐标。覆盖普通素材、常见正交旋转，正确解释有效 SAR；无法可靠解释的显示变换明确返回不支持／需要规范化，不猜测或静默忽略。
3. 显示变换必须在探测解释和 FFmpeg 输出之间保持一致。旋转只应用一次；正确换算显示比例后才输出方形像素，不能把末尾 `setsar=1` 当作比例修正。输出实测宽高和画面形状要与计算结果核对。
4. `decodeScale` 及预算在归一化显示尺寸上计算。这里的“原显示尺寸”不是未经解释的编码尺寸；保持正确形状所需的重采样不等于增加了原素材的细节。
5. 作品 `sourceWidth/sourceHeight`、源坐标标注、已观察画面与实际解码读回描述同一方向、同一比例的画面。第 7.6 节模板不自动提供旋转补偿或物体追踪；坐标输入必须先有正确依据。

将所用流、编码尺寸、SAR／显示变换、归一化显示尺寸及实际输出尺寸等必要结果固定到本次 manifest 并读回。元数据来自本次真实探测／解码，不由作者凭素材名称填写。无法确认几何时返回具体失败位置，不能输出一张被拉伸的图后继续宣称可精确标注。

**验收：** 普通方形像素源、90°／180°／270° 旋转源、有效非方形像素源，以及不能可靠解释的显示变换；检查输出方向、比例、已知方形标记和源坐标指认，不只看编码宽高字段。工程测例用合成标记，不把它当真实创作案例。

#### 7.8.2 能力扩展：按需增加可选 `decodeScale`

基线 `apps/render-worker/src/motion-video.ts` 的 `prepareMotionVideos()` 使用：

```ts
const scale = Math.min(1, work.width / metadata.width, work.height / metadata.height);
```

对未旋转的方形像素源，1920×1080 横片进入 768×1344 作品时，整张源画面会先变成约 768×432。后面即使用源码靠近按钮或条款，也是在放大这份较小画面。这个问题影响细节，但不能解释所有平淡构图或缺少动作的问题。

**拟新增：为每个视频绑定增加可选 `decodeScale`。** 它表示保留归一化原显示尺寸的比例，有限数值且 `0 < value <= 1`。不自动分析任意 TSX 推导视野，不建立智能画质调度系统。

新 Job 不传比例时，继续采用“默认将完整源画面缩入作品边界”的尺度策略；普通未旋转方形像素源保持原缩放尺度和舍入。旋转／SAR 源则在新版本中先修正显示几何，不能承诺和旧错误像素逐字节一致。历史 Job 与旧缓存按 7.8.4 处理。

```ts
// 拟新增合同，不是当前可调用字段：
videoBindings: {
  footage: {
    assetId: '由实际项目返回的ID',
    sourceStartMs: /* 实际起点 */ 0,
    sourceEndMs: /* 实际终点 */ 10000,
    decodeScale: 0.75
  }
}
```

上述是字段说明，不是可直接执行的请求。归一化显示尺寸为 1920×1080 时，0.75 对应约 1440×810；30 fps、10 秒需要 349,920,000 解码像素帧。两路同条件合计 699,840,000，超过 650,000,000 限额，必须拒绝，不能逐路通过后忽略总预算。

第一版保持每边最多 1920 像素的解码上界。显式请求算出的任一边超过 1920，或偶数化后小于 2，明确拒绝，不暗中夹到边界；尺寸不得超过该输入的归一化原显示尺寸。这样避免仅按总像素帧通过时，极短大尺寸源先撑爆单帧缓冲。更高分辨率的局部裁切／解码另行评估，不夹带进本轮。

比例由作者根据最大观察尺度与最终观看尺寸提出。源平面到画布还会再放大时，要同时考虑这次放大；达到原显示尺寸仍不清楚，说明原片细节或观察方式不足，不用 `decodeScale>1` 伪造新细节。图形清晰也不代表内部源视频清晰。

#### 7.8.3 必须一起修改的位置与实际调用链

| 位置 | 具体改动 |
|---|---|
| 受管动效使用的探测／小型显示几何函数 | 固定所选视频流，解析尺寸、SAR 与显示变换，给出归一化显示坐标；只按实际需要扩展共享元数据，不重构所有媒体服务 |
| `packages/motion-work/src/schema.ts` | 公开 `videoBindings` 的严格对象与固定 `boundMotionVideoSchema` 同时增加可选 `decodeScale`；有限数值且 `0 < value <= 1`，不 `.default()` 注入旧对象，不静默修正非法值 |
| `packages/edit-application/src/index.ts` 的受管作品提交／完成 | 创建固定 `boundVideos` 时保留比例，与 source／hash／rights 一起固定；Job 不丢字段；完成及读回沿已有幂等与版本规则 |
| `apps/render-worker/src/motion-job.ts` 的 `runMotionJob()` | 按固定 Job 解析的引擎版本选择实际解码策略，并真正传到解码入口；work 与 boundVideos 逐槽核对比例，两边缺省可以一致，一边有值另一边没有则拒绝；继续固定并核验 source、manifest、输出 |
| `apps/render-worker/src/motion-video.ts` 的 `prepareMotionVideos()` | 消费明确的解码策略；先验证各槽实际文件、源范围和几何，再计算全部槽位尺寸、预计帧数、源文件总量和解码像素帧总量，通过可预检预算后才解码；PNG 编码量在执行中继续累计 |
| `packages/motion-work/src/compiler.ts` 与引擎版本处理 | 新输入／新几何使用明确的新引擎版本；保留旧哈希识别与旧算法恢复的实际分界，不能只更新版本常量而让所有旧 Job 共用新全局函数 |
| `read_motion_work` 当前读取路径／固定 manifest | 保存并返回各槽所用视频流、必要原几何、请求比例、归一化显示尺寸、实际解码尺寸与帧数；从 Worker 真正取得，不依据名称推测 |
| 正式 MCP／HTTP 工具、能力说明与发行 | 新 Schema 发布且 MCP／Runtime release 对齐后才可调用；旧会话不会因 docs 已写字段而自动支持 |

实际调用关系应能被开发者追踪为：固定提交与绑定 → `runMotionJob` 的固定引擎版本 → 对应解码策略 → 源几何／尺寸与预算 → 解码／渲染 → 固定 manifest／Asset → `read_motion_work`。旧恢复路径也必须沿固定版本选择，不只在哈希计算处识别版本。

`runMotionJob()` 已有工作区内临时目录、成功后固定源与 manifest、失败清理、资源及输出哈希核对。沿用这些结构，不另建解码服务或缓存数据库；失败清理不能删除旧作品版本。[S09](#audit-s09)、[实际 Job 与固定版本处理][motion-job]

#### 7.8.4 新旧版本兼容矩阵：不再笼统写“缺省全部保持旧行为”

基线 `runMotionJob()` 解析 `hashEngineVersion`，但调用 `prepareMotionVideos(root, temporary, work, boundVideos)` 时未把算法版本传下去。只有一套算法时这不是独立故障；实施几何修复后，仅更新全局 helper 与版本常量会让旧 Job 在缺缓存时误用新算法。[S09](#audit-s09)

**实现时由固定 Job 的引擎版本选择实际解码策略，不新增给创作代理自由填写的算法版本字段。** 必须落实以下行为：

| 输入／产物 | 必须采用的行为 |
|---|---|
| 旧固定作品已有有效缓存 | 核验并使用原缓存，不重写像素、源码或历史版本 |
| 旧 Job 缺缓存且确需恢复 | 按原引擎策略重执行；无法提供原行为时明确要求生成新版本，不能冒用旧 version 产出新版像素 |
| 新 Job 不传 decodeScale，普通未旋转方形像素源 | 保留原默认缩放尺度和舍入，走新版本的明确实现 |
| 新 Job 不传 decodeScale，含旋转／SAR | 新版本先正确处理显示几何；这是明确的缺陷修复，不声称新旧输出字节相同 |
| 新 Job 显式传 decodeScale | 在新版本正确几何上计算比例、偶数尺寸和累计预算，完整固定并核验绑定 |

新字段不得通过 `.default()` 改写旧 JSON，避免改变旧输入哈希。不能以“旧 hash 仍能识别”代替旧算法恢复；也不能以“缺省兼容”为由在所有新任务中继续保留旧比例错误。同一输入、同一固定引擎版本应保持既有确定性边界。

缓存命中仍执行既有固定 source、资源、帧与预览校验；所需新增读回信息不能从当前可变源码猜测。历史缺少新版几何摘要时如实说明，不批量重写历史 manifest 或重新渲染所有案例。

#### 7.8.5 预算、错误处理与代价

| 检查项 | 保留的边界 | 超限时怎样处理 |
|---|---|---|
| 实际绑定源文件合计 | 512 MB，按整个被绑定文件计 | 指明哪个文件及合计量超出；缩短选段不会减少文件字节，不让作者反复截短同一大文件 |
| 解码 PNG 合计 | 512 MB，实际编码中累计 | 像素预检通过不代表磁盘预算通过；到达上限按既有失败与清理机制退出 |
| 解码像素帧合计 | 650,000,000，累计全部槽位 | 返回各槽尺寸、预计帧数与总量，供作者减少无用绑定、缩紧确实不需的源范围或调整设计 |
| 显式解码边长 | 偶数化后至少 2、每边最多 1920，且不超过归一化原显示尺寸 | 明确拒绝，不暗中夹值、降低比例或上采样假装恢复细节 |
| 输出作品预算 | 仍遵守时长、帧数、画布和输出像素帧等原限制 | 分段须沿自然内容接点；源解码预算与输出预算分别核算 |
| 源范围与执行 | 保留真实范围、实际帧数、超时、哈希、受管路径与清理校验 | 源不足不自动冻结／循环，文件变化不复用旧观察或旧固定结果 |

报错返回具体槽位、请求尺寸、预计帧数及超出的是文件字节、解码像素、PNG 大小还是其他条件。不会减少文件体积的方案不要作为源字节超限的处理建议。没有正式发布的受管裁片能力时，选择预算内的实际文件或返回具体能力缺口；不能让剪辑代理临时用 shell、取消校验或无声降级绕过。

显示方向、非方形像素与图形坐标必须和实际画面一致；提高比例不能修复失焦、压缩块或过低的最终画布分辨率。更大的解码帧增加磁盘、I/O、处理时间和可能的内存压力，实际增幅需实测；不承诺固定速度或“比例越高越好”。不需要局部观察的普通输入继续使用默认尺度，不承担强制高分辨率成本。

### 7.9 工程修改二：记录某个动效作品里实际用了哪段视频

#### 7.9.1 当前缺的不是原片 ID，而是“原片这次被用在哪里”

当前 `MediaUsageTarget` 和工具的严格联合只接受：

```ts
{timelineItemId: string}
// 或
{effectCueId: string, slot: string}
```

后一项指向 EffectCue 的外层绑定。对于 `ManagedMotion`，外层 `slot=motion` 是**生成作品**，不是作品内部 `footage` 等视频槽位。`mediaUsageProblem()` 当前还要求时间素材关联 Timeline Item。因此不能把外层生成 Asset 冒充原片，也不能仅有 `sourceAssetIds` 列表就声称核对了具体源范围。[当前工具][media-tools]、[当前类型][media-contracts]、[当前采用逻辑][media-usage]

#### 7.9.2 拟新增的最小目标形式

沿用 `bind_media_adoption`，只在其 target 严格联合里增加一种形式：

```ts
// 拟新增；与现有两种形式互斥，不是当前可提交字段。
{effectCueId: string, motionVideoSlot: string}
```

调用者只指出“这次放置的作品里的哪个视频槽”。当前作品 Asset 和 version 必须由平台从该 Cue 的 `slot=motion` 解析，不接受客户端另外填一套可能不一致的 workAssetId／version。两次放置使用不同 Cue，就各有各的采用记录。

#### 7.9.3 如何让现有同步核验读到内部源范围

当前 `Asset.motion` 有版本、sourceAssetIds、源码路径和事件等信息，没有逐视频槽位的源范围。为避免让 `mediaUsageState(snapshot, target)` 临时读磁盘或变成异步爬取，增加一个**最多四项的固定摘要**：

```ts
// 拟新增到现有 Asset.motion；不是新增表，也不保存媒体字节。
videoSources?: Array<{
  slot: string;
  assetId: string;
  sourceHash: string;
  sourceStartMs: number;
  sourceEndMs: number;
}>;
```

摘要由 `completeManagedMotion()` 根据当前 Job 中已经固定、核验过的 `boundVideos` 生成，其中 `sourceHash` 取固定绑定的真实 hash。客户端不能直接提交或修改摘要。`runMotionJob()` 已核对 work／boundVideos、实际原文件、固定 manifest 与输出，沿这条完成路径传递，不把模型编写的素材说明当作摘要来源。[现有 Asset.motion][asset-motion]、[固定 Job 校验][motion-job]

这是对现有 Asset 的小型来源元数据扩展，不把全文观察、视频帧或研究缓存放进 ProjectSnapshot。已有 `sourceAssetIds` 可继续服务原用途，不能用它替代这里逐槽范围的核对。

#### 7.9.4 实际核验步骤

`packages/media-intelligence/src/usage.ts` 增加内部视频分支，并保留现有两种目标行为：

1. 找到 target 指定的 Cue，确认是 ManagedMotion，并解析当前实际绑定的作品 Asset／version。不存在、类型不匹配或槽位不存在时给出明确错误。
2. 从该作品的 `motion.videoSources` 找到 `motionVideoSlot`，取得固定原片身份、hash 与半开源区间，再与当前原片及采用记录比对。
3. 采用观察必须覆盖该槽位声明的源区间；本轮按**完整绑定范围**保守核对，不从 CSS 或事件名猜测只显示了哪几帧。实际只需短范围时，作者应缩紧绑定或补足观察。
4. 把内部视频的实际音频策略解释为静音。原片采用要求保留声音时，不能通过这个静音视觉槽位宣称声音已经保留；声音需要关联其真实 Timeline 使用。
5. 使用签名至少包含本次 Cue 身份与放置上下文、作品 Asset／version、内部槽位、原片 ID／hash、源范围及当前相关帧率。改变内部时序、换片、换版本或相关上下文，旧采用记录必须重新确认。
6. 返回本次 Cue 的项目范围供定位；不要把它伪装成已经自动计算出原片每帧在任意源码中的全部可见区域。裁切后的语义和标注正确性仍由连续合成复核。

同一旧作品在两个 Cue 使用时，修改其中一个 Cue 不能让另一个被误标为已经确认。作品换版后也不能仅因原片 ID 没变就继承全部采用判断，因为上下文、源范围或解释关系可能已经变了。

#### 7.9.5 修改位置、历史兼容与代价

| 位置 | 具体修改 |
|---|---|
| `packages/contracts/src/media-intelligence.ts` | 扩展 `MediaUsageTarget` 第三个互斥分支；旧两个分支的意义和序列化不变 |
| `apps/server/src/media-intelligence-tools.ts` | 扩展同一 `usageSchema`，让 MCP 和 HTTP 路由共用；同时传 `slot` 和 `motionVideoSlot` 等歧义输入拒绝 |
| `packages/contracts/src/index.ts` 的 `Asset.motion` | 增加可选、有限项的 `videoSources` 摘要 |
| `packages/edit-application/src/index.ts` 的 `completeManagedMotion()` | 从当前完成 Job 固定绑定生成摘要；应用层不接受任意外部摘要，不绕过现有幂等和版本检查 |
| `apps/render-worker/src/motion-job.ts` | 保持固定源／绑定一致性核对；与完成方法同步传递所需实际信息，缓存命中也不能跳过核验 |
| `packages/media-intelligence/src/usage.ts` | 实现新的状态解析、源范围与静音核验、签名和问题定位；不让旧“时间素材必须 Timeline”分支误拒绝已验证的新目标 |
| 现有 `app.intelligence.bind` 入口及相关调用者 | 接受新增联合类型并保存真实签名，读取后仍能区别三种用途；类型扩展后全面检查 `.slot` 访问，避免把它误当所有目标都有的字段 |

**第一版不批量回填历史作品。** 旧作品继续读取和渲染，旧采用方式不破坏。没有摘要的历史作品请求新式内部关联时，返回“缺少可核验的内部视频摘要”，不从文件名、当前可变源码或单一 sourceAssetIds 推断。确需使用新关联的旧作品，可以生成保留设计的新固定版本再采用；不要求为了本轮升级把六个历史案例或全部正式项目重新渲染。

代价是少量逐槽元数据、一个新目标分支和相关测试；换版后需要重新确认采用。这比另建素材状态机小，也比“反正原片下载过，所以所有用途都算已审”更可靠。

#### 7.9.6 生成、采用、合成与原声分别验证

`BoundVideo` 能生成不等于 `bind_media_adoption` 已经能定位内部槽位；采用关联通过也不等于任意裁切都保留了语义，更不等于原声已经播放。阶段 3 与阶段 4 分别检查固定作品生成、内部采用目标、最终合成和实际声音。

基线用途核验已有“采用要求 mute，而 Timeline 未静音”的检查，但不能反推填写一个保留原声的采用字段就自动保留了声音。[S10](#audit-s10) 新内部分支必须确认视觉槽本身静音；需要原声时沿实际音轨／素材声音合同关联真实源范围与项目范围，检查同步、重复播放及换版后的失效。没有现有入口可表达时返回该项具体缺口，不在 TSX 内嵌音频，也不把本轮扩为任意音轨抽取系统。

该完整声音路径在上次审计中未做端到端验证，本次合并不把它改写成通过。没有原声需求的场面不必额外造声音，但有需求时必须用实际听审说明实现结果。

| 发布与兼容 | MCP／HTTP 接受相同新合同；旧调用不传字段仍可用；候选 Runtime 与 MCP release 对齐；Skill／案例引用同步发行 | 证明工具可见和传输成立，不证明模型实际采用了好设计 |

若测试使用数字帧号或几何图案标记源进度，只用于工程验证；不把这些样本当成现实事件或最终美术。若没有候选 Runtime、媒体或相关依赖，记录哪些测试未执行，不编造通过结果。

#### 7.10.2 创作验证：从普通用户任务进入，而不是人工代写超长提示词

先选一项有实际材料的普通剪辑任务。用户只给主题、粗稿或常规素材要求，由系统自己完成研究／写稿／分镜／视觉深化。不要把第 7.6 节完整制作说明贴给最终执行者后，就声称日常链路已经会自行产生这种设计。

本轮保留以下实际对照，放在既有开发验收资料中，不新建一套作品管理系统：原需求、采用全文、实际素材与范围、导演分镜、作者制作说明、固定源码／参数、生成作品、合成预览、具体修改与当前结论。原片没有被本轮重新生成时，保持同源对照；比较不同版本时明确哪些台词、素材和实现变了，不把全部改善都归因于单一修改。

| 需要看见的结果 | 对应复核方式 | 不足以证明完成 |
|---|---|---|
| 文案不再是平铺介绍 | 实际读完整稿与试听，指出观察、行动、比较或认识如何推进；平静题材按真实体验判断 | 只有标题更夸张，正文没改变 |
| 素材确实承担内容 | 查看连续源范围，能够支持准确台词、具体动作或事实；缺项会推动补材或改稿 | 搜索次数多、链接多或下载数量增加 |
| 画面不再长期空旷小窗 | 以最终观看尺寸看主体、细节、留白用途与主次变化；必要时比较旧版同段 | 只是把中央窗口放大一点，其他过程仍没有发展 |
| 真实素材与图形共同发生 | 素材持续承担动作，图形指认、揭示或比较有明确归属，接点没有重播或跳位 | 先实拍两秒，再换另一套独立卡片 |
| 动作与美术都兑现 | 对照指令与实际视频：载体结构、排印、观察尺度、遮挡、动作中途及收势具体成立；核对真实 Cue／受管源码，而不凭案例名称认定路径正确 | 源码含高级效果名、弹簧参数或很多事件 |
| 放回成片仍然成立 | 听看当前配音、原声、字幕、人物及前后镜头，检查冲突与返回 | 单件无声动画看起来顺滑 |

首次生成后，按阶段 5 做一次实际修订，并读回新 Revision、作品版本、采用关系、源时钟、声音和字幕；不能只验证第一次生成。

第二个任务换成另一类实际内容，例如第一个是界面解释，第二个用数字人配合真实物品／日常行为。检查它是否重新选择画面关系，而不是把一套桌面模板复用到底。不要求一次跑完六个旧案例才能继续，也不要求用户为每个段落审批。

**收敛方式：** 优先修复已经看见、明显破坏理解或接续的问题；可选美术建议不导致无限返工。说明当前版本哪些范围已看、哪些未看，以及作品是否完成用户任务。真正的吸引力、审美偏好和留存变化还要看实际作品与用户反馈，不能由一份通过报告推断。


## 8. 唯一开发顺序与验收

**本节取代旧实施方案与旧审计中的两套执行顺序。** 默认一个开发任务按阶段 0—5 推进；第 4—7 节是各阶段的完整实施规格，不是另外几套任务。每个阶段的“完成标志”用于开发自检，不新增用户逐段审批或平台审美硬门槛。

### 8.1 阶段 0：确认基线，保护已有工作

**目的：** 明确这次要改的实际代码，不在错误版本上套方案。

读取真实仓库 AGENTS、当前分支与提交、未提交改动、相关 docs／Skills 和工具入口。对照本文固定 SHA，只检查本轮涉及的调用链与差异；后来已经实现或修复的部分保留并验证，不重新覆盖。已有未提交工作先保护，不执行会丢失它的重置、清理或强制覆盖。

按现有环境检查相关测试命令与依赖，记录本轮修改前的类型检查／相关测试基线。已有失败要区分与本任务相关的阻碍和无关问题，不能把它们全部转成“先修完整仓库”。外部 Key、浏览器或媒体依赖缺失列明影响范围，不虚报已联通。

**完成标志：** 能说明实际基线、已有改动、保留内容、需要处理的相关事项，以及下一阶段修改范围。没有发现新的直接阻碍就继续阶段 1，不在这里另写一套项目架构。

### 8.2 阶段 1：接通创作职责、完整交接与正确动效路径

**实施正文：第 4—5 节，以及第 7.2—7.6 节。** 本阶段先沿已有合同接创作，不以新增研究服务或解码字段为前提。

开发按第 4 节新增一个 Skill 与三个完整 references，按第 5 节修改既有入口。先保留现有项目合同，避免一开始改 Script 数据结构。

需要同时完成：

- 新主题和授权改稿能够由协调者实际分派文案作者；原声整理、锁稿与无旁白任务按原范围处理。
- 文案作者、素材作者与导演收到同一版用户约束和真实材料；材料发现同时回文案和导演，不只回导演留一条素材链接。
- 导演能收到全文，并交回明确采用稿或具体修改要求；原文案作者完成修订，主任务不擅自压缩正文。
- 完整原创正文通过现有 `apply_authored_script` 提交；下游采用实际返回的对象与 Revision。
- 真实原话编辑保持现有合同；混合 Script 追加原创旁白在本轮明确未支持，不得将真实全稿转为 authored 来绕过。此限制不阻止已有环境声配合新原创旁白。
- 新 Skill 加入已有显式登记／测试名单，发行同步能带上 references。不要只在 docs 写新 Skill 名称。

这一步可以用已在项目中的实际材料验证交接，不必等网络研究全部开发完。不能据此宣布外部研究或成片质量也已通过。

同时完成动效创作部分：按 7.4 局部修订 `remotion-production`、视觉规划、导演／协调、Cutaway、时间／声音和审阅 Skill；替换“先设计停稳卡片”等相冲突正文，保留可读性、稳定参照、人物／字幕保护及正式工具边界。不要只在文件末尾追加相反规则。

按 7.5 给六个案例分别补迁移教学，保留原 MP4、源码、fixture、完整指令与验证状态；按 7.6 将完整混合素材制作说明、时序、坐标、参数、源码与修订示例加入现有 casebook，不只改总索引。第七个教学示例不是已通过的新成片案例。

按 7.2.3 与 7.4.9 明确案例和内置 Registry 的区别：合适的简单组件继续使用，无法兑现内部过程时走受管原创作品。同一视觉作者默认持续完成深化、源码和修订，不再把完整场面拆给只拿到摘要的实现者。文案作者沿现有 `specialist`，不新增平台角色枚举。

**完成标志：** 新 Skill 和完整引用文件接入真实职责入口；采用稿沿现有整稿 Script 写入并处理 Impact；动效路径及相冲突正文已经明确。可用本地材料做限定范围的早期试作，但新接口／新字段尚未发布时不能调用，不能由此宣布外部研究和混合素材工程全部完成。是否真正由普通入口生成好稿与好设计，在阶段 5 继续检查。

### 8.3 阶段 2：先修复素材旧链，再补来源研究与受管取得

**实施正文：第 6 节。** 本阶段内部按 **2A → 2B → 2C → 2D** 推进，相关测试随实现补齐，不把全部修复拖到最后。

**2A．修 Pexels 视频预览和旧搜索结果格式。** 按 6.4.C／D 让 video 候选使用真实 MP4 预览，缺少则明确不可预览。结果格式版本进入操作层缓存资格；预置未过期的旧 JPEG 会话验证修复。旧候选、旧观察和运行中的 Job 不静默换身份，已取得原片不强制重下。

**2B．接通 Commons／Pexels 继续页。** 新格式候选链正确后，按 6.4.C 接 cursor／nextCursor、查询绑定、逐页缓存、每页预算和末页行为；保留部分失败恢复。旧缓存升级与分页一起验收，不把 cursor 当作结果格式版本的替代。

**2C．发布正式来源发现与原文读取。**

按第 6 节接通正式来源研究入口，配置一套可用的 Search/Extract 服务；落实候选继续页、查询缓存和视频预览类型。

开发目标是取得可读原文和可观察的候选，不是输出更多看似相关的 URL。正式剪辑依照发布后的 MCP Schema 调用；平台开发和密钥配置在开发任务完成，不让剪辑任务临时安装工具或改环境。

配置缺失与查询无结果分开返回。没有研究 Key 时，已有本地原片和 Commons 等可用部分继续工作；需要外部原文的具体结论保留缺口，不能自动改成未经核实的“通用科普”。

具体采用 6.1—6.4.A 的一组正式 MCP／HTTP 入口与一个 Tavily client，复用 RuntimeConfig；Search、Extract、正文缓存／分页、部分失败及配置脱敏一起接通。不能把四站动效参考浏览器扩成无约束通用抓取器，也不新增爬虫服务或 Docker 环境。

**2D．把选定来源变成正式可用素材。**

完成网页快照、公开图片／PDF等受管取得；保存来源、内容与结果的对应关系，并进入现有 Asset/EvidenceCapture。页面原文可读不代表已有可剪截图，素材封面可见不代表已检查连续视频。

视频复用现有已支持的取得方式。发现了不受支持平台的公开视频链接时，要如实返回“已发现来源、尚无可用取得能力”，继续寻找其他可用来源或由导演调整表达。不要在本文范围内默认承诺支持所有抖音、B站和需要登录的平台下载。

已选实际材料进入导演分镜，按需要由 Cutaway 或受管动效绑定。代表段要演出一次完整发展：实际操作／事实材料建立对象，图形指认或解释关系，再让实际结果接管。不能只验证动效的漂亮入口。

完成配置与能力摘要 → MCP／HTTP → 服务 → 获取 Job → Worker claim／分派 → 完成回写 → Asset／来源 → 实际观察与采用的完整衔接。PDF 进入画面时必须有正式登记的选定页 PNG Asset，而不只是导入 document 成功。沿现有哈希、许可／用途、受管路径、预算、超时、幂等和未知结果对账规则。

**完成标志：** 6.6 的相关行为测试完成，能区分发现链接、读取原文、取得原文件和观察连续视频；旧缓存不会让修复失效。外部凭据／网络未具备时，只报告替身测试和已验证部分，真实来源可用性保持待验证；可继续不依赖该来源的阶段 3，不能据此宣布阶段 2 的外部联调全部通过。

### 8.4 阶段 3：先修显示几何和版本，再扩展混合动效

**实施正文：第 7.7—7.10 节。** 创作方法在阶段 1 接入，这里补工程能力；不再重新写另一套视觉规范。

**3A．核对实际采用的实现路径。** 用具体代表段读取实际 Cue、绑定与源码，确认不是“学案例，却用不具备相应内部过程的同名模板”。对简单强调保留现有组件；对持续真实视频与图形统一编排，沿既有 `submit_motion_work`／ManagedMotion 路径。

**3B．一起落实显示几何与固定版本分派。** 按 7.8.1／7.8.3／7.8.4 确定视频流、旋转、SAR、归一化显示坐标和尺寸；把固定 Job 的引擎版本真正传入解码策略。普通默认尺度、新版几何修正、旧缓存和旧任务恢复分别处理，不用更新一个 hash 常量假装全部兼容。

**3C．在正确几何上加入 decodeScale。** 公开 Schema、固定 boundVideos、提交／完成、work 与绑定一致性、解码、版本／缓存、manifest 与读回一起更新。先累计所有槽位的可预检预算，再实际解码并累计 PNG 量；源文件字节超限与选段解码超限分开返回。显式非法值拒绝，不静默降级或取消预算。

**3D．接通内部视频采用与真实合成核对。** 按 7.9 扩展内部槽位目标和 `Asset.motion.videoSources` 有限摘要；只从真实固定 Job 生成摘要。关联具体 Cue、作品版本、内部槽位、原片／hash 和范围，保留旧目标与历史资产。分别验证作品生成、采用关联、合成播放和所需原声；不能用静音视觉槽位证明声音已保留。

本阶段可以用已取得的真实本地素材，不必等 Tavily 或所有外部取材完成。先跑真实作品与合成链，再确认清晰度、源时钟、采用关系和前后接点；普通输入的试作不能替代旋转／SAR 与旧任务恢复测试。

**完成标志：** 7.10.1 的相关工程检查有真实结果，普通及已声明支持的几何输入、固定版本／缓存、解码尺度、内部采用能够沿正式链读回。未实现／未测的具体情况仍列明，不批量重做历史项目、六个案例或全部 Registry。缺少实际声音入口的范围如实保留，不用源码内嵌音频绕过。

### 8.5 阶段 4：工程联调、同步与候选发行验证

**前提：** 本次准备发布的模块完成所属实现与测试；有明确外部限制的项目可以保留待验证状态，但不能在能力摘要和交付报告中宣称已可用。

沿用仓库 Node/TypeScript 和既有测试方式，不另造评测平台。建议补的行为测试：

- 搜索第二页实际请求到新候选，查询、游标与结果格式版本共同影响缓存；旧客户端不传游标仍可用，新格式不能复用旧 JPEG 结果。
- Pexels 视频分析取得视频数据，只有图片封面时明确表达其观察边界。
- Search/Extract 的部分失败被保留；长原文可继续读取，不能把摘要或截断正文标为完整。
- 网页／文件受管取得保存真实结果；拒绝的来源、超时和未知写入遵循现有错误与对账机制。
- 通过正式项目命令更新采用稿后，验证实际失效与音频／字幕状态；不测试“所有旧资源自动保持有效”这种并不存在的保证。
- 新 Skill、references 与发行副本引用可达；已有主任务单写入和真实子代理交接规则仍成立。
- 动效显示几何、解码尺度、源时钟、真实引擎策略分派和内部采用目标按第 7.10.1 节验证；普通默认尺度、旋转／SAR 缺陷修复、旧缓存复用和旧任务恢复按 7.8.4 分开验证。
- 实际 Cue／内置组件／受管作品分支与设计对应，不用案例名称或 Skill 加载日志冒充动作实现。源文件预算和选段解码预算不能混淆。
- 代表段真实合成按第 7.10.2 节检查，旁白、人物、字幕、源视频与图形一同复核，不能用 Skill 文本或事件字段替代观看。

不写“文件出现‘节奏’二字即通过”的镜像测试。自动检查能证明工具、版本与交接成立；稿件好不好、连续声画是否有吸引力，需要实际读稿和观看。

源方案基线已核对的命令包括 `npm run typecheck`、`npm run plugin:sync-skills`、`npm run plugin:build`、`npm run plugin:verify`，测试入口为 `tsx --test`。开发按实际修改选择相关测试，完成相关验证后构建发行物。候选运行时与生产运行时仍按现有 AGENTS 隔离；部署切换与正式剪辑分开，不在实现本方案时擅自改正在进行的项目。

在候选环境中实际走 MCP／HTTP → 应用层 → Job／Worker → 固定产物／读回 → Preview 的相关路径，确认新增字段与历史读取均按本文件处理。纯函数测试、教学 TSX 语法解析、文件里出现关键词或目录里有 Skill，都不能代替这项联调。MCP 与 Runtime release 不一致时保留现有拒绝机制，不修改已安装插件缓存来假装发布成功。

**完成标志：** 实际执行命令、修改文件、相应调用链、测试结果、候选发行标识与未验证外部依赖清楚可查。候选部署、正式生产切换和视频项目制作保持既有隔离；工程通过不代表已经完成用户要求的创作品质验收。

### 8.6 阶段 5：普通需求入口、实际修订、跨题材与整片验收

**实施正文：第 7.10.2 节，以及本节下表。** 在已验证的候选环境中，用普通用户请求进入，而不是人工替执行者写出最终专业方案。

由系统从普通需求进入，不给执行者追加一份手工长提示词，也不把附录例子原样当测试答案。

| 情形 | 需要看到的行为 | 不足以证明完成的结果 |
|---|---|---|
| 从陌生主题写原创稿 | 文案作者根据实际材料形成全文；主要段落有可跟随的观察／过程／比较；导演据此展开分镜 | 只有“钩子—解释—结尾”的题纲 |
| 优化一份并列粗稿 | 具体台词和段落发展发生改变，重要删留有依据，素材参与改稿 | 只增加感叹、反问和网络词 |

| 首批素材都不适用 | 按缺失的动作改查询、换来源或继续候选页，查看新候选实际内容 | 重复搜索同一句话并反复返回缓存首批 |
| 原计划的结果没发生 | 文案和导演改变判断或继续补证据，实际素材不被拼成虚构过程 | 用示意动画假装已完成真实测试 |

| 素材由主画面变为参照窗口 | 源进度连续、没有双影；原作者检查新旧构图与最终观看尺寸 | 只验证 CSS 能缩放，或新窗口从头重播 |
